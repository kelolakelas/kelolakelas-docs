# KEL-215 — private approval and invoice recovery

## Observed failure and correction

**Observed (24 October 2026, Asia/Jakarta):** billing's local `DUITKU_MERCHANT_CODE` and `DUITKU_API_KEY` were empty in both the file and running process. The 08:17:43 WIB approval trace reached academic and billing, with gateway request ID `cb20814f34860c20e4bda2fea967be93`; billing logged a Duitku inquiry HTTP 404. A fresh credential-free probe answered `Merchant not found`. The configured inquiry URL matches the [official Duitku API reference](https://docs.duitku.com/api/en/). No credential, account identifier or provider response containing payment details is reproduced here.

The owner supplied sandbox credentials and authorized restart. **Observed:** the restarted billing process has both variables populated, readiness is HTTP 200, and the signed read-only payment-method query answers HTTP 200 / responseCode 00. This establishes sandbox access; it does not establish production configuration.

## Recovery regression and implementation

**Observed:** with a synthetic parent-owned pending private request, pausing billing and approving through the actual tenant browser displayed an unavailable error while a gateway read confirmed the request was already `approved`. Academic commits the purchase before billing I/O. On the previous web revision, approved rows offered only sending a payment link, leaving no approval replay action after reload.

**Implemented:** approved requests without recommended slots offer **Lihat/pulihkan pembayaran** on desktop and mobile. The same confirmation dialog submits only the existing request ID to the existing tenant-scoped approval endpoint. Academic retains `private-request:<id>` and billing's existing invoice claim/replay behavior. No price, tenant, new purchase key or payment channel is accepted from this dialog. Recommendations accepted by a parent keep their existing separate path. A missing/unusable payment link is a retryable failure; network/5xx wording explains uncertainty and where to recover after reload. The normal permission, business refusal, focus-return and pending-submit behavior remains.

Source: web `app/(dashboard)/dashboard/tenant/schedule-requests/_actions/actions.ts`, `_components/ApproveScheduleRequestDialog.tsx`, `_components/ScheduleRequestTable.tsx`; academic `internal/usecase/private_schedule_request_usecase.go::purchase` and billing `internal/usecase/transaction_usecase.go` (unchanged).

## Acceptance evidence

- Actual local browser → Server Action → gateway → academic → billing → Duitku sandbox recovery produced a payment link after billing resumed.
- Two simultaneous gateway approval replays returned HTTP 200 and the same enrollment and transaction IDs. Read-only PostgreSQL counts after recovery/replay: one enrollment, one associated schedule, one generated session, one billing transaction.
- Parent gateway reads expose the same enrollment and transaction; the parent browser renders the corresponding pending invoice and virtual-account instructions in KelolaKelas.
- Parent and fixture Teacher approval attempts return 403; a database-confirmed existing foreign-tenant request returns 404 to the fixture owner. No reset/backfill, duplicate enrollment, provider payment settlement, or real-money payment was performed.
- Automated regressions cover incomplete payment answers, network uncertainty followed by identical-request retry, server/permission/business errors, approved-row recovery, exclusion of parent recommendation replay, dialog request identity and accessible confirmation.

No API or migration change is needed. No architectural decision changed, so no new ADR is introduced. The prior empty credential configuration is corrected only locally, outside Git.
