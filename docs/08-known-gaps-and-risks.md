Additional observations: service CORS only exists at the gateway; direct service exposure must be controlled by deployment (currently **Unknown**). Default DB SSL mode is `disable`, appropriate only for trusted local connections. No refresh/logout/password-reset/MFA endpoints were found.

**Resolved since the 2026-09-15 snapshot:** the academic category, class, list, and schedule handlers previously accepted `X-Tenant-ID` as a tenant source. Because the gateway only overwrites that header when the token carries a tenant claim, a parent token (which legitimately has none) could name an arbitrary tenant. Tenant context is now derived from the verified JWT claim only, with 403 for a missing claim, 401 for an unusable claim, and a claim/path match requirement on tenant enrollment; `kelolakelas-academic-service` commit `7e1ade30858af0d365f61e0f13526c9a4c602d60` (PR #5, KEL-19). See [ADR 0010](adr/0010-tenant-context-from-verified-jwt-claim-only.md). Billing was checked and never trusted the header; its handlers already read the JWT context value (`kelolakelas-billing-service/internal/delivery/http/handler/transaction_handler.go:33,109`).

The same defect existed independently in the identity service and is now also resolved there: `extractTenantID` (`internal/delivery/http/handler/role_handler.go:22-38` at the time) backed the member, role, and tenant handlers and fell back to `X-Tenant-ID` whenever the token had no usable tenant claim, so an authenticated parent could read the member and tutor directories, roles, and tenant settings and location of any tenant, and reach the corresponding mutations when holding a `role_id`. Tenant context now comes from the verified claim only, a caller without a tenant claim is refused with 403 before any use case runs, and the header is no longer part of the published contract; `kelolakelas-identity-service` commit `77a521da869c3dde746174cd0ea29c16460694da` (PR #5, KEL-16). See [ADR 0010](adr/0010-tenant-context-from-verified-jwt-claim-only.md).

**Also resolved:** an unpaid enrollment previously held its schedule seat indefinitely, because the academic capacity predicate counts `status IN ('pending','active')` and nothing moved an abandoned `pending` enrollment out of that set. Expiry and failure now enqueue a durable `release` reconciliation that drops the pending enrollment, so the seat returns to the catalog. `kelolakelas-billing-service` commit `ca5698b` (PR #5) and `kelolakelas-academic-service` commit `defd477` (PR #6), KEL-26. See [ADR 0012](adr/0012-release-enrollment-seat-on-failed-payment.md). The caveat about pre-existing rows is recorded above.

**Gateway boundary closed (KEL-18):** the two remediation notes above described the gateway as still forwarding or conditionally replacing `X-Tenant-ID`, which left the caller in control of the header value even after the services stopped reading it. The gateway now removes `X-Tenant-ID` and `X-Internal-Service-Credential` from every inbound request before any route runs, republishes `X-Tenant-ID` on protected routes from the verified JWT claim only, and refuses 401 for a token without `user_id` or a non-parent token without a usable tenant claim. The two consumer-side fixes above remain the protection for callers that reach a service directly; the gateway change removes the header from proxied traffic as well. See [ADR 0017](adr/0017-gateway-context-header-trust-boundary.md).

**Also resolved (KEL-17):** the five academic session and schedule mutation operations previously resolved their target through unscoped `GetByID` reads, so the tenant the handler had already derived was never part of the query. An authenticated member of any tenant holding a `schedule:update` role could reschedule another tenant's session, change a schedule or tutor permanently, substitute a tutor, or read another tenant's session attendees; the attendee route returned enrollment and student data. Each operation now resolves the resource through `GetByIDForTenant`, which joins `classes` and filters on the owning class's tenant, and a foreign id is reported exactly like a missing one: 404, no data change, and no student data read. The three bulk session writes repeat the predicate as `class_id IN (SELECT id FROM classes WHERE tenant_id = ?)`, the attendee enrollment read filters on `tenant_id` in the same statement, and `ChangeTutorTemporary` now runs inside a transaction. `kelolakelas-academic-service` commit `a47891d5aa183b9c6452ac5adc28e6bc947c1b22` (PR #9). See [ADR 0019](adr/0019-tenant-scoped-session-and-schedule-mutations.md). Two follow-ups this change deliberately did not take are recorded in the table above.
