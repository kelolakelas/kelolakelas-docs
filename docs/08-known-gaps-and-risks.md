**Also resolved (KEL-37):** the gateway proxied every request with no upstream deadline and no body-size limit, and started gin through `r.Run`, which leaves every `http.Server` timeout at zero. A downstream that accepted a request and never answered held the client, a gateway goroutine, and a connection indefinitely; a request body of any size was streamed to the downstream; and a proxy failure reached the client as the standard library's plain-text `Bad Gateway` rather than the envelope every other service returns. Each proxied exchange is now bounded by `PROXY_UPSTREAM_TIMEOUT_SECONDS` (default 30) derived per request with `context.WithTimeout`, a body over `PROXY_MAX_BODY_BYTES` (default 1 MiB) is refused with `413` before forwarding, and the server applies configured `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, and `IdleTimeout` values. Failures are classified into one envelope: `504` `Upstream service timed out`, `502` `Upstream service is unavailable`, or `413` for an oversized body, none of which contains the downstream host, path, or transport text. `kelolakelas-api-gateway` commit `9057e34` (PR #8). See [ADR 0021](adr/0021-bounded-gateway-proxy-and-error-envelope.md). Three consequences are recorded rather than mitigated: a downstream operation legitimately exceeding 30 seconds would now be cut (the measured worst case, tenant location geocoding, is capped well below it and the value is configurable), a future multipart upload over 1 MiB would be refused, and a chunked body with no declared length still reaches the handler before its size can be detected. Retry, circuit breaking, fail-closed rate limiting, and downstream graceful shutdown remain unimplemented and were explicitly out of scope.

Additional observations: service CORS only exists at the gateway; direct service exposure must be controlled by deployment (currently **Unknown**). Default DB SSL mode is `disable`, appropriate only for trusted local connections. No refresh or MFA endpoints were found; KEL-66 added password-reset request/confirm APIs and reset-triggered gateway revocation, but logout is still implemented in the web app only, and identity still exposes no logout endpoint ([ADR 0022](adr/0022-web-logout-ends-browser-session-only.md)).

**Also resolved (KEL-46):** the web app had no logout implementation anywhere in `app/` or `lib/`, while the session cookie written by login and tenant registration lives for seven days and no account affordance existed in the tenant or parent surfaces, so a shared device could not be released. `logoutAction` now deletes both session cookies and redirects to `/login`, and the `LogoutButton` form appears in the tenant sidebar footer, the tenant mobile drawer footer, the parent student-management and enrollment-history headers, and on the public catalog only while a parent session is active. Deletion is unconditional, so an already-signed-out session is a no-op rather than an error, and `revalidatePath('/', 'layout')` prevents the client router from serving a cached protected page. `kelolakelas-web` commit `ef3bda7c65db8e5241c252de825a5aa19ce63b60` (PR #11). See [ADR 0022](adr/0022-web-logout-ends-browser-session-only.md). Two consequences are recorded rather than mitigated: the JWT remains valid up to its 24-hour expiry for any copy taken before logout, because identity has no denylist or revocation route, and logout in one tab does not update other open tabs until their next navigation or reload.

**Also resolved (KEL-45):** the parent enrollment screen at `/dashboard/parent/enrollments` only displayed status, so the cancellation endpoint that shipped with KEL-27 ([ADR 0016](adr/0016-cancel-pending-enrollment.md)) had no surface in the web app and a parent who changed their mind still held the seat until `invoice_expires_at` passed. The row now offers a cancel control backed by the `cancelPendingEnrollment` Server Action, which posts to `POST /api/v1/enrollments/{id}/cancel` with the session bearer token, sends no request body, and revalidates the screen on success so the row reflects the backend's `dropped` state rather than an optimistic local guess. Confirmation uses a native `<dialog>` opened with `showModal()` instead of `window.confirm`, so the prompt is keyboard reachable, focus-trapped, and labelled via `aria-labelledby`. The action is offered only while `canCancelEnrollment` holds — enrollment `pending` and newest transaction neither `paid` nor `refunded` — which mirrors ADR 0016's refusal table so a parent is never shown a control whose only outcome is a 409. `5xx` responses are replaced rather than passed through, because the academic handler answers `500` with the raw Go error string. `kelolakelas-web` PR #15 (KEL-45). Two consequences are recorded rather than mitigated: no optimistic status is written locally, so the row keeps the backend status until the revalidation lands, and the provider invoice still cannot be revoked, so a parent holding an open checkout link can pay after cancelling — that payment is recorded and its activation rejection appears through the existing reconciliation states rather than on this screen. Separately, the same screen's `window.confirm` usage in the parent student deletion control was **not** changed by this issue and remains a follow-up.

**Resolved since the 2026-09-15 snapshot:** the academic category, class, list, and schedule handlers previously accepted `X-Tenant-ID` as a tenant source. Because the gateway only overwrites that header when the token carries a tenant claim, a parent token (which legitimately has none) could name an arbitrary tenant. Tenant context is now derived from the verified JWT claim only, with 403 for a missing claim, 401 for an unusable claim, and a claim/path match requirement on tenant enrollment; `kelolakelas-academic-service` commit `7e1ade30858af0d365f61e0f13526c9a4c602d60` (PR #5, KEL-19). See [ADR 0010](adr/0010-tenant-context-from-verified-jwt-claim-only.md). Billing was checked and never trusted the header; its handlers already read the JWT context value (`kelolakelas-billing-service/internal/delivery/http/handler/transaction_handler.go:33,109`).

The same defect existed independently in the identity service and is now also resolved there: `extractTenantID` (`internal/delivery/http/handler/role_handler.go:22-38` at the time) backed the member, role, and tenant handlers and fell back to `X-Tenant-ID` whenever the token had no usable tenant claim, so an authenticated parent could read the member and tutor directories, roles, and tenant settings and location of any tenant, and reach the corresponding mutations when holding a `role_id`. Tenant context now comes from the verified claim only, a caller without a tenant claim is refused with 403 before any use case runs, and the header is no longer part of the published contract; `kelolakelas-identity-service` commit `77a521da869c3dde746174cd0ea29c16460694da` (PR #5, KEL-16). See [ADR 0010](adr/0010-tenant-context-from-verified-jwt-claim-only.md).

**Also resolved:** an unpaid enrollment previously held its schedule seat indefinitely, because the academic capacity predicate counts `status IN ('pending','active')` and nothing moved an abandoned `pending` enrollment out of that set. Expiry and failure now enqueue a durable `release` reconciliation that drops the pending enrollment, so the seat returns to the catalog. `kelolakelas-billing-service` commit `ca5698b` (PR #5) and `kelolakelas-academic-service` commit `defd477` (PR #6), KEL-26. See [ADR 0012](adr/0012-release-enrollment-seat-on-failed-payment.md). The caveat about pre-existing rows is recorded above.

**Gateway boundary closed (KEL-18):** the two remediation notes above described the gateway as still forwarding or conditionally replacing `X-Tenant-ID`, which left the caller in control of the header value even after the services stopped reading it. The gateway now removes `X-Tenant-ID` and `X-Internal-Service-Credential` from every inbound request before any route runs, republishes `X-Tenant-ID` on protected routes from the verified JWT claim only, and refuses 401 for a token without `user_id` or a non-parent token without a usable tenant claim. The two consumer-side fixes above remain the protection for callers that reach a service directly; the gateway change removes the header from proxied traffic as well. See [ADR 0017](adr/0017-gateway-context-header-trust-boundary.md).

**Also resolved (KEL-17):** the five academic session and schedule mutation operations previously resolved their target through unscoped `GetByID` reads, so the tenant the handler had already derived was never part of the query. An authenticated member of any tenant holding a `schedule:update` role could reschedule another tenant's session, change a schedule or tutor permanently, substitute a tutor, or read another tenant's session attendees; the attendee route returned enrollment and student data. Each operation now resolves the resource through `GetByIDForTenant`, which joins `classes` and filters on the owning class's tenant, and a foreign id is reported exactly like a missing one: 404, no data change, and no student data read. The three bulk session writes repeat the predicate as `class_id IN (SELECT id FROM classes WHERE tenant_id = ?)`, the attendee enrollment read filters on `tenant_id` in the same statement, and `ChangeTutorTemporary` now runs inside a transaction. `kelolakelas-academic-service` commit `a47891d5aa183b9c6452ac5adc28e6bc947c1b22` (PR #9). See [ADR 0019](adr/0019-tenant-scoped-session-and-schedule-mutations.md). Two follow-ups this change deliberately did not take are recorded in the table above.

**Also resolved (KEL-24):** `creating` was written but never unwound, so a failed or interrupted invoice creation left the transaction in that status with no exit. `ClaimInvoice` matched only `pending` and `failed`, the enrollment could therefore never be invoiced again, and because the academic capacity predicate counts `status IN ('pending','active')` the seat stayed held. There was also no column recording why creation failed, so the cause was reachable only in logs. The claim is now recorded in the row (`invoice_claimed_at`) and is reclaimable once it is older than `TRANSACTION_CLAIM_TIMEOUT_MINUTES` (default 10), the provider-failure path releases the claim immediately through `RestoreFailedInvoiceClaim`, and `invoice_failure_reason` exposes the cause through the API; `MarkInvoiceIssued` clears both fields. `kelolakelas-billing-service` commit `9772e10` (PR #7). See [ADR 0020](adr/0020-reclaimable-invoice-claim.md). Two consequences are recorded rather than mitigated: the timeout must exceed the longest legitimate gateway response or an in-flight attempt can be invoiced twice, and a claim released after a failure keeps its `invoice_claimed_at` timestamp as evidence, so `status = 'creating'` rather than a non-null timestamp is what identifies a live claim.

**Also resolved (KEL-42):** each public catalog request previously called identity `GetTenantPublicInfo` for every tenant owning a class and re-saved each snapshot, so an unauthenticated, unthrottled route translated one browser request into one gRPC round trip plus N writes, and the call had no per-call bound (`pkg/grpcclient/tenant_client.go` used the caller context unchanged). Snapshots are now refreshed only when missing or older than `CATALOG_TENANT_INFO_TTL_MINUTES` (default 5), written in one `ON CONFLICT (tenant_id) DO UPDATE` that touches only the refreshed rows, and each identity call is bounded by `CATALOG_TENANT_INFO_TIMEOUT_MS` (default 2000). An identity outage is logged and skipped, and the catalog still answers from the stored snapshot. `mustUUID` previously swallowed a parse failure into `uuid.Nil`, so a tenant id identity could not parse was stored under the nil key and became readable through every tenant's snapshot lookup; such rows are now dropped and logged. Tenant visibility is also consistent between the two catalog paths: the list already filtered on an active snapshot, while the detail joined on `t.is_active = true` with the same result, so the pair now shares one join and a class of an inactive tenant is absent from both. Two consequences are recorded rather than mitigated: an inactive tenant's class disappears from the catalog without a snapshot row to prove why, and `updated_at` is the only freshness signal, so a snapshot refreshed by any other writer silently extends the TTL. Evidence: `internal/usecase/catalog_usecase.go`, `internal/repository/catalog_repository.go`, `pkg/grpcclient/tenant_client.go`; tests `internal/usecase/catalog_usecase_test.go`, `internal/repository/catalog_snapshot_test.go`, `pkg/grpcclient/tenant_client_test.go`.
