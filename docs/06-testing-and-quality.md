# Testing and quality

**Implemented:** Go unit tests exist for config, middleware, selected handlers/use cases, database utilities, migration tooling, Duitku signatures, email client, and subscription worker. Web exposes Vitest through `npm run test`, plus `eslint`, TypeScript checking, and production build commands. Auth-routing and proxy regression tests cover role-aware destinations, open-redirect rejection, and malformed/expired cookie handling. Pure presentation and parsing helpers are unit-tested without a DOM: `lib/list-envelope.test.ts` covers the enveloped, bare-array and malformed payload shapes the tenant class readers accept, and `lib/class-publication.test.ts` covers the publication/enrollment badge and action labels. Dashboard query modules are testable without a browser: `app/(dashboard)/dashboard/tenant/enrollments/_queries/queries.test.ts` stubs `global.fetch` and `next/headers` to assert the outgoing gateway contract (bearer and tenant headers, the `page_size` and `status` it sends, one billing request per enrollment), the forbidden mapping of `401`/`403`, and each degradation path — a failed per-enrollment transaction lookup, a failed schedule list read, and a malformed billing payload all still yield rows. Rendered output is asserted with `renderToStaticMarkup` from `react-dom/server` rather than a DOM testing library, which keeps the Vitest `node` environment unchanged: `_components/EnrollmentTable.test.tsx` covers both layout branches, the payment-state labels, and the empty-versus-filtered empty states. Academic session and schedule tenant scoping is tested at three layers, because the use-case tests use in-memory fakes and therefore cannot detect a dropped SQL predicate: `internal/repository/session_schedule_scope_test.go` asserts on the generated statements through `sqlmock` (`GetByIDForTenant` joins `classes` on the owning tenant, the three bulk writes each carry `class_id IN (SELECT id FROM classes WHERE tenant_id = ?)`, and `GetActiveByScheduleID` filters on `tenant_id`), `internal/usecase/session_schedule_scope_test.go` covers the five operations for both the owning and a foreign tenant plus transaction and error-propagation behaviour, and `internal/delivery/http/handler/session_schedule_scope_handler_test.go` covers tenant resolution from the token, the permission-before-tenant ordering, alias id handling, and status mapping. The web CI gate in `.github/workflows/ci.yml` runs on every pull request to `main` and executes `npm ci`, `npm audit --omit=dev --audit-level=high` (KEL-68), `npm run test`, `npx tsc --noEmit`, ESLint over the TypeScript files changed by the pull request, and `npm run build` with a placeholder `GATEWAY_API_URL`; the Go repositories run `go mod download`, `go mod verify`, a `gofmt` check, `go vet ./...`, `go test -race -count=1 ./...`, `go build ./...`, and `go run golang.org/x/vuln/cmd/govulncheck@v1.8.0 ./...` (KEL-68). Evidence: `rg --files` under each repository and `package.json`, `lib/auth-routing.test.ts`, `lib/list-envelope.test.ts`, `lib/class-publication.test.ts`, `proxy.test.ts`, `app/(dashboard)/dashboard/tenant/enrollments/_lib/schema.test.ts`, `app/(dashboard)/dashboard/tenant/enrollments/_queries/queries.test.ts`, `app/(dashboard)/dashboard/tenant/enrollments/_components/EnrollmentTable.test.tsx`, `vitest.config.ts`, academic `internal/repository/session_schedule_scope_test.go`, academic `internal/usecase/session_schedule_scope_test.go`, academic `internal/delivery/http/handler/session_schedule_scope_handler_test.go`, `.github/workflows/ci.yml`.

## Dependency vulnerability gate (KEL-68)

**Implemented (KEL-68):** the required `gate` check in every application repository fails when a dependency carries a known advisory. The job id and check name `gate` did not change, so branch protection needs no update; the new step only adds to the existing steps.

| Repository | Step | Fails when |
|---|---|---|
| `kelolakelas-web` | `Audit production dependencies`: `npm audit --omit=dev --audit-level=high`, right after `npm ci` | a production dependency (direct or transitive) in `package-lock.json` has a high or critical advisory. Advisories affecting only `devDependencies` are excluded by `--omit=dev` and do not fail the gate. |
| `kelolakelas-api-gateway`, `-identity-service`, `-academic-service`, `-billing-service` | `Vulnerability check`: `go run golang.org/x/vuln/cmd/govulncheck@v1.8.0 ./...`, after `Build` | code reachable from the module calls a symbol with a known Go vulnerability (standard library or module). Advisories in required modules that the code does not call are printed as informational and do not fail the gate. |

The tool version is pinned (`govulncheck@v1.8.0`; `npm` comes with the Node 20 runtime that `actions/setup-node` installs). Never run the scan with `GOFLAGS=-mod=mod`: that flag lets the Go command rewrite `go.mod`.

Both steps **fail closed**: if the vulnerability database (`vuln.go.dev`) or the npm registry audit endpoint cannot be reached, the step exits non-zero with a connection error and no findings. That failure is not a finding. Re-run the job; if the outage persists, wait for it to clear rather than bypassing the step.

Proof (throwaway PRs, closed without merge): gateway PR [#23](https://github.com/kelolakelas/kelolakelas-api-gateway/pull/23) replaced `golang.org/x/net` with v0.34.0 and called `html.Parse`; `gate` failed only at `Vulnerability check` with eight called vulnerabilities, starting with GO-2026-5030 ([run](https://github.com/kelolakelas/kelolakelas-api-gateway/actions/runs/36250119004)). Web PR [#36](https://github.com/kelolakelas/kelolakelas-web/pull/36) added the production dependency `js-yaml@4.3.0`; `gate` failed at `Audit production dependencies` on GHSA-2883-xcg3-v3hh (high) ([run](https://github.com/kelolakelas/kelolakelas-web/actions/runs/36250121206)). The real KEL-68 PRs passed the new step on clean `main`.

### Handling a new advisory

When `gate` fails on the new step (on your own PR, or on every PR because an advisory was published against code already on `main`):

1. **Read the finding.** Take the advisory id (`GO-…`, `GHSA-…`), the affected package and version, and the fixed version from the step log. For Go, `govulncheck -show verbose ./...` shows the call path; for web, `npm audit --omit=dev` lists the dependency chain.
2. **Upgrade (the default remedy).** Move to the fixed version in a PR of its own linked to a Linear issue: `go get <module>@<fixed>` then `go mod tidy` (or raise the `go` directive for a standard-library advisory, since CI follows `go-version-file`), or `npm install <pkg>@<fixed>` / `npm audit fix --omit=dev` for web. Re-run the scan locally, then the repository's normal gates. Check every repository that shares the dependency; the same advisory usually affects several Go services.
3. **No fix available, or the upgrade is not safe yet: a documented, time-boxed exception.** The gate has no allowlist and no `continue-on-error`, so an exception is itself a reviewed change and never a silent skip. It needs, together:
   - a Linear issue that names the advisory id, the affected repositories, why the upgrade cannot land now, the reachability/exposure assessment, and an explicit **expiry date** by which the exception is removed or renewed (the contract sets no maximum; choose it per advisory and record the reason);
   - a row for the advisory in [known gaps and risks](08-known-gaps-and-risks.md) linking that issue;
   - the narrowest code change that excludes only that advisory id (for example a scripted filter on `govulncheck -format json` output or on `npm audit --json`), in its own PR that cites the issue and the expiry, and that is removed when the fix ships.

   Never disable the step, drop `--omit=dev`/`--audit-level`, or widen the exclusion beyond the single advisory id.
4. **Outage, not a finding:** re-run the job (see fail-closed above).
