# Identity service (`kelolakelas-identity-service`)

**Implemented:** Gin HTTP server default `:8080`, gRPC tenant service fixed at `:50051`, PostgreSQL via GORM, optional Redis, Resend invitation delivery, and optional Google Maps geocoding. Startup wiring is in `cmd/server/main.go:33-158`.

Data owned by its migrations includes users, tenants, tenant members, roles, permissions, role permissions and invitations. The HTTP API handles registration/login, tenant registration/settings/location, invitations, member operations and roles. Handler/ use-case/ repository separation is present under `internal/delivery`, `internal/usecase`, and `internal/repository`.

JWT issuance uses HS256 and has a 24-hour validity. Login selects a tenant/member context according to `AuthUsecase.Login`; Redis permission caching is populated during tenant registration and login when Redis is available. Tenant-administration mutations query persisted role permissions rather than relying on that cache (`internal/usecase/permission.go`, `internal/repository/member_repository.go`). Every one of those checks passes the tenant being operated on, and the lookup only counts an assignment when the role belongs to that tenant or is a system role with a null tenant, so a role owned by another tenant never grants access; a role that no longer exists matches no row and is therefore denied rather than reported as an error. `CreateInvitation` additionally resolves the role it would grant and rejects one that does not exist, belongs to another tenant, or is not a system role with a 400 validation error before persisting anything. No refresh-token route, logout route, or session-revocation check was found (`pkg/jwt/jwt.go`, `internal/usecase/auth_usecase.go`). Logout is therefore implemented in `kelolakelas-web` alone, by deleting the browser's session cookies ([ADR 0022](../adr/0022-web-logout-ends-browser-session-only.md)).

Tenant context for the member, role, and tenant HTTP handlers is resolved from the `tenant_id` claim of the validated access token and from nothing else (`internal/delivery/http/handler/tenant_context.go`). The shared `tenantIDFromContext` helper reads the context value that `AuthMiddleware` set from the verified JWT and never reads a request header; `writeTenantError` maps a missing claim to 403 and an unusable claim to 401. Because login issues a nil `tenant_id` for users without an active membership, which includes every parent, a parent calling a tenant-scoped route is rejected in the handler before any use case runs. This mirrors the academic service's resolution path recorded in ADR 0010.

The gRPC service implements `ValidateTenantStatus`, `GetTenantPublicInfo`, and the internal `tenant.PermissionService/CheckPermission` contract used by academic catalog, student, and enrollment middleware. The request carries `role_id`, `permission`, and `tenant_id`; permission checks join persisted `role_permissions` to `permissions` and apply the same tenant-or-system-role rule, so they do not rely on Redis or active JWT claims. While `PERMISSION_REQUIRE_TENANT_ID` is false a request that omits `tenant_id` is still answered with the previous tenant-blind result, because identity is deployed before academic and must stay compatible during that window; setting the flag to true rejects such a request as `InvalidArgument` (see [ADR 0002](../adr/0002-academic-permission-enforcement.md)). gRPC server/client transport security and authentication are not configured in the inspected code; network restriction remains required.
