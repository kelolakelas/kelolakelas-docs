# Identity service (`kelolakelas-identity-service`)

**Implemented:** Gin HTTP server default `:8080`, gRPC tenant service fixed at `:50051`, PostgreSQL via GORM, optional Redis, Resend invitation delivery, and optional Google Maps geocoding. Startup wiring is in `cmd/server/main.go:33-158`.

**Implemented (KEL-63):** the build toolchain is pinned by `go 1.26.6` (`go.mod`; CI follows via `go-version-file`), fixing the reachable go1.26.5 standard-library advisories (GO-2026-6089/GO-2026-5026 `net/http`, GO-2026-6090 `crypto/tls`, GO-2026-5972 `encoding/asn1`, GO-2026-6218 `net/url`, GO-2026-6091 `html/template`). `google.golang.org/grpc` moves v1.82.1 → v1.83.2 (GO-2026-6348, OOM heap growth via HTTP/2 DATA-frame fragmentation, and GO-2026-6443) — the same version academic-service now uses, so both ends of the `tenant.PermissionService/CheckPermission` contract run on it. `github.com/jackc/pgx/v5` moves v5.6.0 → v5.9.2 (GO-2026-5004), and `go mod tidy` promotes it and `golang-migrate/migrate/v4` from `// indirect` to direct `require` entries because both are already imported directly (`internal/repository/creator_request_repository.go`, `internal/migration/tools.go`); tidy-driven transitives (`golang.org/x/{crypto,net,text,tools}`, `google.golang.org/genproto/googleapis/rpc`) follow. `govulncheck ./...` reports no vulnerabilities; no runtime code or behaviour changed, and the `internal/delivery/grpc` tenant-contract tests pass under `-race`. Evidence: `kelolakelas-identity-service/go.mod`, `go.sum`; PR #16, squash `29598211601bc8ab6fbf5e9d1977456653ce82c0`.

**Implemented (KEL-68):** the required CI `gate` job ends with `Vulnerability check`, `go run golang.org/x/vuln/cmd/govulncheck@v1.8.0 ./...`, so a PR that makes a known-vulnerable symbol reachable (standard library or module) fails; uncalled module advisories are informational. The step fails closed when `vuln.go.dev` is unreachable (re-run). Evidence: `.github/workflows/ci.yml`; PR [#25](https://github.com/kelolakelas/kelolakelas-identity-service/pull/25), squash `fffd2c39644afbd167171b0fbdbd13a66eb1bb65`. Procedure for a new advisory: [testing and quality § Dependency vulnerability gate](../06-testing-and-quality.md#dependency-vulnerability-gate-kel-68).

Data owned by its migrations includes users, tenants, tenant members, roles, permissions, role permissions, invitations, platform admin assignments, and (since KEL-94) Creator requests. The HTTP API handles registration/login, tenant registration/settings/location, invitations, member operations and roles. Handler/ use-case/ repository separation is present under `internal/delivery`, `internal/usecase`, and `internal/repository`.

JWT issuance uses HS256 and has a 24-hour validity. Login selects a tenant/member context according to `AuthUsecase.Login`; Redis permission caching is populated during tenant registration and login when Redis is available. Tenant-administration mutations query persisted role permissions rather than relying on that cache (`internal/usecase/permission.go`, `internal/repository/member_repository.go`). Every one of those checks passes the tenant being operated on, and the lookup only counts an assignment when the role belongs to that tenant or is a system role with a null tenant, so a role owned by another tenant never grants access; a role that no longer exists matches no row and is therefore denied rather than reported as an error. Since KEL-76 the lookup also requires the caller's active, non-deleted `tenant_members` row in that tenant that still carries the token's role (see below). `CreateInvitation` additionally resolves the role it would grant and rejects one that does not exist or belongs to another tenant with a 400 validation error before persisting anything; a system Creator target is rejected with 403. Invitation email delivery is reported instead of swallowed (KEL-36): the use case captures the `SendInvitationEmail` outcome on the transient `TenantInvitation.EmailSent` field (`gorm:"-"`, serialized as `email_sent`), logs a failure with the invitation and tenant IDs but never the token, and the handler keeps **201** for a stored invitation while its message distinguishes a delivered email from a failed one. The Resend client is built through `resend.NewCustomClient` with a 10-second `http.Client` timeout (`pkg/email/resend.go`), so a stalled provider call can no longer hold the invitation request open. No refresh-token or logout route was found. Reset-triggered session revocation is implemented as described below; logout remains web-only (`pkg/jwt/jwt.go`, `internal/usecase/auth_usecase.go`), implemented in `kelolakelas-web` by deleting the browser's session cookies ([ADR 0022](../adr/0022-web-logout-ends-browser-session-only.md)).

**Implemented (KEL-61):** the three handler error branches that used to quote the use case error in a 500 body — tenant registration (`RegisterTenant`), invitation creation (`CreateInvitation`), and invited-user registration (`RegisterInvitedUser`) — now log the original error server-side through `slog.ErrorContext` carrying only the operation context and the error (never payload values such as passwords or tokens) and answer with a fixed generic message inside the unchanged `{status, message, data}` envelope (`Failed to register tenant and user`, `Failed to create invitation`, `Failed to register invited user`). Mapped 4xx branches (403/404/409) and the 400 `ShouldBindJSON` validation feedback are unchanged, and after this change no identity HTTP handler answers 500 with raw error text; the remaining `err.Error()` sites in handlers are mapped 4xx branches only. Regression tests drive each branch with an internal-looking database error and assert the marker is absent from the response body while present in the captured server log. Evidence: `kelolakelas-identity-service/internal/delivery/http/handler/{auth_handler,invitation_handler}.go`, `internal/delivery/http/handler/sanitize_500_test.go`; PR #20, squash `70bc2410349117d094bf38e7d3bcfeef9f2ef07c`.

Tenant context for the member, role, and tenant HTTP handlers is resolved from the `tenant_id` claim of the validated access token and from nothing else (`internal/delivery/http/handler/tenant_context.go`). The shared `tenantIDFromContext` helper reads the context value that `AuthMiddleware` set from the verified JWT and never reads a request header; `writeTenantError` maps a missing claim to 403 and an unusable claim to 401. Because login issues a nil `tenant_id` for users without an active membership, which includes every parent, a parent calling a tenant-scoped route is rejected in the handler before any use case runs. This mirrors the academic service's resolution path recorded in ADR 0010.

**Implemented (KEL-82):** tenant-scoped `GET /api/v1/invitations` lists unredeemed invitations (including expired entries with an `expired` status), and `DELETE /api/v1/invitations/:id` marks an unredeemed invitation used; both require `member:invite`. `CreateInvitation` rejects existing accounts with 409 before sending email, and atomically replaces prior unredeemed invitations for the same tenant/email under a tenant row lock before sending a fresh token. Create and list responses explicitly omit the bearer token. Verification and registration reject revoked or superseded tokens. Evidence: `cmd/server/main.go`, `internal/usecase/invitation_usecase.go`, `internal/repository/invitation_repository.go`, `internal/delivery/http/handler/invitation_handler.go`; PR #14 (`258ddd4d727a481c16ac1ca0df64815afd06dcc6`).

**Implemented (KEL-93):** `migrations/000002_platform_admin.up.sql` creates an assignment keyed by existing user ID, independent of tenant roles. A database-authorized operator can idempotently grant or restore it using `go run ./cmd/platform-admin -user-id <uuid>`; there is no public grant endpoint. `POST /api/v1/platform/auth/login` checks password and active assignment before issuing a tenantless `is_platform_admin` JWT (since KEL-105 the password stage issues a non-privileged pending token instead; see the KEL-105 entry below). `GET /api/v1/platform/me` checks that signed claim and re-reads the assignment and user, so revocation denies a still-unexpired token. The identity middleware refuses a platform-only token on ordinary protected tenant routes; an account with both capabilities uses separate logins. Apply the migration before exposing the routes. Recovery and revocation precautions are in identity `PLATFORM_ADMIN.md`; no production bootstrap was verified. See [ADR 0026](../adr/0026-platform-admin-assignment-and-principal.md).

**Implemented (KEL-96):** Identity now owns a static configuration metadata catalog for five applications and a platform-admin-only record-only API for inventory, non-secret version requests, history, and operator application-status acknowledgements (`internal/usecase/configuration_catalog.go`, `internal/usecase/configuration.go`, `internal/delivery/http/handler/configuration_handler.go`). Migration `000003_configuration_control_plane` adds version heads, immutable requested versions, and append-only reports; it does not migrate or override deployed environment values. A signed platform claim and a fresh active-assignment check protect every route. Metadata includes owner, type, redacted default, sensitivity, validation, deployment application method and bootstrap-only status; secrets are catalog-only and cannot be written or read back. Reports do not independently prove deployment; KEL-97 tenant registration and KEL-98 public catalog are runtime applied-version consumers, while other catalog values remain record-only. See [ADR 0027](../adr/0027-configuration-control-plane-record-only.md) and [ADR 0031](../adr/0031-applied-tenant-registration-policy.md).

**Implemented (KEL-98):** migration `000009_public_catalog_policy` seeds the `academic/platform/PUBLIC_CATALOG_OPEN` head at version 0 (open). Platform-only `GET /api/v1/platform/catalog-policy` reads effective open state and desired/applied versions; `POST .../close` and `.../open` append desired boolean versions with optimistic head checking. The generic configuration history/report endpoints provide actor audit, applied acknowledgement, and rollback by version; desired changes alone do not become effective. A desired-only policy after version 0 hides the catalog until an applied report; a missing head, corrupt boolean, or storage error fails closed. The `tenant.CatalogPolicyService/GetPublicCatalogPolicy` RPC exposes the same effective state to academic over the existing identity gRPC listener. Neither class nor tenant rows are updated. Apply migration 000009 before rolling out academic. Evidence: `internal/{repository/public_catalog_policy.go,usecase/public_catalog_policy.go,delivery/grpc/catalog_policy_service.go,delivery/http/handler/public_catalog_policy_handler.go}`, `migrations/000009_public_catalog_policy.up.sql`; PR #23, squash `225292705dfff275897e4a49a899c79fb485e5c8`; [ADR 0036](../adr/0036-applied-public-catalog-policy.md).

**Implemented (KEL-97):** migration `000007_registration_policy` seeds a version-0 default-open head for the typed `identity/platform/TENANT_REGISTRATION_OPEN` setting. Platform admins can read effective state with desired/applied versions and append open/close requests; the existing configuration history supplies actor/timestamp audit, and an `applied` report activates the requested version. Registration evaluates this policy before any writes and rechecks it in the user/tenant/wallet/Creator transaction under a shared head lock; applied acknowledgements take an exclusive lock. Missing/invalid policy or store failure rejects new registration with stable 403 and no partial records. Login, platform bootstrap, invited-user registration, and existing tenants are unaffected. Apply migration 000007 before exposing the feature. Close/open responses re-evaluate applied state: a pending close still returns `open: true`, and a pending open still returns `open: false`, with divergent `applied_version` and `desired_version`. Evidence: identity PR #17 (`c1fa5e3234e787ec7932dc958fdc16972bf517e5`) and correction PR #18 (`c8893abd4a39c931ea1c67a11f162a1b01e2136a`), `internal/{repository/registration_policy.go,usecase/registration_policy.go}` and [ADR 0031](../adr/0031-applied-tenant-registration-policy.md).

**Implemented (KEL-94):** `POST` and `GET /api/v1/creator-requests` let an active tenant Creator create and list pending requests for the tenant in the verified JWT. `internal/repository/creator_request_repository.go` checks live membership and the system Creator role under a row lock; request creation resolves target email/user, rejects existing active Creator targets, and never changes membership. Migration `000004_creator_requests` stores requests and enforces one pending request per tenant and normalized target email. Invitation creation, legacy invitation redemption and member role updates reject a system Creator target with 403, while initial tenant registration remains intact. Apply the migration before deploying these routes.

**Implemented (KEL-103):** `GET /api/v1/platform/creator-requests` joins the identity `platform` group protected by `AuthMiddleware` and `RequireActivePlatform`; it returns only pending cross-tenant requests joined to tenant names, oldest first with id tie-break, without pagination/filter. The response selects decision-relevant columns, never credentials or unrelated members. Repository errors return 500 without exposing SQL. Tenant list and approve/reject behavior remain unchanged. Evidence: `cmd/server/main.go`, `internal/{domain,repository}/platform_creator_request*`, `internal/delivery/http/handler/platform_creator_request_handler.go` and tests, generated Swagger; [identity PR #24](https://github.com/kelolakelas/kelolakelas-identity-service/pull/24), squash `fd033ccac7649e34f3b0bce85eadd4321dce95f5`; [ADR 0037](../adr/0037-creator-request-browser-queue.md).

**Implemented (KEL-95):** active platform admins decide pending Creator requests through `POST /api/v1/platform/creator-requests/{id}/approve` and `.../reject` (mounted in the active-platform-admin group in `cmd/server/main.go`). `internal/repository/creator_decision_repository.go` runs the whole decision in one transaction: live admin assignment locked `FOR SHARE`, request locked `FOR UPDATE`, target email re-resolved under the lock, then grant (member upgrade or email-bound invitation) + request update + `creator_request_audit` insert (UNIQUE `request_id`) commit together; a replayed decision returns 409. Approving an unregistered email creates an invitation linked by `creator_requests.invitation_id` and grants nothing until acceptance: `internal/repository/user_repository.go` `RegisterInvitedUserTx` locks the invitation `FOR UPDATE` and permits Creator redemption only when exactly one approved request matches invitation, tenant, and email with `target_user_id` NULL. Stale targets (email remapped, parent, suspended/deleted tenant, inactive/deleted membership, already Creator) yield no grant. Migration `000005_creator_decisions` adds the decision columns and audit table. See [ADR 0029](../adr/0029-platform-admin-creator-decision.md).

**Implemented (KEL-105):** platform login is now two-stage. A correct password on an active assignment returns a five-minute pending JWT (`platform_pending`, bound to the assignment's factor version) that no protected handler accepts: identity's `AuthMiddleware` rejects pending and legacy versionless platform tokens with 401, and `GET /api/v1/internal/session/check` applies the same rule for the gateway. `POST /api/v1/platform/auth/challenge` (purpose `enroll`|`verify`) and `POST /api/v1/platform/auth/verify` implement RFC 6238 TOTP: challenges are 256-bit tokens stored only as SHA-256 hashes, bound to user/purpose/factor version, five-minute expiry, five-attempt limit, consumed inside one transaction that row-locks the assignment and challenge (`internal/repository/platform_factor.go`), so concurrent verifications cannot both succeed and verifier/storage failure answers 503 without a password-only fallback. Seeds are stored AES-256-GCM-encrypted under `PLATFORM_FACTOR_KEY` (32-byte hex, required at startup; identity exits without it). Migration `000008_platform_factor` adds `factor_secret`, `enrollment_allowed`, `factor_version` and the `platform_factor_challenges` table; existing assignments stay unenrolled after migration. `cmd/platform-admin` recovery now also deletes factor material and challenges, re-enables one enrollment, and bumps `factor_version`, invalidating old platform/pending JWTs; verified sessions carry `platform_factor_version` and `/platform/me` re-checks assignment plus version on every request. `ADR-KEL-105.md` in the repo records the implementation decision and [ADR 0032](../adr/0032-platform-admin-second-factor-totp.md) the docs copy. Evidence: identity PR #19 (squash `5ca2ddb1aee4946143e8ecacd5c18e4648bb9ed9`).

**Implemented (KEL-66):** public password-reset request and confirm handlers use a 256-bit random token whose SHA-256 digest alone is stored in `password_reset_tokens`; `migrations/000006_password_reset.up.sql` also adds nullable `users.session_valid_after`. Request rotation and confirmation serialize on the user row, and confirmation updates password hash, token consumption, and the session boundary in one transaction. Default token TTL is 60 minutes (`PASSWORD_RESET_TTL_MINUTES`); invalid values fail config loading. The internal `/api/v1/internal/session/check` handler independently verifies the signed JWT and reads the boundary; it returns 204/401/503 for active/revoked-or-unknown/unavailable respectively. Gateway does not proxy that path publicly. Resend sends a link using `APP_URL`, with delivery failures logged without the address/token and a generic public 200. The web entry and `/reset-password` confirmation pages are implemented by KEL-67 ([web component](web.md), web PR #32, `21c3ba5087a640fa3346c62a9c151cc16a10a61a`). Evidence: `internal/repository/password_reset_repository.go`, `internal/usecase/auth_usecase.go`, `internal/delivery/http/handler/{auth_handler,session_handler}.go`, identity PR #13 (`e5d5e2ba411c0b78b7e145aaaf9db3b838991dc8`), [ADR 0030](../adr/0030-password-reset-and-gateway-session-revocation.md).

**Implemented (KEL-88):** registration handlers reject passwords over 72 bytes and names/phone fields exceeding the persisted column limits with 400. Tenant settings rename checks for another tenant's name case-insensitively before mutation and returns 409; optional `google_place_id` length is enforced by request binding. Unique-constraint races are not translated here. Evidence: `internal/delivery/http/handler/registration_limits_test.go`, `internal/usecase/tenant_settings_conflict_test.go`, `internal/repository/tenant_name_test.go`; identity PR #15 (`cc9459680436ce5ac5d2bd246b718a53efb30fb4`).

The gRPC service implements `ValidateTenantStatus`, `GetTenantPublicInfo`, and the internal `tenant.PermissionService/CheckPermission` contract used by academic catalog, student, and enrollment middleware. The request carries `role_id`, `permission`, and `tenant_id`; permission checks join persisted `role_permissions` to `permissions` and apply the same tenant-or-system-role rule, so they do not rely on Redis or active JWT claims. While `PERMISSION_REQUIRE_TENANT_ID` is false a request that omits `tenant_id` is still answered with the previous tenant-blind result, because identity is deployed before academic and must stay compatible during that window; setting the flag to true rejects such a request as `InvalidArgument` (see [ADR 0002](../adr/0002-academic-permission-enforcement.md)). gRPC server/client transport security and authentication are not configured in the inspected code; network restriction remains required.

**Implemented (KEL-76):** permissions are granted only through an active membership with the token's role. `repository.ActiveMemberHasPermission` joins `tenant_members` (`tenant_id`, `role_id` = token role, `is_active`, explicit `deleted_at IS NULL`) to roles (tenant or system role), `role_permissions` and `permissions` in one count query. `AuthMiddleware` puts the verified caller (`domain.Caller{UserID, MemberID}`) into the request context, and every in-process check (`usecase.callerHasPermission`) uses it: a token with the `member_id` claim is pinned to that row and user; a token without the claim matches by (tenant, user, role). A missing caller or an incomplete query is denied without a lookup, and a lookup error is returned, never allowed. A removed, deactivated or re-roled member therefore gets 403 on permission-gated identity routes (e.g. `DELETE /api/v1/members/:id`) with a still-valid token; re-login restores access for the new role. Ungated reads such as `GET /api/v1/members` are unchanged. gRPC `CheckPermission` accepts an optional `member_id`: with it (and `tenant_id`, otherwise `InvalidArgument`; a non-UUID/nil/non-string value is also `InvalidArgument`) `allowed` requires that active membership; without it (absent, null or empty string) the previous query is used unchanged. Academic and billing send it on every tenant check since KEL-80. Evidence: `internal/repository/member_permission.go`, `internal/domain/caller.go`, `internal/usecase/permission.go`, `internal/delivery/http/middleware/auth_middleware.go`, `internal/delivery/grpc/permission_service.go`; PR #21, squash `8bf0bf8b842c518730994602475cdf205525f03c`; [ADR 0034](../adr/0034-permission-requires-active-membership.md).

**Implemented (KEL-79):** `PUT /api/v1/members/:id/role` no longer freezes every member on a system role. `memberRepository.UpdateRole` now takes the verified caller and runs its guards inside the update transaction, before the write: member in the token's tenant (404), not the caller's own membership (409 `ErrMemberSelfRoleChange`, matched on the `member_id` claim or on `user_id` for tokens without it), target role in the tenant or a system role (409), never the system Creator as target (403, KEL-94), and never a member whose current role is the system Creator (403 "Creator role cannot be changed"). A system Teacher can therefore be moved to a tenant custom role and back. The `member:update` check still runs first in `usecase.memberUsecase.UpdateRole`. Evidence: `internal/repository/member_repository.go` (`isOwnMembership`, `isSystemCreatorRole`), `internal/domain/member.go`, `internal/delivery/http/handler/member_handler.go`, `internal/delivery/http/middleware/kel79_member_role_integration_test.go` (PostgreSQL, `KEL79_TEST_DATABASE_URL`); PR #22, squash `cf5d4f6a49c90abc5c215768e07f3489bb33ecd3`; [ADR 0035](../adr/0035-member-role-change-self-and-creator-guards.md).
