# Identity service (`kelolakelas-identity-service`)

**Implemented:** Gin HTTP server default `:8080`, gRPC tenant service fixed at `:50051`, PostgreSQL via GORM, optional Redis, Resend invitation delivery, and optional Google Maps geocoding. Startup wiring is in `cmd/server/main.go:33-158`.

Data owned by its migrations includes users, tenants, tenant members, roles, permissions, role permissions, invitations, platform admin assignments, and (since KEL-94) Creator requests. The HTTP API handles registration/login, tenant registration/settings/location, invitations, member operations and roles. Handler/ use-case/ repository separation is present under `internal/delivery`, `internal/usecase`, and `internal/repository`.

JWT issuance uses HS256 and has a 24-hour validity. Login selects a tenant/member context according to `AuthUsecase.Login`; Redis permission caching is populated during tenant registration and login when Redis is available. Tenant-administration mutations query persisted role permissions rather than relying on that cache (`internal/usecase/permission.go`, `internal/repository/member_repository.go`). Every one of those checks passes the tenant being operated on, and the lookup only counts an assignment when the role belongs to that tenant or is a system role with a null tenant, so a role owned by another tenant never grants access; a role that no longer exists matches no row and is therefore denied rather than reported as an error. `CreateInvitation` additionally resolves the role it would grant and rejects one that does not exist or belongs to another tenant with a 400 validation error before persisting anything; a system Creator target is rejected with 403. Invitation email delivery is reported instead of swallowed (KEL-36): the use case captures the `SendInvitationEmail` outcome on the transient `TenantInvitation.EmailSent` field (`gorm:"-"`, serialized as `email_sent`), logs a failure with the invitation and tenant IDs but never the token, and the handler keeps **201** for a stored invitation while its message distinguishes a delivered email from a failed one. The Resend client is built through `resend.NewCustomClient` with a 10-second `http.Client` timeout (`pkg/email/resend.go`), so a stalled provider call can no longer hold the invitation request open. No refresh-token or logout route was found. Reset-triggered session revocation is implemented as described below; logout remains web-only (`pkg/jwt/jwt.go`, `internal/usecase/auth_usecase.go`), implemented in `kelolakelas-web` by deleting the browser's session cookies ([ADR 0022](../adr/0022-web-logout-ends-browser-session-only.md)).

Tenant context for the member, role, and tenant HTTP handlers is resolved from the `tenant_id` claim of the validated access token and from nothing else (`internal/delivery/http/handler/tenant_context.go`). The shared `tenantIDFromContext` helper reads the context value that `AuthMiddleware` set from the verified JWT and never reads a request header; `writeTenantError` maps a missing claim to 403 and an unusable claim to 401. Because login issues a nil `tenant_id` for users without an active membership, which includes every parent, a parent calling a tenant-scoped route is rejected in the handler before any use case runs. This mirrors the academic service's resolution path recorded in ADR 0010.

**Implemented (KEL-82):** tenant-scoped `GET /api/v1/invitations` lists unredeemed invitations (including expired entries with an `expired` status), and `DELETE /api/v1/invitations/:id` marks an unredeemed invitation used; both require `member:invite`. `CreateInvitation` rejects existing accounts with 409 before sending email, and atomically replaces prior unredeemed invitations for the same tenant/email under a tenant row lock before sending a fresh token. Create and list responses explicitly omit the bearer token. Verification and registration reject revoked or superseded tokens. Evidence: `cmd/server/main.go`, `internal/usecase/invitation_usecase.go`, `internal/repository/invitation_repository.go`, `internal/delivery/http/handler/invitation_handler.go`; PR #14 (`258ddd4d727a481c16ac1ca0df64815afd06dcc6`).

**Implemented (KEL-93):** `migrations/000002_platform_admin.up.sql` creates an assignment keyed by existing user ID, independent of tenant roles. A database-authorized operator can idempotently grant or restore it using `go run ./cmd/platform-admin -user-id <uuid>`; there is no public grant endpoint. `POST /api/v1/platform/auth/login` checks password and active assignment before issuing a tenantless `is_platform_admin` JWT. `GET /api/v1/platform/me` checks that signed claim and re-reads the assignment and user, so revocation denies a still-unexpired token. The identity middleware refuses a platform-only token on ordinary protected tenant routes; an account with both capabilities uses separate logins. Apply the migration before exposing the routes. Recovery and revocation precautions are in identity `PLATFORM_ADMIN.md`; no production bootstrap was verified. See [ADR 0026](../adr/0026-platform-admin-assignment-and-principal.md).

**Implemented (KEL-96):** Identity now owns a static configuration metadata catalog for five applications and a platform-admin-only record-only API for inventory, non-secret version requests, history, and operator application-status acknowledgements (`internal/usecase/configuration_catalog.go`, `internal/usecase/configuration.go`, `internal/delivery/http/handler/configuration_handler.go`). Migration `000003_configuration_control_plane` adds version heads, immutable requested versions, and append-only reports; it does not migrate or override deployed environment values. A signed platform claim and a fresh active-assignment check protect every route. Metadata includes owner, type, redacted default, sensitivity, validation, deployment application method and bootstrap-only status; secrets are catalog-only and cannot be written or read back. Reports do not independently prove deployment, and no service consumes these values at runtime. See [ADR 0027](../adr/0027-configuration-control-plane-record-only.md).

**Implemented (KEL-94):** `POST` and `GET /api/v1/creator-requests` let an active tenant Creator create and list pending requests for the tenant in the verified JWT. `internal/repository/creator_request_repository.go` checks live membership and the system Creator role under a row lock; request creation resolves target email/user, rejects existing active Creator targets, and never changes membership. Migration `000004_creator_requests` stores requests and enforces one pending request per tenant and normalized target email. Invitation creation, legacy invitation redemption and member role updates reject a system Creator target with 403, while initial tenant registration remains intact. Apply the migration before deploying these routes.

**Implemented (KEL-95):** active platform admins decide pending Creator requests through `POST /api/v1/platform/creator-requests/{id}/approve` and `.../reject` (mounted in the active-platform-admin group in `cmd/server/main.go`). `internal/repository/creator_decision_repository.go` runs the whole decision in one transaction: live admin assignment locked `FOR SHARE`, request locked `FOR UPDATE`, target email re-resolved under the lock, then grant (member upgrade or email-bound invitation) + request update + `creator_request_audit` insert (UNIQUE `request_id`) commit together; a replayed decision returns 409. Approving an unregistered email creates an invitation linked by `creator_requests.invitation_id` and grants nothing until acceptance: `internal/repository/user_repository.go` `RegisterInvitedUserTx` locks the invitation `FOR UPDATE` and permits Creator redemption only when exactly one approved request matches invitation, tenant, and email with `target_user_id` NULL. Stale targets (email remapped, parent, suspended/deleted tenant, inactive/deleted membership, already Creator) yield no grant. Migration `000005_creator_decisions` adds the decision columns and audit table. See [ADR 0029](../adr/0029-platform-admin-creator-decision.md).

**Implemented (KEL-66):** public password-reset request and confirm handlers use a 256-bit random token whose SHA-256 digest alone is stored in `password_reset_tokens`; `migrations/000006_password_reset.up.sql` also adds nullable `users.session_valid_after`. Request rotation and confirmation serialize on the user row, and confirmation updates password hash, token consumption, and the session boundary in one transaction. Default token TTL is 60 minutes (`PASSWORD_RESET_TTL_MINUTES`); invalid values fail config loading. The internal `/api/v1/internal/session/check` handler independently verifies the signed JWT and reads the boundary; it returns 204/401/503 for active/revoked-or-unknown/unavailable respectively. Gateway does not proxy that path publicly. Resend sends a link using `APP_URL`, with delivery failures logged without the address/token and a generic public 200. The reset web page is not implemented. Evidence: `internal/repository/password_reset_repository.go`, `internal/usecase/auth_usecase.go`, `internal/delivery/http/handler/{auth_handler,session_handler}.go`, identity PR #13 (`e5d5e2ba411c0b78b7e145aaaf9db3b838991dc8`), [ADR 0030](../adr/0030-password-reset-and-gateway-session-revocation.md).

**Implemented (KEL-88):** registration handlers reject passwords over 72 bytes and names/phone fields exceeding the persisted column limits with 400. Tenant settings rename checks for another tenant's name case-insensitively before mutation and returns 409; optional `google_place_id` length is enforced by request binding. Unique-constraint races are not translated here. Evidence: `internal/delivery/http/handler/registration_limits_test.go`, `internal/usecase/tenant_settings_conflict_test.go`, `internal/repository/tenant_name_test.go`; identity PR #15 (`cc9459680436ce5ac5d2bd246b718a53efb30fb4`).

The gRPC service implements `ValidateTenantStatus`, `GetTenantPublicInfo`, and the internal `tenant.PermissionService/CheckPermission` contract used by academic catalog, student, and enrollment middleware. The request carries `role_id`, `permission`, and `tenant_id`; permission checks join persisted `role_permissions` to `permissions` and apply the same tenant-or-system-role rule, so they do not rely on Redis or active JWT claims. While `PERMISSION_REQUIRE_TENANT_ID` is false a request that omits `tenant_id` is still answered with the previous tenant-blind result, because identity is deployed before academic and must stay compatible during that window; setting the flag to true rejects such a request as `InvalidArgument` (see [ADR 0002](../adr/0002-academic-permission-enforcement.md)). gRPC server/client transport security and authentication are not configured in the inspected code; network restriction remains required.
