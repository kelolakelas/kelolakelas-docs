**Implemented (KEL-71):** the HTTP server is built by `newHTTPServer` (`cmd/server/server.go`) with bounded timeouts instead of `&http.Server{Addr, Handler}` with none:

| Setting | Server field | Default |
|---|---|---|
| `SERVER_READ_HEADER_TIMEOUT_SECONDS` | `ReadHeaderTimeout` | 5 |
| `SERVER_READ_TIMEOUT_SECONDS` | `ReadTimeout` | 30 |
| `SERVER_WRITE_TIMEOUT_SECONDS` | `WriteTimeout` | 60 |
| `SERVER_IDLE_TIMEOUT_SECONDS` | `IdleTimeout` | 120 |

- The signal context, the in-process workers and the 10-second `Shutdown` are unchanged. The workers still stop on the same context as the server.

See [ADR 0043](../adr/0043-gateway-graceful-shutdown-and-billing-server-timeouts.md). **Implemented (KEL-99):** billing prices every new transaction from identity's applied platform fee policy and no longer trusts the internal request's `platform_fee`, which academic still sends and billing ignores. `platform_fee = floor(gross_amount × percent_bps / 10000) + fixed_fee`, and the tenant bears it: `net_amount = gross_amount - platform_fee - payment_gateway_fee`. `GenerateSubscriptionPayment` decides the fee before any write. When fee plus gateway fee exceeds gross it answers 422 `platform_fee_exceeds_gross` (`Biaya platform melebihi jumlah pembayaran`) and writes no subscription or transaction. An unreadable, malformed or unapplied policy answers 503 `platform_fee_policy_unavailable`; there is no 0% fallback. A re-invoice of an existing transaction keeps its original snapshot and does not read the policy, so a policy change during checkout does not reprice it. The renewal worker prices each renewal with the policy applied at renewal creation and creates no renewal when the policy cannot be read; it no longer copies the first transaction's fee. The policy comes from `tenant.FeePolicyService/GetPlatformFeePolicy` at `IDENTITY_GRPC_HOST`, bounded by `IDENTITY_PERMISSION_TIMEOUT_MS`, and every field is strictly parsed as an in-bounds integer. Migration `20260928000000_transaction_platform_fee_snapshot` adds nullable `platform_fee_policy_version`, `platform_fee_percent_bps` and `platform_fee_fixed` columns. Transactions created before KEL-99 keep NULL and are not backfilled. A CHECK enforces an all-or-nothing snapshot, the bounds, and fee/net consistency, and a BEFORE UPDATE trigger makes a written snapshot and its amounts immutable. Identity must answer the RPC before this billing version serves checkout. A job that reached the attempt limit used to be recoverable only by replaying a provider callback. KEL-29 adds an operator path that does not need the provider: `GET /internal/billing/reconciliations` lists jobs by status and `POST /internal/billing/reconciliations/requeue` moves `terminal_failed` rows back to `pending`, both behind the internal credential (`internal/delivery/http/handler/reconciliation_handler.go`, `internal/usecase/reconciliation_admin_usecase.go`). The status guard is part of the update statement in `internal/repository/payment_reconciliation_repository.go`, so a replay cannot reset a pending, in-flight, or completed job, and the attempt count is preserved so the configured limit keeps bounding further attempts. The same repository logs every transition it actually persists — a `WARN` retry with the next attempt instant, an `ERROR` for the attempt limit, and an `INFO` on completion — with the transaction and enrollment ids and no credential or provider payload. Batch statements that insert release jobs during expiry and cancellation report which rows they inserted, so a skipped `ON CONFLICT` is not logged as a transition.

The transaction expiry worker is enabled by `TRANSACTION_EXPIRY_WORKER_ENABLED` (default true) at `TRANSACTION_EXPIRY_WORKER_INTERVAL_MINUTES` (default 5). It marks overdue `pending` transactions as `expired` in batches of 200 using one conditional update per batch with `FOR UPDATE SKIP LOCKED`, so multiple billing replicas never expire the same row twice and a transaction paid in the meantime is skipped. The same `SUBSCRIPTION_PAYMENT_EXPIRY_PERIOD_DAYS` value drives both the Duitku `expiryPeriod` and the stored `invoice_expires_at`. Expiry is one-directional: a late `resultCode=00` callback for an already-expired transaction still marks it `paid`, retains `expired_at`, and runs reconciliation. The same statement that expires a transaction also enqueues a durable `release` reconciliation for its enrollment, so the seat is given back by the reconciliation worker rather than by any second code path. Callback result codes outside `00`/`01`/`02` are logged with a structured `WARN` and leave the transaction untouched. Evidence: `internal/usecase/transaction_expiry_worker.go`, `internal/repository/transaction_repository.go`, `internal/repository/payment_reconciliation_repository.go`, `internal/usecase/transaction_usecase.go`. No separate worker deployment is required.

Invoice creation is guarded by a reclaimable claim recorded in the transaction row, so an enrollment is never stranded in `creating` when a provider call fails or the process dies mid-request (KEL-24). `invoice_claimed_at` records when the attempt took ownership and `invoice_failure_reason` records why the last attempt failed; the claim is released on the provider error path and becomes reclaimable after `TRANSACTION_CLAIM_TIMEOUT_MINUTES` (default 10) otherwise. Exclusivity comes from a single conditional `UPDATE` and its affected-row count, so no lock is added.
