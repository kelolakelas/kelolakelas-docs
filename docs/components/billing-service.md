# Billing service (`kelolakelas-billing-service`)

**Implemented:** Gin HTTP server default `:8082`, GORM/PostgreSQL data store, Duitku client, Resend client, internal academic client, and optional subscription worker. Evidence: `cmd/server/main.go:31-114`.

Publicly reachable from the gateway are the callback `POST /api/v1/billing/webhooks/duitku` and JWT-protected transaction list/get routes. Invoice creation is only available at the internal credential-protected transaction endpoint for the academic enrollment flow. Callback signature checks happen in the handler before the use case; the use case validates state/amount, commits the paid side effects, enqueues a durable reconciliation, and attempts enrollment activation through academic (`internal/usecase/transaction_usecase.go`, `internal/usecase/reconciliation_worker.go`).

The subscription worker is enabled by `SUBSCRIPTION_WORKER_ENABLED`; it creates/sends payment reminders and creates renewal invoices at the configured interval (`internal/usecase/subscription_worker.go`). The payment reconciliation worker is enabled by `PAYMENT_RECONCILIATION_WORKER_ENABLED` (default true), claims due rows with a five-minute lease, retries Academic activation with exponential backoff, and records terminal failure after `PAYMENT_RECONCILIATION_MAX_ATTEMPTS` (`internal/usecase/reconciliation_worker.go`, `internal/repository/payment_reconciliation_repository.go`).

The transaction expiry worker is enabled by `TRANSACTION_EXPIRY_WORKER_ENABLED` (default true) at `TRANSACTION_EXPIRY_WORKER_INTERVAL_MINUTES` (default 5). It marks overdue `pending` transactions as `expired` in batches of 200 using one conditional update per batch with `FOR UPDATE SKIP LOCKED`, so multiple billing replicas never expire the same row twice and a transaction paid in the meantime is skipped. The same `SUBSCRIPTION_PAYMENT_EXPIRY_PERIOD_DAYS` value drives both the Duitku `expiryPeriod` and the stored `invoice_expires_at`. Expiry is one-directional: a late `resultCode=00` callback for an already-expired transaction still marks it `paid`, retains `expired_at`, and runs reconciliation. Callback result codes outside `00`/`01`/`02` are logged with a structured `WARN` and leave the transaction untouched. Evidence: `internal/usecase/transaction_expiry_worker.go`, `internal/repository/transaction_repository.go:125-166`, `internal/usecase/transaction_usecase.go:480-602`. No separate worker deployment is required.
