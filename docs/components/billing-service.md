# Billing service (`kelolakelas-billing-service`)

**Implemented:** Gin HTTP server default `:8082`, GORM/PostgreSQL data store, Duitku client, Resend client, internal academic client, and optional subscription worker. It exposes an internal cancellation path that withdraws the unpaid invoice of a cancelled enrollment (KEL-27). Evidence: `cmd/server/main.go:31-115`.

**Implemented (KEL-63):** the build toolchain is pinned by `go 1.26.6` (`go.mod`; CI follows via `go-version-file`), fixing the reachable go1.26.5 standard-library advisories, including GO-2026-6088 (`encoding/xml`) that only this repository carried, alongside GO-2026-6089/GO-2026-5026 (`net/http`), GO-2026-6090 (`crypto/tls`), GO-2026-5972 (`encoding/asn1`), GO-2026-6218 (`net/url`), and GO-2026-6091 (`html/template`). `github.com/jackc/pgx/v5` moves v5.6.0 → v5.9.2 as an indirect dependency of the GORM Postgres driver (GO-2026-5004), with tidy-driven transitives (`golang.org/x/{crypto,mod,net,text,tools}`, `google.golang.org/genproto/googleapis/rpc`); billing has no direct `grpc` requirement. `govulncheck ./...` reports no vulnerabilities; no runtime code or behaviour changed, and the full `-race` suite (including `pkg/identity` and `pkg/duitku`) passes. Evidence: `kelolakelas-billing-service/go.mod`, `go.sum`; PR #12, squash `48d54619ef789c8e5128918d0259adda32a3a0b6`.

Publicly reachable from the gateway are the callback `POST /api/v1/billing/webhooks/duitku` and JWT-protected transaction list/get routes. Since KEL-57 the tenant path of those two reads also requires `billing:read`, checked through identity's `CheckPermission` gRPC at `IDENTITY_GRPC_HOST` with a per-call bound of `IDENTITY_PERMISSION_TIMEOUT_MS`; parents skip the check, a denied or role-less tenant token is 403, and an identity failure is 503. The route table lives in `cmd/server/routes.go` so which middleware guards which route is tested (`cmd/server/routes_test.go`); see [ADR 0024](../adr/0024-billing-read-permission-on-tenant-transaction-reads.md). Invoice creation is only available at the internal credential-protected transaction endpoint for the academic enrollment flow. Callback signature checks happen in the handler before the use case; the use case validates state/amount, commits the paid side effects, enqueues a durable reconciliation, and attempts enrollment activation through academic (`internal/usecase/transaction_usecase.go`, `internal/usecase/reconciliation_worker.go`).

The subscription worker is enabled by `SUBSCRIPTION_WORKER_ENABLED`; it creates/sends payment reminders and creates renewal invoices at the configured interval (`internal/usecase/subscription_worker.go`).

**Implemented (KEL-55):** Billing bounds each Duitku and Resend HTTP request using `DUITKU_HTTP_TIMEOUT_SECONDS` and `RESEND_HTTP_TIMEOUT_SECONDS` (default 10 seconds each, including unset or nonpositive values). On a failed payment-link email, the worker conditionally clears only its own `payment_link_sent_at` stamp while the transaction is still `pending`; it does not save the stale transaction row, so a concurrent paid callback remains paid. Renewal listing failures emit a structured error without a subscription ID (none was listed); per-subscription processing errors log `subscription_id`, and a failed claim-release write logs `transaction_id`. The other full-row write paths and worker scheduling are unchanged. Evidence: billing `internal/config/config.go` (`LoadConfig`), `cmd/server/main.go`, `pkg/duitku/client.go`, `pkg/email/resend.go`, `internal/usecase/subscription_worker.go` (`RunOnce`, `sendEmails`), `internal/repository/transaction_repository.go` (`ReleasePaymentLinkEmailClaim`); tests in `pkg/{duitku,email}`, `internal/usecase/subscription_worker_safety_test.go`, and `internal/repository/transaction_email_claim_test.go`; billing PR #11 (`582b80eba5b55a01a8c04479ca0e2e1f82444ccd`).

The payment reconciliation worker is enabled by `PAYMENT_RECONCILIATION_WORKER_ENABLED` (default true), claims due rows with a five-minute lease, retries the Academic call with exponential backoff, and records terminal failure after `PAYMENT_RECONCILIATION_MAX_ATTEMPTS` (`internal/usecase/reconciliation_worker.go`, `internal/repository/payment_reconciliation_repository.go`). The row it claims carries a `kind` that selects the endpoint: `activation` confirms a paid seat, `release` returns the seat of a payment that failed or expired (KEL-26, [ADR 0012](../adr/0012-release-enrollment-seat-on-failed-payment.md)).

**Implemented (KEL-61):** the two handler branches that used to return the raw use case error in a 500 body — the default branch of the internal enrollment-payment cancellation and `GenerateSubscriptionPayment` — now log the original error server-side through `slog.ErrorContext` carrying only the operation context and the error, and answer with the fixed generic messages `Failed to cancel transaction` and `Failed to generate subscription payment` inside the unchanged `{status, message, data}` envelope. Mapped 404/409 branches and the 400 binding-validation feedback are unchanged, and after this change no billing HTTP handler answers 500 with raw error text. Regression tests drive each branch with an internal-looking database error and assert the marker is absent from the response body while present in the captured server log. Evidence: `kelolakelas-billing-service/internal/delivery/http/handler/transaction_handler.go`, `internal/delivery/http/handler/sanitize_500_test.go`; PR #13, squash `0f1ebcc24b4b654d931548074b4f19d8115fb1a2`.

**Implemented (KEL-75):** the internal invoice request's `sender_email` is the billing contact when academic forwards it. `GenerateSubscriptionPaymentRequest.SenderEmail` carries `binding:"omitempty,email"`, so a non-empty value that is not a real address is rejected with 400 by handler binding before any transaction or subscription row is written, while an empty value stays accepted so rollout tokens without the email claim keep working. A valid value flows through the unchanged use case into `Subscription.BillingEmail`, `Transaction.BillingEmail`, and the Duitku invoice `Email`; the subscription renewal worker already reads `Transaction.BillingEmail`, so payment-link and reminder emails now reach the parent for checkouts that carry the claim. Billing stores the value as received and never normalises it itself: academic's auth middleware is the single normalisation point (TrimSpace once, case preserved — the contract's delegated "Email dengan huruf besar atau spasi di tepi" decision). Pre-existing subscriptions and transactions are not backfilled. Evidence: `internal/domain/transaction.go`, `internal/delivery/http/handler/transaction_handler.go`, `internal/delivery/http/handler/transaction_generate_sender_email_test.go`, `internal/usecase/subscription_billing_email_test.go`; billing PR #14, squash `5286a66f4ada37107de9061a2edc9b1d90eb9fcc`.

A job that reached the attempt limit used to be recoverable only by replaying a provider callback. KEL-29 adds an operator path that does not need the provider: `GET /internal/billing/reconciliations` lists jobs by status and `POST /internal/billing/reconciliations/requeue` moves `terminal_failed` rows back to `pending`, both behind the internal credential (`internal/delivery/http/handler/reconciliation_handler.go`, `internal/usecase/reconciliation_admin_usecase.go`). The status guard is part of the update statement in `internal/repository/payment_reconciliation_repository.go`, so a replay cannot reset a pending, in-flight, or completed job, and the attempt count is preserved so the configured limit keeps bounding further attempts. The same repository logs every transition it actually persists — a `WARN` retry with the next attempt instant, an `ERROR` for the attempt limit, and an `INFO` on completion — with the transaction and enrollment ids and no credential or provider payload. Batch statements that insert release jobs during expiry and cancellation report which rows they inserted, so a skipped `ON CONFLICT` is not logged as a transition.

The transaction expiry worker is enabled by `TRANSACTION_EXPIRY_WORKER_ENABLED` (default true) at `TRANSACTION_EXPIRY_WORKER_INTERVAL_MINUTES` (default 5). It marks overdue `pending` transactions as `expired` in batches of 200 using one conditional update per batch with `FOR UPDATE SKIP LOCKED`, so multiple billing replicas never expire the same row twice and a transaction paid in the meantime is skipped. The same `SUBSCRIPTION_PAYMENT_EXPIRY_PERIOD_DAYS` value drives both the Duitku `expiryPeriod` and the stored `invoice_expires_at`. Expiry is one-directional: a late `resultCode=00` callback for an already-expired transaction still marks it `paid`, retains `expired_at`, and runs reconciliation. The same statement that expires a transaction also enqueues a durable `release` reconciliation for its enrollment, so the seat is given back by the reconciliation worker rather than by any second code path. Callback result codes outside `00`/`01`/`02` are logged with a structured `WARN` and leave the transaction untouched. Evidence: `internal/usecase/transaction_expiry_worker.go`, `internal/repository/transaction_repository.go`, `internal/repository/payment_reconciliation_repository.go`, `internal/usecase/transaction_usecase.go`. No separate worker deployment is required.

Invoice creation is guarded by a reclaimable claim recorded in the transaction row, so an enrollment is never stranded in `creating` when a provider call fails or the process dies mid-request (KEL-24). `invoice_claimed_at` records when the attempt took ownership and `invoice_failure_reason` records why the last attempt failed; the claim is released on the provider error path and becomes reclaimable after `TRANSACTION_CLAIM_TIMEOUT_MINUTES` (default 10) otherwise. Exclusivity comes from a single conditional `UPDATE` and its affected-row count, so no lock is added. Evidence: `internal/repository/transaction_repository.go:124-175,305`, `internal/usecase/transaction_usecase.go:326,338`, `internal/usecase/subscription_worker.go:147,157`, `internal/config/config.go:47`, `migrations/20260922000000_invoice_claim_recovery.up.sql`.
