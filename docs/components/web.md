# Web (`kelolakelas-web`)

**Implemented:** a Next.js App Router application with public `/`, `/kelas`, `/kelas/:id`, auth `/login` and `/register`, tenant dashboard pages for overview, members, roles, settings, classes, and enrollments, and parent student management at `/dashboard/parent/students`. Public catalog pages call the gateway’s public catalog list/detail endpoints server-side, support core text/type/price/sort filters and pagination, and display explicit loading, invalid-filter, empty, API-error, and not-found states. The public class detail page now offers a parent-only enrollment panel: it loads the authenticated parent’s owned students, presents available/full schedules and billing-cycle choices, submits the catalog enrollment endpoint with a stable per-form `Idempotency-Key`, and redirects only to a validated backend-provided checkout URL. Parent student management calls the authenticated student list/create/update/delete routes through Server Components and Server Actions, validates the API fields in the web form, exposes loading/empty/validation/forbidden/conflict/API-error states, and restricts the route to `is_parent` sessions in `proxy.ts`. Schedule payloads are rendered only when day/time fields are complete. Parent registration does not auto-login: it returns the user to `/login?registered=1`; login uses the identity response (`is_parent` and tenant context) to select `/kelas` or `/dashboard/tenant`, while preserving only role-compatible internal redirects. Evidence: `app/(public)/kelas/[id]/page.tsx`, `app/(public)/kelas/[id]/_actions/actions.ts`, `app/(public)/kelas/[id]/_components/EnrollmentPanel.tsx`, `app/(dashboard)/dashboard/parent/students/**`, `lib/auth-routing.ts`, `lib/auth-session.ts`, `lib/catalog.ts`, `lib/enrollment.ts`, `proxy.ts`.

**Implemented (KEL-48):** route error boundaries and a branded 404. Every boundary renders `app/_components/RouteErrorState.tsx`. It shows an Indonesian title and description, a **Coba lagi** button wired to Next.js 16 `unstable_retry` (which re-fetches and re-renders the segment), and an optional recovery link. It never renders `error.message`. It shows only `error.digest` as a reference code, and only when the digest is an opaque token of at most 64 `[A-Za-z0-9_-]` characters. The digest matches the line Next.js writes to the server log for the same error, so a user-reported code can be correlated there.

Boundaries:
- `app/(public)/kelas/error.tsx` covers `/kelas` and `/kelas/[id]`.
- `app/(dashboard)/dashboard/parent/enrollments/error.tsx` links to `/login?redirectTo=…` as the expired-session recovery.
- `app/(dashboard)/dashboard/tenant/error.tsx` shares its segment with the tenant `layout.tsx`, so it renders inside that layout and the sidebar and mobile navigation remain usable. Errors thrown by the tenant layout itself are not covered by it and fall through to `app/error.tsx`.

- `app/global-error.tsx` replaces the root layout when the root layout throws. It renders its own `<html lang="id">`, imports `globals.css`, and titles itself with a React `<title>`.
- `app/not-found.tsx` is the branded 404 for unmatched URLs and for any `notFound()` call. Next.js adds `noindex` to it.

Explicitly handled states are unchanged: catalog `invalid_filter`/`api`/`not_found`, the enrollments API error card, and parent students `error.tsx`. `/kelas/[id]` still renders its own not-found state without calling `notFound()`, and no Server Action calls `notFound()`. An expired or malformed session never reaches a boundary on protected routes, because `proxy.ts` redirects it to `/login` first. External error reporting is not implemented.

The tenant settings page at `/dashboard/tenant/settings` is no longer a placeholder. It renders two independent forms over the identity endpoints: profile (`GET`/`PATCH /api/v1/tenant/settings`: name, phone, address, about) and location (`GET`/`PUT /api/v1/tenant/settings/location`: address, optional latitude/longitude pair), both reached through the gateway with the session cookie (`app/(dashboard)/dashboard/tenant/settings/_queries/queries.ts`, `_actions/settingsActions.ts`). Field-level validation mirrors the identity DTOs rather than replacing them: the name and address are required with the same maximum lengths, a blank optional field is omitted from the request so a stored value is not replaced by an empty string, and a lone coordinate is refused locally because `UpdateTenantLocationRequest.Validate` rejects the pair. `about` is a JSON column on the backend, so it is read and written as text through `aboutToText`/`textToAbout` and an unrecognised stored shape renders as an empty field instead of failing the page. Both update routes require `tenant:update`, so a refusal is rendered as a permission state, and the geocoded address the backend resolved is displayed after a save so a tenant sees the effect of submitting an address without coordinates. The identity endpoints are catalogued in the [identity service](identity-service.md) documentation and the permission is described in [security](../05-security.md).

The members screen reports the real invitation email outcome instead of always claiming a delivery (KEL-36). `inviteTenantMember` reads `data.email_sent` from the identity create-invitation response and mirrors it as `ActionResponse.emailSent`; the success message comes from the backend (`Invitation created and email sent successfully` versus `Invitation created but the email could not be sent. …`), with `inviteDeliveryMessage` in `lib/invitation.ts` as the fallback when an older backend omits the message. The backend message wins over the local fallback because identity is the authority on what happened to the email. `InviteMemberForm` now passes the settled action state to `onSuccess`, and `InviteMemberModal` closes only when `emailSent !== false`: a stored invitation with a failed email keeps the form open so the tenant reads the warning and can resend later, while the members list still refreshes through `revalidatePath`. Evidence: `app/(dashboard)/dashboard/tenant/members/_actions/actions.ts`, `_actions/inviteActions.test.ts`, `_components/InviteMemberForm.tsx`, `_components/InviteMemberModal.tsx`, `lib/invitation.ts`, `lib/invitation.test.ts`.

Server actions and tenant dashboard queries validate input as applicable, then call `${GATEWAY_API_URL}/api/v1/...`. `GATEWAY_API_URL` is a required server-side HTTP(S) gateway origin: blank, malformed, non-HTTP(S), and path-bearing values fail diagnostically, and a trailing slash is normalized. Successful login and registrations set an HTTP-only cookie (`app/(auth)/login/_actions/actions.ts`, `app/(auth)/register/_actions/actions.ts`). Tenant dashboard actions/queries read the cookie and send it as a Bearer token. Tenant dashboard actions and queries additionally send an `X-Tenant-ID` from the `tenant_id` cookie set at login/registration out of the login response's `user.tenant_id`; the header agrees with the token's tenant claim for legitimate traffic, and the gateway discards the inbound copy and publishes the claim value instead, so sending it is compatible but carries no authority ([ADR 0017](../adr/0017-gateway-context-header-trust-boundary.md)). Academic ignores the header for tenant resolution ([ADR 0010](../adr/0010-tenant-context-from-verified-jwt-claim-only.md)).

`proxy.ts` protects `/dashboard` and `/profile` using an optimistic JWT payload/expiry check, clears malformed or expired cookies, and routes valid parent/tenant sessions away from auth pages to their compatible entry point. It does not verify the JWT signature; the backend remains the security authority. It excludes `/api/` and static assets. Browser-side UI coverage is narrower than backend route coverage: no implemented frontend attendance, report, or tutor-management screen was found.

The gateway origin is deliberately server-only rather than a `NEXT_PUBLIC_*` variable because the relevant requests run in Server Actions and Server Components. Enrollment actions authenticate from the HTTP-only cookie, validate all form references, and never accept a price or parent ID from the browser. A duplicate submit/retry keeps the same hidden idempotency key for the mounted form; a new page render creates a new intent. Parent users can open `/dashboard/parent/enrollments`, which fetches parent-scoped enrollment and transaction lists with the session bearer token and presents backend payment states, including pending, paid/active, failed/expired, and durable reconciliation states. The page does not infer payment success from a provider redirect. The web package includes Vitest coverage for gateway configuration, catalog schedule parsing, session identity, enrollment payload validation, and payment-status presentation.

**Implemented:** the tenant invitation link is now accepted in the browser at `/invitations/verify?token=…`. The route is a Server Component that verifies the token against the gateway's public `GET /api/v1/invitations/verify` before rendering anything, with `cache: 'no-store'` and an `Accept: application/json` header, so a stale or reused link never reaches a form. The verification result is reduced by `verifyInvitation` in `lib/invitation.ts` to one of six mutually exclusive states — valid, or `missing_token`, `not_found`, `expired`, `used`, `unavailable`, `invalid` — and each failure renders `InvitationNotice` with its own title and message. Distinct states matter because identity answers an expired or already-used token with `400` and the two are indistinguishable by status code alone, so `classifyInvitationFailure` reads the backend message; a `5xx`, an unparseable body, or an unreachable/`GATEWAY_API_URL` misconfiguration is reported as `unavailable` rather than as an invalid invitation, so a gateway outage never tells an invited user that their link is bad. The token is dropped during normalisation (`normalizeInvitationDetails`) and therefore cannot be rendered, logged as page content, or reflected into markup; it travels only as a hidden form field. `proxy.ts` neither protects nor redirects `/invitations/verify`, so an invitation can be opened while signed out and a signed-in visitor is not bounced away; the page shows an informational notice in that case instead. On success the page displays the facts the invitation itself owns — the invited email address and the formatted expiry (`formatInvitationExpiry`, rendered in `Asia/Jakarta` as `… WIB`) — plus a best-effort tenant name resolved through the public catalog endpoint, and the `InvitationRegisterForm` collects first name, last name, and password. Email is read-only and is never sent from the browser: identity takes the address, tenant, and role from the persisted invitation row inside `RegisterInvitedUserTx`, so a tampered payload cannot redirect an invitation to a different address or tenant. Submission calls the `registerInvitedUser` Server Action, which validates the payload with `invitedUserRegistrationSchema` and posts to the public `POST /api/v1/invitations/register`; success redirects to `/login?registered=1` and deliberately does not create a session. Failure messages are mapped per case by `invitationRegisterErrorMessage`: expired, already used, `404` gone, `409` address already registered (the invited person is told to sign in with their existing password instead), `400` rejected — used instead of the raw Go binding error, which is not readable — `5xx`/unreachable, or the backend message otherwise. **Known limitation:** identity's verify response carries `tenant_id` and `role_id` only and no public endpoint resolves those to display names, so the invited role is not shown and the tenant name is present only when the public catalog already exposes a published, open class for that tenant (`getCatalog` reads `tenant_location_snapshots` through a left join, so the name is absent for a tenant with no published open class); the resolved tenant name therefore degrades to a generic heading. Wiring the role and tenant names into the invitation contract is follow-up work that belongs to identity, not to the web app. Evidence: `app/(auth)/invitations/verify/page.tsx`, `app/(auth)/invitations/verify/_actions/actions.ts`, `app/(auth)/invitations/verify/_components/InvitationRegisterForm.tsx`, `lib/invitation.ts`, `lib/invitation.test.ts`, `proxy.test.ts`, gateway `internal/delivery/http/router.go:60-61`, identity `internal/delivery/http/handler/invitation_handler.go`, identity `internal/repository/user_repository.go` (`RegisterInvitedUserTx`).

## Tenant enrollment and payment overview

**Implemented:** a tenant can see the enrollments of its own classes together with the payment status of each one at `/dashboard/tenant/enrollments`, reached from a new Enrollments tab in the tenant sidebar and the mobile drawer. The route is a Server Component whose content is wrapped in `Suspense` with `EnrollmentsSkeleton` as the fallback, and it reads two academic lists and one billing lookup per row. Before KEL-33 the only enrollment screen in the app was the parent-scoped `/dashboard/parent/enrollments`, so a tenant could create and publish classes but had no view that answered who had enrolled and whether they had paid.

The page reads the academic enrollment list and the academic schedule list, then joins each row with the newest billing transaction for that enrollment:

| Source | Request | Notes |
| --- | --- | --- |
| Enrollments | `GET /api/v1/enrollments?page=…&page_size=20[&status=…]` | permission-guarded by `enrollment:read` ([ADR 0002](../adr/0002-academic-permission-enforcement.md)) |
| Schedules | `GET /api/v1/schedules?page_size=100` | looked up by `schedule_id` from the enrollment response |
| Transactions | `GET /api/v1/billing/transactions?enrollment_id=…&page_size=1&page=1` | one request per enrollment, newest first |

The filter vocabulary is the enrollment record's own status — `pending`, `active`, `completed`, `dropped` — and it is deliberately **not** the class-level enrollment status. A class carries `open`/`closed`/`full`/`archived` on a different field, so the enum is named `enrollmentRecordStatusSchema` in `_lib/schema.ts` and `parseEnrollmentFilters` rejects anything outside the four values. An unrecognised `status` renders a validation notice and issues **no** gateway request, so a stale or hand-edited link cannot forward an arbitrary value to the backend.

Two non-obvious decisions shape the implementation, both recorded with their alternatives in [ADR 0023](../adr/0023-tenant-enrollment-payment-join-per-row.md):

- **The transaction join is one request per enrollment, newest first.** `page_size=1` with the billing service's `created_at DESC` ordering means the newest transaction wins. This is required rather than incidental: migration `000002_payment_idempotency` created a unique index on `transactions.enrollment_id` and `000003_subscription_renewals` drops it (`kelolakelas-billing-service/migrations/000003_subscription_renewals.up.sql:13`), so a renewal can leave several transactions on one enrollment and a naive join would surface a stale one.
- **Unreadable detail degrades instead of failing the page.** A failed transaction lookup for one enrollment, a failed schedule list read, and a malformed billing payload each leave the enrollment rows on screen with the missing value rendered as "not available" (`Nominal belum tersedia`, `Belum ada jadwal`). Only an unreadable *enrollment* list is an error, because then there is nothing to show. The schedule list is not permission-guarded (`cmd/server/main.go:118`) and the billing transaction list is not either, so neither can produce the forbidden state on its own.

A payment lookup refused with `403` is the one exception to that degradation (KEL-57). Billing now requires `billing:read` for tenant transaction reads, so a member without it — the built-in Teacher role, for instance — would otherwise have been told every enrollment is waiting for a transaction. `loadTransactions` records such a row as `paymentForbidden`, and `EnrollmentTable` renders "Tidak tersedia untuk role Anda" with "Nominal tidak tersedia" in both layouts; `500`, `503`, and network failures still render "Menunggu transaksi". The shared `lib/payment-status.ts` presentation used by the parent page is unchanged. See [ADR 0024](../adr/0024-billing-read-permission-on-tenant-transaction-reads.md).

The forbidden state is driven by the academic service's permission middleware. A `401` or `403` from the enrollment list renders "Akses ditolak" with the actionable message naming `enrollment:read`, and the filter control is disabled; no status code, gateway URL, or stack trace reaches the UI. This is the same `RequirePermissionUnlessParent` behaviour introduced with the academic enforcement in KEL-21 ([ADR 0002](../adr/0002-academic-permission-enforcement.md)), now surfaced to a tenant member who lacks the permission instead of only to an API client. Remaining failures are mapped to a generic "Data enrollment belum dapat dimuat" for an API error and to the gateway-configuration diagnostic when `GATEWAY_API_URL` is absent or malformed.

**Implemented:** the display layer is format-only and tolerant of the backend's actual shape. `studentDisplayName` reads `first_name`, then `last_name`, then `lastå_name` — the last of which is the key the academic service really serializes `Student.LastName` under, so the helper follows the wire contract rather than the Go field name and never throws on an unexpected payload. `scheduleLabel` returns `null` unless the day and both times are present, rendering `Rabu, 15:30–17:00` (times truncated to minutes) and appending the location when there is one; the payment presentation reuses `lib/payment-status.ts`, so the billing API's `reconciling` collapse of the database's `pending`/`processing` states is what the tenant sees. The table has both a mobile card layout and a desktop table, and its empty state distinguishes "no enrollments at all" from "no enrollments matching this filter". Evidence: `app/(dashboard)/dashboard/tenant/enrollments/page.tsx`, `_queries/queries.ts`, `_components/EnrollmentTable.tsx`, `_components/EnrollmentStatusFilter.tsx`, `_components/EnrollmentsSkeleton.tsx`, `_lib/schema.ts`, `_constants/constants.ts`, `_components/TenantSidebar.tsx`, `_components/MobileNav.tsx`, [ADR 0023](../adr/0023-tenant-enrollment-payment-join-per-row.md).

## Parent cancellation of a pending enrollment

**Implemented:** a parent can withdraw a pending enrollment from `/dashboard/parent/enrollments`. The backend route shipped with KEL-27 ([ADR 0016](../adr/0016-cancel-pending-enrollment.md)) but the web app deliberately offered no control for it, so a parent who changed their mind still had to wait for `invoice_expires_at` before the seat came back.

The control is a client component backed by the `cancelPendingEnrollment` Server Action (`_actions/actions.ts`). The action reads the session cookie, forwards the enrollment id to `POST /api/v1/enrollments/{id}/cancel` with the bearer token, sends no request body, and calls `revalidatePath('/dashboard/parent/enrollments')` on success so the row is re-rendered from the backend rather than from an optimistic local guess. The browser supplies only the enrollment id from a hidden field; the parent identity and every status decision stay server-side, and the academic service scopes the lookup to the caller, so another parent's enrollment answers 404 rather than confirming it exists.

Two decisions shape the screen:

- **The action is offered only where the backend would accept it.** `canCancelEnrollment` (`lib/enrollment-cancellation.ts`) requires the enrollment to be `pending` *and* its newest transaction to be neither `paid` nor `refunded`. Both halves are needed: an enrollment stays `pending` until activation is applied, so a parent whose payment was already accepted would otherwise be shown a control whose only outcome is the 409 that billing returns when the invoice can no longer be withdrawn.
- **Confirmation uses a native `<dialog>` opened with `showModal()`, not `window.confirm`.** `window.confirm` blocks the event loop, cannot be styled, and cannot be labelled for assistive technology; the platform modal supplies focus trapping, Escape-to-cancel, an inert background and a label via `aria-labelledby` without a dependency. The submit button is disabled while its form is pending, so a double click cannot issue two cancellations.

A refusal keeps the dialog open with its explanation, because the usual reaction is to read it and decide again; a success closes the dialog. The message mapping is what carries the outcome: `409` is reported in full as a state no retry can fix, `404` as an enrollment that is not on this account, `401`/`403` separate an expired session from a caller that is not a parent, and `503` names the authorization service. A `5xx` is replaced rather than passed through, because the academic handler answers `500` with the raw Go error string, which can name internal repositories and database errors — no status code, gateway URL or stack trace reaches the UI.

**Not implemented:** no optimistic status is written locally, so the row keeps showing the backend status until the revalidation lands; and the provider invoice cannot be revoked ([ADR 0016](../adr/0016-cancel-pending-enrollment.md)), so a parent who already has the checkout link open can still pay it, in which case the money is recorded and the activation rejection is surfaced by the existing reconciliation states rather than by this screen.
