# Web (`kelolakelas-web`)

**Implemented:** a Next.js App Router application with public `/`, `/kelas`, `/kelas/:id`, auth `/login` and `/register`, tenant dashboard pages for overview, members, roles, settings, and classes, and parent student management at `/dashboard/parent/students`. Public catalog pages call the gateway’s public catalog list/detail endpoints server-side, support core text/type/price/sort filters and pagination, and display explicit loading, invalid-filter, empty, API-error, and not-found states. The public class detail page now offers a parent-only enrollment panel: it loads the authenticated parent’s owned students, presents available/full schedules and billing-cycle choices, submits the catalog enrollment endpoint with a stable per-form `Idempotency-Key`, and redirects only to a validated backend-provided checkout URL. Parent student management calls the authenticated student list/create/update/delete routes through Server Components and Server Actions, validates the API fields in the web form, exposes loading/empty/validation/forbidden/conflict/API-error states, and restricts the route to `is_parent` sessions in `proxy.ts`. Schedule payloads are rendered only when day/time fields are complete. Parent registration does not auto-login: it returns the user to `/login?registered=1`; login uses the identity response (`is_parent` and tenant context) to select `/kelas` or `/dashboard/tenant`, while preserving only role-compatible internal redirects. Its root layout remains create-next-app metadata while multiple screens and package name still say `Tutorin`. Evidence: `app/(public)/kelas/[id]/page.tsx`, `app/(public)/kelas/[id]/_actions/actions.ts`, `app/(public)/kelas/[id]/_components/EnrollmentPanel.tsx`, `app/(dashboard)/dashboard/parent/students/**`, `lib/auth-routing.ts`, `lib/auth-session.ts`, `lib/catalog.ts`, `lib/enrollment.ts`, `proxy.ts`, `app/layout.tsx:16-17`, `package.json:2`.

Server actions and tenant dashboard queries validate input as applicable, then call `${GATEWAY_API_URL}/api/v1/...`. `GATEWAY_API_URL` is a required server-side HTTP(S) gateway origin: blank, malformed, non-HTTP(S), and path-bearing values fail diagnostically, and a trailing slash is normalized. Successful login and registrations set an HTTP-only cookie (`app/(auth)/login/_actions/actions.ts`, `app/(auth)/register/_actions/actions.ts`). Tenant dashboard actions/queries read the cookie and send it as a Bearer token. Tenant dashboard actions and queries additionally send an `X-Tenant-ID` from the `tenant_id` cookie set at login/registration out of the login response's `user.tenant_id`; the header agrees with the token's tenant claim for legitimate traffic, and the gateway discards the inbound copy and publishes the claim value instead, so sending it is compatible but carries no authority ([ADR 0017](../adr/0017-gateway-context-header-trust-boundary.md)). Academic ignores the header for tenant resolution ([ADR 0010](../adr/0010-tenant-context-from-verified-jwt-claim-only.md)).

`proxy.ts` protects `/dashboard` and `/profile` using an optimistic JWT payload/expiry check, clears malformed or expired cookies, and routes valid parent/tenant sessions away from auth pages to their compatible entry point. It does not verify the JWT signature; the backend remains the security authority. It excludes `/api/` and static assets. Browser-side UI coverage is narrower than backend route coverage: no implemented frontend attendance, report, or tutor-management screen was found.

The gateway origin is deliberately server-only rather than a `NEXT_PUBLIC_*` variable because the relevant requests run in Server Actions and Server Components. Enrollment actions authenticate from the HTTP-only cookie, validate all form references, and never accept a price or parent ID from the browser. A duplicate submit/retry keeps the same hidden idempotency key for the mounted form; a new page render creates a new intent. Parent users can open `/dashboard/parent/enrollments`, which fetches parent-scoped enrollment and transaction lists with the session bearer token and presents backend payment states, including pending, paid/active, failed/expired, and durable reconciliation states. The page does not infer payment success from a provider redirect. The web package includes Vitest coverage for gateway configuration, catalog schedule parsing, session identity, enrollment payload validation, and payment-status presentation.

**Implemented:** the tenant class list at `/dashboard/tenant/classes` now exposes class publication. Each row shows a publication badge (Published/Draft), an enrollment-status badge (`open`, `closed`, `full`, `archived`, or an unrecognised-status fallback) and a Publish/Unpublish control, in both the mobile card layout and the desktop table; the Classes tab counts how many classes are published. The control submits through the `updateClassPublication` Server Action, which reads the session cookies server-side, sends only the class id from the browser, calls `PATCH /api/v1/classes/:id/published` with `{"is_published": boolean}` behind the academic service's `class:update` permission, and calls `revalidatePath('/dashboard/tenant/classes')` on success. Responses are mapped to actionable messages: `401` session expired, `403` missing permission, `404` class gone, `503` authorization service unavailable, otherwise the backend message verbatim. The submit button is disabled while its form is pending, so a double click cannot submit twice. The tenant is never taken from the browser: the gateway discards the inbound `X-Tenant-ID` and republishes the value from the verified JWT claim ([ADR 0017](../adr/0017-gateway-context-header-trust-boundary.md)), and academic resolves the tenant from that claim only ([ADR 0010](../adr/0010-tenant-context-from-verified-jwt-claim-only.md)). Evidence: `app/(dashboard)/dashboard/tenant/classes/_actions/classActions.ts` (`updateClassPublication`), `_components/ClassPublicationControl.tsx`, `_components/ClassListTable.tsx`, `lib/class-publication.ts`, `lib/class-publication.test.ts`.

Tenant academic list readers unwrap the paginated envelope the services return. `GET /api/v1/classes`, `/categories` and `/schedules` answer with `data: { items, pagination }`, and the gateway proxies that body through unchanged, so the readers in `app/(dashboard)/dashboard/tenant/classes/_queries/queries.ts` pass the payload through `normalizeListEnvelope` from `lib/list-envelope.ts`. The helper accepts the enveloped form, a bare array, and malformed input (which yields an empty result rather than throwing), and the readers request `page_size=100` — the service maximum — so the dashboard lists every configured class on one page. Before KEL-31 these readers tested `Array.isArray(result.data)`, which is always `false` for an object envelope, so the tenant class list rendered its empty state regardless of database contents; see [ADR 0018](../adr/0018-web-list-envelope-unwrapping.md). Evidence: `lib/list-envelope.ts`, `lib/list-envelope.test.ts`, `app/(dashboard)/dashboard/tenant/classes/_queries/queries.ts`.

**Implemented:** the tenant class list now exposes class editing from an Edit control on every row, rendered both in the mobile card layout and in the desktop table's Actions cell. The control opens a modal whose form is the `ClassEditForm` component: name, category (a select over the tenant's categories), price, and description, with the same field markup and messages as the creation wizard. Class type is deliberately absent because the academic service rejects a type change, and capacity is absent because schedule capacity replaced it. `updateClassSchema` is a `z.strictObject` over exactly those four fields, so `type` and `capacity` are rejected in the browser: the academic request DTO cannot refuse them itself, because Go's JSON binding silently ignores keys that the struct does not declare. The form is only mounted while the modal is open, so each open seeds its fields from the current class record rather than syncing props into state inside an effect. Price accepts what tenants actually type — `Rp 1.500.000`, `1,500,000`, and `1 500 000` are all normalised to whole rupiah amounts, and a value that is not a whole rupiah amount is rejected. Submitting calls the `updateClass` Server Action, which reads the session cookies server-side, sends only the class id from the browser, calls `PATCH /api/v1/classes/:id` with the four editable fields, and calls `revalidatePath('/dashboard/tenant/classes')` on success. A cleared description is submitted as an empty string rather than omitted, because the endpoint keeps the stored value for an absent field and would otherwise make clearing a description a silent no-op; the stored blank value renders as no description on the public catalog page through `descriptionText`. Responses are mapped to actionable messages by `classUpdateErrorMessage`: `401` session expired, `403` missing `class:update` permission, `404` class no longer exists, `503` authorization service unavailable, otherwise the backend message verbatim. The submit button is disabled while its form is pending, and each field renders its validation message with `aria-invalid`/`aria-describedby`. Evidence: `app/(dashboard)/dashboard/tenant/classes/_actions/classActions.ts` (`updateClass`), `_components/ClassEditForm.tsx`, `_components/ClassEditModal.tsx`, `_components/ClassListTable.tsx`, `_lib/schema.ts` (`updateClassSchema`), `_lib/schema.test.ts`, `lib/class-edit.ts`, `lib/class-edit.test.ts`, `lib/catalog.ts` (`descriptionText`).

**Implemented:** the tenant invitation link is now accepted in the browser at `/invitations/verify?token=…`. The route is a Server Component that verifies the token against the gateway's public `GET /api/v1/invitations/verify` before rendering anything, with `cache: 'no-store'` and an `Accept: application/json` header, so a stale or reused link never reaches a form. The verification result is reduced by `verifyInvitation` in `lib/invitation.ts` to one of six mutually exclusive states — valid, or `missing_token`, `not_found`, `expired`, `used`, `unavailable`, `invalid` — and each failure renders `InvitationNotice` with its own title and message. Distinct states matter because identity answers an expired or already-used token with `400` and the two are indistinguishable by status code alone, so `classifyInvitationFailure` reads the backend message; a `5xx`, an unparseable body, or an unreachable/`GATEWAY_API_URL` misconfiguration is reported as `unavailable` rather than as an invalid invitation, so a gateway outage never tells an invited user that their link is bad. The token is dropped during normalisation (`normalizeInvitationDetails`) and therefore cannot be rendered, logged as page content, or reflected into markup; it travels only as a hidden form field. `proxy.ts` neither protects nor redirects `/invitations/verify`, so an invitation can be opened while signed out and a signed-in visitor is not bounced away; the page shows an informational notice in that case instead. On success the page displays the facts the invitation itself owns — the invited email address and the formatted expiry (`formatInvitationExpiry`, rendered in `Asia/Jakarta` as `… WIB`) — plus a best-effort tenant name resolved through the public catalog endpoint, and the `InvitationRegisterForm` collects first name, last name, and password. Email is read-only and is never sent from the browser: identity takes the address, tenant, and role from the persisted invitation row inside `RegisterInvitedUserTx`, so a tampered payload cannot redirect an invitation to a different address or tenant. Submission calls the `registerInvitedUser` Server Action, which validates the payload with `invitedUserRegistrationSchema` and posts to the public `POST /api/v1/invitations/register`; success redirects to `/login?registered=1` and deliberately does not create a session. Failure messages are mapped per case by `invitationRegisterErrorMessage`: expired, already used, `404` gone, `409` address already registered (the invited person is told to sign in with their existing password instead), `400` rejected — used instead of the raw Go binding error, which is not readable — `5xx`/unreachable, or the backend message otherwise. **Known limitation:** identity's verify response carries `tenant_id` and `role_id` only and no public endpoint resolves those to display names, so the invited role is not shown and the tenant name is present only when the public catalog already exposes a published, open class for that tenant (`getCatalog` reads `tenant_location_snapshots` through a left join, so the name is absent for a tenant with no published open class); the resolved tenant name therefore degrades to a generic heading. Wiring the role and tenant names into the invitation contract is follow-up work that belongs to identity, not to the web app. Evidence: `app/(auth)/invitations/verify/page.tsx`, `app/(auth)/invitations/verify/_actions/actions.ts`, `app/(auth)/invitations/verify/_components/InvitationRegisterForm.tsx`, `lib/invitation.ts`, `lib/invitation.test.ts`, `proxy.test.ts`, gateway `internal/delivery/http/router.go:60-61`, identity `internal/delivery/http/handler/invitation_handler.go`, identity `internal/repository/user_repository.go` (`RegisterInvitedUserTx`).
