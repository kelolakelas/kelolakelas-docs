# Web (`kelolakelas-web`)

**Implemented:** a Next.js App Router application with public `/`, `/kelas`, `/kelas/:id`, auth `/login` and `/register`, tenant dashboard pages for overview, members, roles, settings, and classes, and parent student management at `/dashboard/parent/students`. Public catalog pages call the gateway’s public catalog list/detail endpoints server-side, support core text/type/price/sort filters and pagination, and display explicit loading, invalid-filter, empty, API-error, and not-found states. The public class detail page now offers a parent-only enrollment panel: it loads the authenticated parent’s owned students, presents available/full schedules and billing-cycle choices, submits the catalog enrollment endpoint with a stable per-form `Idempotency-Key`, and redirects only to a validated backend-provided checkout URL. Parent student management calls the authenticated student list/create/update/delete routes through Server Components and Server Actions, validates the API fields in the web form, exposes loading/empty/validation/forbidden/conflict/API-error states, and restricts the route to `is_parent` sessions in `proxy.ts`. Schedule payloads are rendered only when day/time fields are complete. Parent registration does not auto-login: it returns the user to `/login?registered=1`; login uses the identity response (`is_parent` and tenant context) to select `/kelas` or `/dashboard/tenant`, while preserving only role-compatible internal redirects. Its root layout remains create-next-app metadata while multiple screens and package name still say `Tutorin`. Evidence: `app/(public)/kelas/[id]/page.tsx`, `app/(public)/kelas/[id]/_actions/actions.ts`, `app/(public)/kelas/[id]/_components/EnrollmentPanel.tsx`, `app/(dashboard)/dashboard/parent/students/**`, `lib/auth-routing.ts`, `lib/auth-session.ts`, `lib/catalog.ts`, `lib/enrollment.ts`, `proxy.ts`, `app/layout.tsx:16-17`, `package.json:2`.

Server actions and tenant dashboard queries validate input as applicable, then call `${GATEWAY_API_URL}/api/v1/...`. `GATEWAY_API_URL` is a required server-side HTTP(S) gateway origin: blank, malformed, non-HTTP(S), and path-bearing values fail diagnostically, and a trailing slash is normalized. Successful login and registrations set an HTTP-only cookie (`app/(auth)/login/_actions/actions.ts`, `app/(auth)/register/_actions/actions.ts`). Tenant dashboard actions/queries read the cookie and send it as a Bearer token. Tenant dashboard actions and queries additionally send an `X-Tenant-ID` from the `tenant_id` cookie set at login/registration out of the login response's `user.tenant_id`; the header agrees with the token's tenant claim for legitimate traffic, and the gateway discards the inbound copy and publishes the claim value instead, so sending it is compatible but carries no authority ([ADR 0017](../adr/0017-gateway-context-header-trust-boundary.md)). Academic ignores the header for tenant resolution ([ADR 0010](../adr/0010-tenant-context-from-verified-jwt-claim-only.md)).

`proxy.ts` protects `/dashboard` and `/profile` using an optimistic JWT payload/expiry check, clears malformed or expired cookies, and routes valid parent/tenant sessions away from auth pages to their compatible entry point. It does not verify the JWT signature; the backend remains the security authority. It excludes `/api/` and static assets. Browser-side UI coverage is narrower than backend route coverage: no implemented frontend payment, student, attendance, report, enrollment, or invitation-acceptance screen was found.

The gateway origin is deliberately server-only rather than a `NEXT_PUBLIC_*` variable because the relevant requests run in Server Actions and Server Components. Enrollment actions authenticate from the HTTP-only cookie, validate all form references, and never accept a price or parent ID from the browser. A duplicate submit/retry keeps the same hidden idempotency key for the mounted form; a new page render creates a new intent. Parent users can open `/dashboard/parent/enrollments`, which fetches parent-scoped enrollment and transaction lists with the session bearer token and presents backend payment states, including pending, paid/active, failed/expired, and durable reconciliation states. The page does not infer payment success from a provider redirect. The web package includes Vitest coverage for gateway configuration, catalog schedule parsing, session identity, enrollment payload validation, and payment-status presentation.
