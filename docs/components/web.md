# Web (`kelolakelas-web`)

**Implemented:** a Next.js App Router application with public `/`, `/kelas`, `/kelas/:id`, auth `/login`, `/register`, `/forgot-password` and `/reset-password`, tenant dashboard pages for overview, members, roles, settings, classes, enrollments, and schedule requests, and parent student management at `/dashboard/parent/students`. Public catalog pages call the gateway’s public catalog list/detail endpoints server-side, support core text/type/price/sort filters and pagination, and display explicit loading, invalid-filter, empty, API-error, and not-found states. The public class detail page now offers a parent-only enrollment panel: it loads the authenticated parent’s owned students. For group classes it presents available/full schedules and billing-cycle choices, submits the catalog enrollment endpoint with a stable per-form `Idempotency-Key`, and redirects only to a validated backend-provided checkout URL. For private classes (KEL-109) it shows a schedule request form instead of checkout (see "Private schedule request form" below). Parent student management calls the authenticated student list/create/update/delete routes through Server Components and Server Actions, validates the API fields in the web form, exposes loading/empty/validation/forbidden/conflict/API-error states, and restricts the route to `is_parent` sessions in `proxy.ts`. Schedule payloads are rendered only when day/time fields are complete. Parent registration does not auto-login: it returns the user to `/login?registered=1`; login uses the identity response (`is_parent` and tenant context) to select `/kelas` or `/dashboard/tenant`, while preserving only role-compatible internal redirects. Evidence: `app/(public)/kelas/[id]/page.tsx`, `app/(public)/kelas/[id]/_actions/actions.ts`, `app/(public)/kelas/[id]/_components/EnrollmentPanel.tsx`, `app/(dashboard)/dashboard/parent/students/**`, `lib/auth-routing.ts`, `lib/auth-session.ts`, `lib/catalog.ts`, `lib/enrollment.ts`, `proxy.ts`.

**Implemented (KEL-72):** search-engine discovery through Next.js metadata routes.

- `app/robots.ts` serves `/robots.txt`. It allows `/`, disallows `/dashboard`, `/login`, `/register`, `/forgot-password`, `/reset-password`, `/invitations` and `/platform`, and names the absolute sitemap `${getAppUrl()}/sitemap.xml`.
- `app/sitemap.ts` serves `/sitemap.xml` with `/`, `/kelas` and `/kelas/<encoded id>` for every class the public catalog (`GET /api/v1/catalog/classes`) returns, so no draft classes appear. It reads pages of `page_size=100` until `pagination.total_pages`, and skips duplicate or empty ids.
- Any catalog failure (network error, non-success envelope, 4xx/5xx) yields only the two static entries with HTTP 200, never a 500.
- **Revalidation:** the route exports `revalidate = 3600` and builds as static/ISR (`○ /sitemap.xml`, 1h). Its catalog fetches pass `next: { revalidate: 3600 }` instead of `cache: 'no-store'`, and send no client IP, because the route has no request. Crawler traffic therefore does not reach the gateway: the catalog is read at build time and then at most hourly. New classes can take up to an hour (or the next deploy) to appear. A catalog outage during the build or a background revalidation leaves the static-only sitemap in place until the next successful revalidation.
- `lib/catalog.ts` `getCatalog`/`catalogQuery` gained optional `{ pageSize (1..100), revalidateSeconds, forwardClientIp }`. The defaults keep `cache: 'no-store'` and client-IP forwarding for `/kelas` and `/kelas/[id]`. `/kelas` passes a fixed `pageSize: 12`, so a URL `page_size` is still ignored.
- Page metadata is unchanged. JSON-LD, tenant profile pages and a sitemap index (over 50,000 URLs) are not implemented.

Server actions and tenant dashboard queries validate input as applicable, then call `${GATEWAY_API_URL}/api/v1/...`. `GATEWAY_API_URL` is a required server-side HTTP(S) gateway origin: blank, malformed, non-HTTP(S), and path-bearing values fail diagnostically, and a trailing slash is normalized. Successful login and registrations set an HTTP-only cookie (`app/(auth)/login/_actions/actions.ts`, `app/(auth)/register/_actions/actions.ts`). Tenant dashboard actions/queries read the cookie and send it as a Bearer token. Tenant dashboard actions and queries additionally send an `X-Tenant-ID` from the `tenant_id` cookie set at login/registration out of the login response's `user.tenant_id`; the header agrees with the token's tenant claim for legitimate traffic, and the gateway discards the inbound copy and publishes the claim value instead, so sending it is compatible but carries no authority ([ADR 0017](../adr/0017-gateway-context-header-trust-boundary.md)). Academic ignores the header for tenant resolution ([ADR 0010](../adr/0010-tenant-context-from-verified-jwt-claim-only.md)).

`proxy.ts` protects `/dashboard` and `/profile` using an optimistic JWT payload/expiry check, clears malformed or expired cookies, and routes valid parent/tenant sessions away from auth pages to their compatible entry point. It does not verify the JWT signature; the backend remains the security authority. It excludes `/api/` and static assets. Browser-side UI coverage is narrower than backend route coverage: no implemented frontend attendance, report, or tutor-management screen was found.

The gateway origin is deliberately server-only rather than a `NEXT_PUBLIC_*` variable because the relevant requests run in Server Actions and Server Components. Enrollment actions authenticate from the HTTP-only cookie, validate all form references, and never accept a price or parent ID from the browser. A duplicate submit/retry keeps the same hidden idempotency key for the mounted form; a new page render creates a new intent. ## Tenant enrollment and payment overview

**Implemented:** a tenant can see the enrollments of its own classes together with the payment status of each one at `/dashboard/tenant/enrollments`, reached from a new Enrollments tab in the tenant sidebar and the mobile drawer. The route is a Server Component whose content is wrapped in `Suspense` with `EnrollmentsSkeleton` as the fallback, and it reads two academic lists and one billing lookup per row. Before KEL-33 the only enrollment screen in the app was the parent-scoped `/dashboard/parent/enrollments`, so a tenant could create and publish classes but had no view that answered who had enrolled and whether they had paid.

The page reads the academic enrollment list and the academic schedule list, then joins each row with the newest billing transaction for that enrollment:

| Source | Request | Notes |
| --- | --- | --- |
| Enrollments | `GET /api/v1/enrollments?page=…&page_size=20[&status=…]` | permission-guarded by `enrollment:read` ([ADR 0002](../adr/0002-academic-permission-enforcement.md)) |
| Schedules | `GET /api/v1/schedules?page_size=100` | looked up by `schedule_id` from the enrollment response |
| Transactions | `GET /api/v1/billing/transactions?enrollment_id=…&page_size=1&page=1` | one request per enrollment, newest first |

The filter vocabulary is the enrollment record's own status — `pending`, `active`, `completed`, `dropped` — and it is deliberately **not** the class-level enrollment status. A class carries `open`/`closed`/`full`/`archived` on a different field, so the enum is named `enrollmentRecordStatusSchema` in `_lib/schema.ts` and `parseEnrollmentFilters` rejects anything outside the four values. An unrecognised `status` renders a validation notice and issues **no** gateway request, so a stale or hand-edited link cannot forward an arbitrary value to the backend.

Two non-obvious decisions shape the implementation, both recorded with their alternatives in [ADR 0023](../adr/0023-tenant-enrollment-payment-join-per-row.md):

- **The transaction join is one request per enrollment, newest first.** `page_size=1` with the billing service's `created_at DESC` ordering means the newest transaction wins. This is required rather than incidental: migration `000002_payment_idempotency` created a unique index on `transactions.enrollment_id` and `000003_subscription_renewals` drops it (`kelolakelas-billing-service/migrations/000003_subscription_renewals.up.sql:13`), so a renewal can leave several transactions on one enrollment and a naive join would surface a stale one.
- **Unreadable detail degrades instead of failing the page.** A failed transaction lookup for one enrollment, a failed schedule list read, and a malformed billing payload each leave the enrollment rows on screen with the missing value rendered as "not available" (`Nominal belum tersedia`, `Belum ada jadwal`). Only an unreadable *enrollment* list is an error, because then there is nothing to show. The schedule list is not permission-guarded (`cmd/server/main.go:118`) and the billing transaction list is not either, so neither can produce the forbidden state on its own.

A payment lookup refused with `403` is the one exception to that degradation (KEL-57). Billing now requires `billing:read` for tenant transaction reads, so a member without it — the built-in Teacher role, for instance — would otherwise have been told every enrollment is waiting for a transaction. `loadTransactions` records such a row as `paymentForbidden`, and `EnrollmentTable` renders "Tidak tersedia untuk role Anda" with "Nominal tidak tersedia" in both layouts; `500`, `503`, and network failures still render "Menunggu transaksi". The shared `lib/payment-status.ts` presentation used by the parent page is unchanged. See [ADR 0024](../adr/0024-billing-read-permission-on-tenant-transaction-reads.md).

The forbidden state is driven by the academic service's permission middleware. A `401` or `403` from the enrollment list renders "Akses ditolak" with the actionable message naming `enrollment:read`, and the filter control is disabled; no status code, gateway URL, or stack trace reaches the UI. This is the same `RequirePermissionUnlessParent` behaviour introduced with the academic enforcement in KEL-21 ([ADR 0002](../adr/0002-academic-permission-enforcement.md)), now surfaced to a tenant member who lacks the permission instead of only to an API client. Remaining failures are mapped to a generic "Data enrollment belum dapat dimuat" for an API error and to the gateway-configuration diagnostic when `GATEWAY_API_URL` is absent or malformed.

## Parent payment return landing

**Implemented (KEL-44):** `/dashboard/parent/enrollments/return` is the landing page for `DUITKU_RETURN_URL` (see [environment variables](../reference/environment-variables.md)). Duitku sends the parent's browser there after checkout with `merchantOrderId`, `resultCode` and `reference`. None of those values is signed, so the page reads only `merchantOrderId`, and only as a lookup key. It never reads or renders `resultCode` or `reference`, and it never shows success because of the redirect. The status always comes from billing and academic, which change only after the verified provider callback ([payment callback flow](../flows/payment-callback.md)).

- **Validation.** `parseMerchantOrderId` (`lib/payment-return.ts`) accepts a single value matching `[A-Za-z0-9-]{1,50}`, which covers a transaction UUID and `renewal-<uuid>`. Anything else (absent, repeated, or containing `%`/`_`, which billing's `ILIKE` search would treat as wildcards) renders "Tautan pembayaran tidak valid" and makes no gateway call.
- **Lookup.** `getPaymentReturnStatus` (`_queries/queries.ts`) calls the parent-scoped `GET /api/v1/billing/transactions?search=<id>&page=1&page_size=20`, where billing applies `parent_id` from the verified session. It accepts only an exact `merchant_order_id` match, because billing's `search` is a substring match on the merchant order id or payment intent id. It then reads `GET /api/v1/enrollments/<enrollment_id>`. The list is unwrapped with `normalizeListEnvelope` ([ADR 0018](../adr/0018-web-list-envelope-unwrapping.md)). `GET /billing/transactions/:id` is not used, because a renewal's merchant order id is not the transaction id.
- **Errors.** Another parent's order id matches no row, so it is reported exactly like an unknown id: "Pembayaran tidak ditemukan", with no enrollment detail. A `401`/`403` renders "Akses ditolak". A `5xx`, a malformed envelope, or a non-UUID `enrollment_id` renders "Status pembayaran belum dapat dimuat", and the page retries on the same bounded automatic refresh described below. A missing or invalid `GATEWAY_API_URL` renders the gateway-configuration diagnostic without a fetch.
- **Presentation.** Reuses `paymentPresentation` (`lib/payment-status.ts`), so pending, reconciling, paid, active, failed, expired, cancelled, refunded and `terminal_failed` look the same as on `/dashboard/parent/enrollments`. A failed or expired payment on an enrollment that is already `active` (a renewal) no longer says "Enrollment belum aktif".
- **Automatic refresh.** `paymentIsSettling` is true while the backend state can still change on its own: transaction `pending`/`creating`, reconciliation `reconciling`, or `paid` with the enrollment still `pending`. While it is true, `PaymentReturnRefresher` calls `router.refresh()` every 5 s, which re-runs the Server Component, so each new status again comes from the backend. The refresh runs one request at a time, pauses while the tab is hidden, and stops at a final status or after a 120 s window anchored to the first render. That is at most 24 refreshes, each one billing list read plus one academic read. After the window, "Periksa status sekarang" re-checks once and starts a new window.
- **Session.** The route sits under `/dashboard/parent`, so `proxy.ts` (unchanged) redirects a missing or expired session to `/login?redirectTo=<path and query>` and keeps tenant sessions out. `getLoginDestination` (`lib/auth-routing.ts`) previously honoured `redirectTo` for a parent only within `/kelas`, so the return URL was dropped after login. It now also accepts paths within `/dashboard/parent` (`PARENT_DASHBOARD_ROOT`), still behind `isSafeRedirectPath`. A non-parent is never sent there. A side effect: a parent sent to login from any `/dashboard/parent/*` page now returns to that page instead of `/kelas`.

Evidence: `kelolakelas-web` `app/(dashboard)/dashboard/parent/enrollments/return/page.tsx`, `return/_components/PaymentReturnRefresher.tsx`, `return/page.test.tsx`, `_queries/queries.ts` (`getPaymentReturnStatus`), `_queries/queries.test.ts`, `lib/payment-return.ts`, `lib/payment-return.test.ts`, `lib/payment-status.ts` (`paymentIsSettling`), `lib/auth-routing.ts`, `lib/auth-routing.test.ts`, `proxy.test.ts`; web [PR #47](https://github.com/kelolakelas/kelolakelas-web/pull/47), squash `60dfae0666c9d660960ec3232dc485a05118b2c8`. 620 tests, typecheck, lint and build passed, and the PR and post-merge push `gate` passed. ## Parent cancellation of a pending enrollment

**Implemented:** a parent can withdraw a pending enrollment from `/dashboard/parent/enrollments`. The backend route shipped with KEL-27 ([ADR 0016](../adr/0016-cancel-pending-enrollment.md)) but the web app deliberately offered no control for it, so a parent who changed their mind still had to wait for `invoice_expires_at` before the seat came back.

The control is a client component backed by the `cancelPendingEnrollment` Server Action (`_actions/actions.ts`). The action reads the session cookie, forwards the enrollment id to `POST /api/v1/enrollments/{id}/cancel` with the bearer token, sends no request body, and calls `revalidatePath('/dashboard/parent/enrollments')` on success so the row is re-rendered from the backend rather than from an optimistic local guess. The browser supplies only the enrollment id from a hidden field; the parent identity and every status decision stay server-side, and the academic service scopes the lookup to the caller, so another parent's enrollment answers 404 rather than confirming it exists.

Two decisions shape the screen:

- **The action is offered only where the backend would accept it.** `canCancelEnrollment` (`lib/enrollment-cancellation.ts`) requires the enrollment to be `pending` *and* its newest transaction to be neither `paid` nor `refunded`. Both halves are needed: an enrollment stays `pending` until activation is applied, so a parent whose payment was already accepted would otherwise be shown a control whose only outcome is the 409 that billing returns when the invoice can no longer be withdrawn.
- **Confirmation uses a native `<dialog>` opened with `showModal()`, not `window.confirm`.** `window.confirm` blocks the event loop, cannot be styled, and cannot be labelled for assistive technology; the platform modal supplies focus trapping, Escape-to-cancel, an inert background and a label via `aria-labelledby` without a dependency. The submit button is disabled while its form is pending, so a double click cannot issue two cancellations.

A refusal keeps the dialog open with its explanation, because the usual reaction is to read it and decide again; a success closes the dialog. The message mapping is what carries the outcome: `409` is reported in full as a state no retry can fix, `404` as an enrollment that is not on this account, `401`/`403` separate an expired session from a caller that is not a parent, and `503` names the authorization service. A `5xx` is replaced rather than passed through, because the academic handler answers `500` with the raw Go error string, which can name internal repositories and database errors — no status code, gateway URL or stack trace reaches the UI.

**Not implemented:** no optimistic status is written locally, so the row keeps showing the backend status until the revalidation lands; and the provider invoice cannot be revoked ([ADR 0016](../adr/0016-cancel-pending-enrollment.md)), so a parent who already has the checkout link open can still pay it, in which case the money is recorded and the activation rejection is surfaced by the existing reconciliation states rather than by this screen.
