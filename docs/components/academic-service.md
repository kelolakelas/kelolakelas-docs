# Academic service (`kelolakelas-academic-service`)

**Implemented:** Gin HTTP server default `:8081`, GORM/PostgreSQL store and public catalog routes. Protected HTTP routes cover categories, classes (including tenant-scoped attribute update behind `class:update`), schedules/sessions, students, attendance, reports and enrollment queries. A parent can cancel their own pending enrollment through `POST /api/v1/enrollments/:id/cancel`, which withdraws the invoice and releases the seat (KEL-27). Two internal credential-protected endpoints serve billing: one activates an enrollment after a confirmed payment, and one releases the seat of a `pending` enrollment whose payment failed or expired (KEL-26). Evidence: `cmd/server/main.go:98-170`.

The service dials identity gRPC using `IDENTITY_GRPC_HOST`; use cases validate tenant status before category/class operations (`pkg/grpcclient/tenant_client.go`, `internal/usecase/category_usecase.go:77`, `class_creation_usecase.go:48`). Tenant-scoped handlers resolve the tenant from the verified JWT claim through `tenantIDFromContext`, never from a request header: a missing claim is 403 and an unusable claim is 401 (`internal/delivery/http/handler/tenant_context.go`). Catalog mutation routes additionally call identity's `tenant.PermissionService/CheckPermission` middleware, which reads persisted role permissions for the caller's `role_id`; denied or missing role context is 403 and identity failure is 503 (`pkg/grpcclient/permission_client.go`, `internal/delivery/http/middleware/permission_middleware.go`). Its catalog use case obtains public tenant information via gRPC. It also makes an internal HTTP payment-initiation call to billing when marketplace catalog enrollment needs payment (`pkg/billing/client.go:45-75`, `internal/usecase/enrollment_usecase.go`).

Academic migrations own categories, classes, schedules, sessions, students, enrollments, attendance, student notes, reports and tenant-location snapshots. They use soft-delete columns where supplied; many identity IDs are UUID values without cross-database foreign keys.

Catalog and schedule mutation routes apply the persisted role-permission check described above before invoking handlers. Other academic domains still rely on JWT authentication plus their existing handler/use-case checks; individual evidence should be reviewed before granting a role access. See [academic API](../api/academic.md).

## Billing-driven enrollment transitions

**Implemented:** billing drives two enrollment transitions through internal-credential routes. `PUT /internal/enrollments/:id/activate` confirms a paid seat. `PUT /internal/enrollments/:id/release` (KEL-26) moves a `pending` enrollment to `dropped` so its schedule seat is available again. Release is idempotent — repeating it succeeds without a second transition — and it never revokes an `active` enrollment, so a late failure notification cannot take back a seat that a confirmed payment already activated. A status that is neither `pending`, `dropped`, nor `active` is rejected with 409 and recorded by billing in the reconciliation row, which makes "paid after the seat was released" an operator-visible outcome instead of a silent success. Evidence: `internal/usecase/enrollment_usecase.go`, `internal/delivery/http/handler/enrollment_handler.go`, `internal/repository/enrollment_repository.go`.
