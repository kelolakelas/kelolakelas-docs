# Academic service (`kelolakelas-academic-service`)

**Implemented:** Gin HTTP server default `:8081`, GORM/PostgreSQL store and public catalog routes. Protected HTTP routes cover categories, classes (including tenant-scoped attribute update behind `class:update`), schedules/sessions, students, attendance, reports and enrollment queries. A parent can cancel their own pending enrollment through `POST /api/v1/enrollments/:id/cancel`, which withdraws the invoice and releases the seat (KEL-27). Two internal credential-protected endpoints serve billing: one activates an enrollment after a confirmed payment, and one releases the seat of a `pending` enrollment whose payment failed or expired (KEL-26). Evidence: `cmd/server/main.go:98-170`.

**Implemented (KEL-63):** the build toolchain is pinned by `go 1.26.6` (`go.mod`; CI follows via `go-version-file`), fixing the reachable go1.26.5 standard-library advisories (GO-2026-6089/GO-2026-5026 `net/http`, GO-2026-6090 `crypto/tls`, GO-2026-5972 `encoding/asn1`, GO-2026-6218 `net/url`, GO-2026-6091 `html/template`). `google.golang.org/grpc` moves v1.82.1 → v1.83.2 (GO-2026-6348, OOM heap growth via HTTP/2 DATA-frame fragmentation) — the same version identity-service now uses, so both ends of the `tenant.PermissionService/CheckPermission` contract run on it. `github.com/jackc/pgx/v5` moves v5.6.0 → v5.9.2 as an indirect dependency of the GORM Postgres driver (GO-2026-5004), with tidy-driven transitives (`golang.org/x/{crypto,net,text,tools}`, `google.golang.org/genproto/googleapis/rpc`). `govulncheck ./...` reports no vulnerabilities; no runtime code or behaviour changed, and the `pkg/grpcclient` contract tests (request carries the tenant, denial and timeout paths) pass under `-race`. Evidence: `kelolakelas-academic-service/go.mod`, `go.sum`; PR #15, squash `da337f83d8eea994c46fcd62653f7b006f7d9dcc`.

The service dials identity gRPC using `IDENTITY_GRPC_HOST`; use cases validate tenant status before category/class operations (`pkg/grpcclient/tenant_client.go`, `internal/usecase/category_usecase.go:77`, `class_creation_usecase.go:48`). Tenant-scoped handlers resolve the tenant from the verified JWT claim through `tenantIDFromContext`, never from a request header: a missing claim is 403 and an unusable claim is 401 (`internal/delivery/http/handler/tenant_context.go`). Session and schedule mutations carry that tenant into the query rather than checking it afterwards: the five operations (reschedule, permanent schedule change, temporary and permanent tutor change, attendees) resolve the target through `GetByIDForTenant`, which joins `classes` and filters on the owning class's tenant, so a foreign resource is 404 with no data change; the three bulk session writes repeat the predicate as `class_id IN (SELECT id FROM classes WHERE tenant_id = ?)` (KEL-17, [ADR 0019](../adr/0019-tenant-scoped-session-and-schedule-mutations.md)). Catalog mutation routes additionally call identity's `tenant.PermissionService/CheckPermission` middleware, which reads persisted role permissions for the caller's `role_id` **inside the tenant the caller is operating on**; academic sends the tenant from the same verified JWT claim the rest of the request uses, and a caller without a usable tenant claim is refused before identity is consulted. Because identity only accepts a role that belongs to that tenant or is a system role, a role lifted from another tenant cannot authorize these mutations. Denied or missing role context is 403 and identity failure, including a check slower than `IDENTITY_PERMISSION_TIMEOUT_MS` (KEL-78), is 503 (`pkg/grpcclient/permission_client.go`, `internal/delivery/http/middleware/permission_middleware.go`). The same middleware guards the tenant-side student and enrollment operations — `student:read` for list/detail, `student:create|update|delete` for the mutations, `enrollment:create` for `POST /tenants/:tenant_id/enrollments`, and `enrollment:read` for enrollment list/detail — while parent tokens skip the check because they carry ownership rather than a role, leaving the handler's own owned-resource rules as the only authority for them (KEL-21). Its catalog use case obtains public tenant information via gRPC. It also makes an internal HTTP payment-initiation call to billing when marketplace catalog enrollment needs payment (`pkg/billing/client.go:45-75`, `internal/usecase/enrollment_usecase.go`).

Academic migrations own categories, classes, schedules, sessions, students, enrollments, attendance, student notes, reports and tenant-location snapshots. They use soft-delete columns where supplied; many identity IDs are UUID values without cross-database foreign keys.

Catalog and schedule mutation routes apply the persisted role-permission check described above before invoking handlers. Other academic domains still rely on JWT authentication plus their existing handler/use-case checks; individual evidence should be reviewed before granting a role access. See [academic API](../api/academic.md).

## Catalog tenant snapshots and outage behavior

**Implemented:** the public catalog does not contact identity on every request. `catalogUsecase.refreshTenantSnapshots` lists the tenants that own classes, subtracts the tenants whose `tenant_location_snapshots.updated_at` is younger than `CATALOG_TENANT_INFO_TTL_MINUTES` (default 5), and only refreshes the remainder — so a request inside the TTL performs no gRPC call and no stored-procedure write. The refresh is written with a single `ON CONFLICT (tenant_id) DO UPDATE` that touches only the refreshed rows, which keeps the snapshot age the TTL is measured against. When identity is unreachable the refresh is logged at `WARN` and skipped, and the catalog still answers from the stored snapshot; a tenant id identity returns that is not a UUID is dropped rather than stored under `uuid.Nil`. Identity calls issued by the catalog are bounded per call by `CATALOG_TENANT_INFO_TIMEOUT_MS` (default 2000) in `pkg/grpcclient/tenant_client.go:41-68` (KEL-42).

The same change made tenant visibility consistent between the two catalog paths: both `List` and `GetByID` join `tenant_location_snapshots` with an inner join on `is_active = true` (`internal/repository/catalog_repository.go:49-52,92`), so a class belonging to an inactive or not-yet-snapshotted tenant is absent from the list and also not reachable by direct id. Filtering, sorting, pagination, and per-schedule availability are unchanged. Evidence: `internal/usecase/catalog_usecase.go`, `internal/repository/catalog_repository.go`, `pkg/grpcclient/tenant_client.go`.

## Billing-driven enrollment transitions

**Implemented:** billing drives two enrollment transitions through internal-credential routes. `PUT /internal/enrollments/:id/activate` confirms a paid seat. `PUT /internal/enrollments/:id/release` (KEL-26) moves a `pending` enrollment to `dropped` so its schedule seat is available again. Release is idempotent — repeating it succeeds without a second transition — and it never revokes an `active` enrollment, so a late failure notification cannot take back a seat that a confirmed payment already activated. A status that is neither `pending`, `dropped`, nor `active` is rejected with 409 and recorded by billing in the reconciliation row, which makes "paid after the seat was released" an operator-visible outcome instead of a silent success. Evidence: `internal/usecase/enrollment_usecase.go`, `internal/delivery/http/handler/enrollment_handler.go`, `internal/repository/enrollment_repository.go`.
