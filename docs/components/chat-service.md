# Chat service

**Implemented (KEL-119):** `kelolakelas-chat-service` runs a Go `net/http` server (`cmd/server/main.go`) with `/health` and staff-only conversation routes. It uses its own PostgreSQL database (`migrations/000001_chat.up.sql`) and a tenant/member-scoped identity gRPC `CheckPermission` request for `chat:manage` (`pkg/grpcclient/permission.go`). Configure the same JWT HMAC secret used by identity, a PostgreSQL connection and `IDENTITY_GRPC_HOST`; run the migration with `cmd/migrate` before starting the server.

`internal/chat/chat.go` is the visibility boundary. A non-parent owner sees a staff conversation when its `member_user_id` matches their verified JWT `user_id`; another tenant member sees it only when identity grants `chat:manage` for the claimed tenant, role and member. Permission failure denies access. Detail, messages, send and read return 404 for invisible conversations. Listing filters in SQL before pagination and validates returned rows. Creation accepts only `staff` and is unique per `(tenant_id, kind, subject_id)`; the subject is the caller's member ID. HTTP errors do not return underlying database details.

Messages contain plain text only, 1–2000 Unicode code points after trimming, with a required `client_message_id`. The database unique key `(conversation_id, sender_user_id, client_message_id)` makes retries return the existing message. Unread count excludes the reader's messages and uses `conversation_reads.last_read_at`; `/read` advances that watermark. Message timelines are ordered newest first by `(created_at, id)`.

**Integration boundary:** as of KEL-119 the existing API gateway and web app do not route or render this service. Direct service HTTP requires a valid Bearer JWT. No parent conversation, attachment, notification or realtime transport is implemented. Tests include service and handler authorization coverage and an optional PostgreSQL integration test gated on `TEST_DATABASE_URL`; the implementer executed it locally, while CI runs without that variable.
