# Academic API

Routes registered in `kelolakelas-academic-service/cmd/server/main.go:98-170` are the source of truth. `GET /api/v1/catalog/classes` and `GET /api/v1/catalog/classes/:id` are public; all other `/api/v1` routes require JWT. Internal activation, release, chat-context reads, and the billing cancel path are outside `/api/v1`.

| Area | Operations | Request/response source |
|---|---|---|
| Catalog | list/detail public classes | `catalog_handler.go`, `domain/catalog.go` |
| Categories/classes | list/create/delete, create-with-category, attribute update, publication toggle | `category_handler.go`, `class_handler.go`, `domain/category.go`, `domain/class.go` |
| Schedules/sessions | create/list/delete, permanent/time or tutor changes, reschedule/substitute, attendees; mutations are tenant-scoped to the owning class, and a foreign resource is 404; tenant-member reads (`GET /sessions`, `GET /sessions/:id`, `GET /sessions/:id/attendees`) require `schedule:read` (KEL-135) | `schedule_handler.go`, `session_handler.go`, `domain/schedule_dto.go`; ADR [0019](../adr/0019-tenant-scoped-session-and-schedule-mutations.md), [0051](../adr/0051-substitute-tutor-active-membership-gate.md) |
| Students | list/create/get/update/delete; parent list/create/update/delete is ownership-scoped; non-parent callers need `student:read|create|update|delete` | `student_handler.go`, `domain/student.go`, web `app/(dashboard)/dashboard/parent/students/**` |
| Attendance/reports | list/create/get/update (reports also delete); tenant members need the operation-specific permission below | `cmd/server/attendance_report_routes.go`, respective handlers/domain files |
| Enrollments | create tenant/catalog enrollment, list/get, schedule assignment, parent cancellation; internal activate, release, suspend, resume, and end; non-parent callers need `enrollment:read|create` | `enrollment_handler.go`, `domain/enrollment.go` |

The public catalog enrollment route is in the gateway’s protected group despite its path beginning `/catalog`; callers need a JWT at the gateway. This is a route-policy distinction from public catalog reads. `POST /api/v1/catalog/classes/{class_id}/enrollments` requires a parent JWT and `Idempotency-Key`; the request body contains `student_id`, `billing_cycle`, optional `schedule_id`, and optional `payment_method` (KEL-125). Group classes require a schedule, and any supplied schedule must belong to the selected class; capacity is rechecked under a database lock. On success it returns a payment transaction ID and checkout URL. `ErrScheduleFull`, idempotency conflicts and a duplicate pending/active enrollment (KEL-54, below) are HTTP 409; missing class/student is 404; ownership, schedule validation, or an unpublished/closed class is 422; billing's platform fee refusal is 422 with `code: platform_fee_exceeds_gross` (KEL-106, below); provider or other unexpected failures are 500. Evidence: `internal/delivery/http/handler/enrollment_handler.go`, `internal/usecase/enrollment_usecase.go`, `internal/repository/enrollment_repository.go`, and the web enrollment action.

**Implemented (KEL-75):** the checkout request body was unchanged by KEL-75; the handler takes the billing contact from the verified parent JWT: the auth middleware publishes the token's `email` claim (TrimSpace applied once at the middleware, case preserved) and both `EnrollPublic` call sites — fresh checkout and the idempotent invoice replay — forward it to billing as `sender_email`. The value is a server-side field (`json:"-"`), so it can never be supplied through the body or a header; a token without the claim forwards the empty string, which billing accepts (unchanged pre-KEL-75 behaviour); a token without a valid signature still fails 401 before the handler. On the billing side a non-empty `sender_email` must be a real address (400 otherwise, before any transaction or subscription is written) and a valid one is stored as `Subscription.BillingEmail` / `Transaction.BillingEmail` and sent as the Duitku invoice email, which is what renewal payment-link emails address. Existing subscriptions are not backfilled. Evidence: academic `internal/delivery/http/middleware/auth_middleware.go`, `internal/delivery/http/handler/enrollment_handler.go`, `internal/domain/enrollment.go`, `internal/usecase/enrollment_usecase.go`, `pkg/billing/client.go`; billing `internal/domain/transaction.go`; academic PR #16 (`d6e2906c726a81ec6ba17861aca265eb19239ef6`), billing PR #14 (`5286a66f4ada37107de9061a2edc9b1d90eb9fcc`).

**Implemented (KEL-125):** Catalog and tenant enrollment requests may include `payment_method`: `VC` (hosted card), `VA` or `BC` (virtual account), `SP` or `NQ` (QRIS). It is optional; an omitted value keeps billing's VC default. Academic validates the allowlist at HTTP binding and again in the use case before reserving an enrollment; an unknown value answers 400. Both new and replayed public enrollment invoice calls, and tenant enrollment invoice calls, forward the field through the internal billing client. Billing retains the already issued transaction's channel and payment URL on replay. Private schedule approval and recommendation acceptance still send no field and use VC; private selection is KEL-133. This is a backend contract only: the current web UI does not expose a channel selector. Evidence: academic `internal/domain/enrollment.go`, `internal/delivery/http/handler/enrollment_handler.go`, `internal/usecase/enrollment_usecase.go`, `pkg/billing/client.go`; [academic PR #38](https://github.com/kelolakelas/kelolakelas-academic-service/pull/38), squash `94b485ad1086379c32ece8af86545ef5ccca7e78`.

## Input bounds and literal search (KEL-87)

**Implemented (KEL-87):** list and request input is bounded before it reaches PostgreSQL. Input over a bound answers **400** with the existing envelope `{"status":"error","message":...,"data":null}`, where it previously reached the database and surfaced as 500.

| Input | Accepted range | Applies to |
|---|---|---|
| `page` query | 1..1000 (`domain.MaxPage`) | public `GET /api/v1/catalog/classes` and the category, class, schedule, session, student, enrollment, report, and attendance list routes |
| `page_size` query | 1..100 (`domain.MaxPageSize`, unchanged) | same routes |
| `search` query | at most 255 Unicode characters (`domain.MaxSearchLength`), counted in runes like PostgreSQL `varchar` | public catalog and the category, class, session, student, enrollment, and report list routes; the schedule list shares the category/class query parser, so it also rejects an overlong `search`, although its repository does not filter on it |
| `name` in create category, create class, and create-with-category `class` payload; report `title` (create and update); schedule `location`; reschedule `new_location` | at most 255 characters (`binding:"max=255"`, the `varchar(255)` column length; a multibyte character counts once) | JSON request bodies |
| schedule `capacity` | group: 1..2147483647 (PostgreSQL `integer` maximum); private: exactly 1 (KEL-132, below) | `POST /api/v1/schedules` items |

**Implemented (KEL-132):** `POST /api/v1/schedules` rejects a private-class item whose `capacity` is not exactly 1 with **400** (`private class schedules must have capacity 1`, existing `{"status":"error",...,"data":null}` envelope) before any write, including direct API calls. Group items keep the 1..2147483647 range, and the approval path for existing private schedule requests (which always writes capacity 1) is unchanged. Historic private rows with capacity > 1 stay readable; no migration was required. Evidence: academic `internal/usecase/schedule_usecase.go` (`ErrPrivateScheduleCapacity`), `internal/delivery/http/handler/schedule_handler.go`; tests `internal/usecase/private_schedule_capacity_test.go`, `internal/usecase/private_schedule_capacity_postgres_test.go`, `internal/delivery/http/handler/schedule_validation_test.go`; [academic PR #40](https://github.com/kelolakelas/kelolakelas-academic-service/pull/40), squash `1a90621237e355cbed0bc1a5e18474a1b0232e49`.

The 400 message is `Invalid pagination` for page, page size, and (on the category/class/schedule and student lists) search; the public catalog answers `Invalid search` for an overlong search, and the session, enrollment, and report lists answer `invalid search`. A body over a length or capacity bound fails Gin binding and uses that handler's existing binding-error 400. Clients must key on the status code, not the message.

Search matches literal text. Every `ILIKE` predicate escapes `\`, `%`, and `_` in the caller's value (`repository.escapeLikePattern`) and declares `ESCAPE '\'`, so `search=50%` matches only names containing `50%`, and `a_b` no longer matches `axb`. The surrounding `%…%` substring match, case-insensitivity, and results for ordinary text are unchanged. The checked-in Swagger now declares the same `maxLength: 255` and `maximum: 2147483647` constraints.

Not bounded by KEL-87: the enrollment `Idempotency-Key` header (stored in `varchar(255)` with no length check) and the class `price` upper bound (a product decision). Evidence: academic `internal/domain/validation.go`, `internal/domain/{catalog,category,class,report,schedule_dto}.go`, `internal/delivery/http/handler/{catalog,list,student,session,enrollment_query,report,attendance}_handler.go`, `internal/repository/search.go` and the seven repositories that search (catalog, category, class, session, student, enrollment, report); tests `internal/domain/validation_test.go`, `internal/delivery/http/handler/{catalog_policy_handler,schedule_validation}_test.go`, `internal/repository/{search,catalog_availability}_test.go`; PR [#30](https://github.com/kelolakelas/kelolakelas-academic-service/pull/30), squash `4e63449a66251dfd05d592b6c0805d3c1b1146cd`.

## Public catalog visibility (KEL-98)

Both public `GET /api/v1/catalog/classes` and `GET /api/v1/catalog/classes/:id` check identity's effective applied `PUBLIC_CATALOG_OPEN` before reading catalog classes or refreshing tenant snapshots. Default version 0 remains open and retains the published/open and active-tenant filters. A closed list answers 200 with `data.items: []`, `data.catalog_open: false`, and pagination totals zero (page/page size follow the validated query); a closed detail answers 404. An open list includes `catalog_open: true`. When the policy is unreadable, malformed or times out, both routes answer 503 without classes, not a cached open response. An open answer is refreshed every request; successful closed answers may persist up to 15 seconds after reopening. The response envelope remains `{status, data}` or `{status, message, data}`. Evidence: academic `internal/usecase/{catalog_policy,catalog_usecase}.go`, `internal/delivery/http/handler/catalog_handler.go`, `pkg/grpcclient/catalog_policy_client.go`; PR #21, squash `d4033c1c6999cfb00660e4a59c8b7c330a59a41b`; [ADR 0036](../adr/0036-applied-public-catalog-policy.md).

## Enrollment suspension, resume, and end (KEL-149)

**Implemented (KEL-149):** billing parks and releases active enrollments through three idempotent internal-credential endpoints: `PUT /internal/enrollments/:id/suspend` (`active` → `suspended`), `PUT /internal/enrollments/:id/resume` (`suspended` → `active`), and `PUT /internal/enrollments/:id/end` (`active`|`suspended` → `dropped`). A suspended enrollment holds no seat — every capacity predicate counts only `pending`/`active` — so suspend frees the schedule slot, the student leaves upcoming session attendees, and attendance can no longer be recorded for it, while history rows stay. Resume reclaims the seat under the enrollment row lock plus the schedule lock with the same capacity and duplicate checks a new signup passes; a full schedule, an ended schedule, or a student who re-enrolled meanwhile answers 409 (`ErrScheduleFull` / `ErrEnrollmentSuspendedConflict`) and the enrollment stays suspended for billing to retry. End frees the seat permanently through the same `dropped` state a parent cancellation writes, so the student may enroll again; a `pending` enrollment is refused with 409 because it must go through the cancel/release paths that also unwind billing. Repeating a transition on its target state answers the row unchanged; any other starting state is 409, unknown ids 404, malformed UUIDs 400. `CancelPendingEnrollment` refuses a suspended enrollment like an active one, so the parent cannot withdraw it and its invoice stays untouched. No migration was needed: `enrollments.status` is `varchar(50)` with no CHECK constraint. Contract details: [ADR 0050](../adr/0050-enrollment-suspend-resume-end.md). Evidence: academic `internal/domain/enrollment.go`, `internal/usecase/enrollment_usecase.go`, `internal/repository/enrollment_repository.go` (`ResumeUnderCapacity`), `internal/repository/session_repository.go`, `internal/delivery/http/handler/enrollment_handler.go`, `cmd/server/routes.go`, regenerated Swagger; tests `internal/usecase/enrollment_suspend_test.go`, `internal/delivery/http/handler/enrollment_lifecycle_handler_test.go`, `internal/repository/enrollment_suspend_postgres_test.go`; [academic PR #41](https://github.com/kelolakelas/kelolakelas-academic-service/pull/41), squash `4afb40acde884a2c61639c304c5cb5d9fdbb0fb4`.

## Private schedule requests (KEL-107)

**Implemented (KEL-107):** Authenticated parents create with `POST /api/v1/catalog/classes/:class_id/schedule-requests` using `student_id`, `billing_cycle` (`monthly`, `quarterly`, `yearly`), `slots` (one or more ISO weekday 1–7 with `HH:MM:SS` start/end), and optional `note`; success is 201 with `status: pending`. The token supplies `parent_id` and `parent_email`, not the body. The student must belong to the parent and the class must be published, open and private. Invalid slots, ownership or class state return 4xx; a second pending request for the same student/class returns 409. `GET /api/v1/schedule-requests` (optional `status` filter) and `GET /api/v1/schedule-requests/:id` are scoped to the parent or tenant; tenant members require `enrollment:read`. `POST /api/v1/schedule-requests/:id/reject` requires tenant `enrollment:update` and accepts optional `reason`; `POST /api/v1/schedule-requests/:id/cancel` requires the owning parent. Only pending requests transition; other-tenant/parent IDs are indistinguishable from missing IDs. Creating a request does not create an enrollment or invoice; approval does (KEL-108, below). ## Private schedule approval and checkout (KEL-108)

**Implemented (KEL-108):** `POST /api/v1/schedule-requests/:id/approve` accepts a request UUID, with no body or caller-supplied billing key. The gateway requires a JWT; academic requires a tenant member with `enrollment:update` (parent tokens denied) and resolves the request by both ID and the verified JWT tenant claim. A foreign/missing request returns 404, a rejected/cancelled request 409, and a caller without permission 403. An approved request can be replayed with the same enrollment and checkout details; the endpoint returns 200 `{status:"success",data:{enrollment:{id,...},payment:{transaction_id,checkout_session_url,...}}}`. A malformed UUID is rejected before usecase execution.

For a pending request, academic creates one pending enrollment at the class price, capacity-one private schedules for the saved slots, and sessions through the current month in a single transaction. It marks the request approved, then invokes billing `GenerateInvoice` **outside** that transaction with `private-request:<request UUID>` as the stable key and the stored parent email as `sender_email`. On success it saves transaction ID and checkout URL without overwriting a concurrent activation webhook; the parent can find the new enrollment/payment through the existing KEL-53 status page and billing transaction listing. Repeated/parallel approvals reuse the same enrollment and schedules; concurrent billing calls rely on billing's idempotency key. A transient billing failure leaves a pending enrollment and approved request with no checkout for a retry. A `platform_fee_exceeds_gross` rejection drops the enrollment, resets the request to pending, returns 422 with that code, and allows retry under the same key after the fee policy changes. No billing or web change is part of KEL-108. Evidence: academic `internal/usecase/private_schedule_request_usecase.go` (`Approve`), `internal/repository/{private_schedule_request,enrollment}_repository.go`, `internal/delivery/http/handler/private_schedule_request_handler.go`, `cmd/server/routes.go`, tests `internal/usecase/private_schedule_approval_{test,postgres_test}.go`, handler permission test; gateway `internal/delivery/http/{router,router_test}.go`; [academic PR #35](https://github.com/kelolakelas/kelolakelas-academic-service/pull/35), squash `603b29aa0a14c2da04cede9da62f8504446c5151`; [gateway PR #29](https://github.com/kelolakelas/kelolakelas-api-gateway/pull/29), squash `2ce4b1b7024758d96f3506e8b938e3a55b315428`.

**Implemented (KEL-128):** that same approval call (and the KEL-115 recommendation acceptance sharing the purchase operation) now also sends `private_schedule_request: true` to billing, so billing emails the payment link, amount and exact expiry to the saved parent address — see [billing API](billing.md). The academic response, retry and manual checkout behavior are unchanged, and an email delivery failure in billing never fails the approval. Evidence: academic `internal/usecase/private_schedule_request_usecase.go` (`GenerateInvoice` call), `pkg/billing/client.go`, `internal/usecase/private_schedule_approval_test.go`; [academic PR #39](https://github.com/kelolakelas/kelolakelas-academic-service/pull/39), squash `08aa007b488914281be917ccd00eeda1f22d0637`.

## Duplicate enrollment conflict (KEL-54)

**Implemented (KEL-54):** a student may hold only one `pending` or `active`, non-deleted enrollment per class (partial unique index `idx_student_class_active`, `migrations/00000000000000_init_schema.up.sql`). A second enrollment for the same student and class used to hit that index unmapped and answer 500. Both `POST /api/v1/catalog/classes/{class_id}/enrollments` and `POST /api/v1/tenants/{tenant_id}/enrollments` now answer **HTTP 409** with a machine-readable distinguisher:

```json
{"status": "error", "message": "student already has a pending or active enrollment in this class", "code": "duplicate_enrollment", "data": null}
```

(`data` is present only on the catalog route.) `code` is the contract, not `message`. It is the optional `ErrorResponse.code` field (`omitempty`) and is sent only for this case: the 409 bodies for a full schedule and an Idempotency-Key reused with a different request are unchanged and carry no `code`, and a client must treat a 409 without `code` as before. Detection has two layers inside the enrollment transaction. A pre-check with the index predicate runs after the schedule row lock and before the capacity count, so a student's own seat is reported as a duplicate rather than a full schedule. A PostgreSQL `23505` on `idx_student_class_active` alone is mapped to the same error, which settles two concurrent requests with different Idempotency-Keys (two tabs, different schedules, or a private class without a schedule to lock): one enrollment is created and the other gets the 409. The mapping is local; GORM `TranslateError` stays disabled because attendance inspects `gorm.ErrDuplicatedKey` separately. A retry with the same Idempotency-Key still returns the original enrollment, and a `dropped`, `completed` or soft-deleted enrollment does not block a new one. Evidence: academic `internal/domain/{enrollment,category}.go` (`ErrDuplicateEnrollment`, `DuplicateEnrollmentErrorCode`, `ErrorResponse.Code`), `internal/repository/enrollment_repository.go` (`rejectLiveEnrollment`, `mapDuplicateEnrollment`), `internal/delivery/http/handler/enrollment_handler.go`; tests `internal/repository/duplicate_enrollment_postgres_test.go`, `internal/delivery/http/handler/enrollment_handler_test.go`, `internal/usecase/enrollment_duplicate_test.go`; academic PR [#23](https://github.com/kelolakelas/kelolakelas-academic-service/pull/23), squash `ff462d6592e66c570fafc86d218dc899bc0a47cc`.

## Platform fee rejection (KEL-106)

**Implemented (KEL-106):** billing refuses an invoice whose platform fee plus payment gateway fee exceeds the gross amount with HTTP 422 `code: platform_fee_exceeds_gross` and writes no transaction (KEL-99, [billing API](billing.md)). Academic used to surface that as a 500. Both `POST /api/v1/catalog/classes/{class_id}/enrollments` and `POST /api/v1/tenants/{tenant_id}/enrollments` (tenant-member callers and the parent branch) now answer **HTTP 422** with the same code and billing's message:

```json
{"status": "error", "message": "Biaya platform melebihi jumlah pembayaran", "code": "platform_fee_exceeds_gross", "data": null}
```

(`data` is present only on the catalog route and the tenant route's parent branch.) `code` is the contract, not `message`; other 422 bodies (ownership, schedule validation, closed class) carry no `code` and are unchanged. Only billing's exact pair, status 422 with that code, is treated as the rejection. A billing 422 without a code or with another code, the same code on another status, and every other billing failure keep their existing answer (500 on the catalog route and for tenant members; 422 without `code` on the tenant route's parent branch, which answers every error 422) and keep the pending enrollment for a same-key retry. A policy outage (`platform_fee_policy_unavailable`, 503) is handled the same way.

The enrollment row created before the invoice call is moved, under a row lock, from `pending` to `status = dropped` with `payment_status = platform_fee_rejected`. Capacity and the `idx_student_class_active` duplicate check count only `pending` and `active`, so the rejected attempt holds no seat and does not make a new attempt for the same student and class answer `duplicate_enrollment`. A replay with the same `Idempotency-Key` (including the concurrent-create fallback) finds that row and answers the same 422, without calling billing or creating an enrollment or transaction. After the platform fee policy changes, a new attempt needs a new key. If the drop itself fails, the request answers as an unexpected failure (500 on the catalog route and for tenant members) rather than with the coded 422; the row still has no transaction, so a same-key retry asks billing again. `platform_fee_rejected` is a new value of the existing `payment_status` varchar(30) column, so no migration is required. See [ADR 0045](../adr/0045-drop-enrollment-on-platform-fee-rejection.md). Evidence: academic `pkg/billing/client.go` (`PlatformFeeExceedsGrossCode`, `ErrPlatformFeeExceedsGross`), `internal/domain/enrollment.go` (`ErrPlatformFeeExceedsGross`, `PlatformFeeExceedsGrossErrorCode`, `PaymentStatusPlatformFeeRejected`), `internal/usecase/enrollment_usecase.go` (`invoiceFailure`, `dropPlatformFeeRejected`, `platformFeeRejected`), `internal/delivery/http/handler/enrollment_handler.go`; tests `pkg/billing/platform_fee_test.go`, `internal/usecase/enrollment_platform_fee_test.go`, `internal/usecase/enrollment_platform_fee_postgres_test.go` (`KEL106_TEST_DSN`), `internal/delivery/http/handler/enrollment_handler_test.go`; academic PR [#33](https://github.com/kelolakelas/kelolakelas-academic-service/pull/33), squash `23fc8dc7a3750a9f2592d62557017da7e0a95379`.

## Enrollment schedule summary (KEL-70)

**Implemented (KEL-70):** `GET /api/v1/enrollments` (each list item) and `GET /api/v1/enrollments/:id` carry an additive, optional `schedule` object next to the existing `schedule_id`:

```json
"schedule": {"day_of_week": 1, "start_time": "16:00:00", "end_time": "17:30:00", "location": "Ruang A"}
```

`day_of_week` uses ISO numbering (1 = Monday/Senin, 7 = Sunday/Minggu), times are the stored `HH:MM:SS` wall-clock strings, and `location` is omitted when the schedule has none or only whitespace. Capacity, tutor and the validity window are not exposed. The whole `schedule` key is omitted for a private enrollment (no `schedule_id`), for a soft-deleted schedule, and for a schedule whose id or class does not match the enrollment. Clients must treat it as optional even when `schedule_id` is present. Every existing field is unchanged. The raw `Enrollment` model keeps the preloaded schedule out of JSON (`json:"-"`), so other payloads that embed enrollments, such as session attendees, are unchanged too.

The data comes only from rows the caller may already see. The scoped repository reads (`List`, `GetByIDForAccess`) add `Preload("Schedule")`, which GORM runs as ONE `class_schedules.id IN (...) AND deleted_at IS NULL` query keyed by the schedule ids of rows that passed the tenant/parent filter. That is one extra round trip per call, with no N+1 and no schedule a parent's own rows do not reference. There is no parent schedule endpoint. Tenant callers of the same routes receive the field too; the tenant dashboard does not use it yet and still resolves schedules through `GET /api/v1/schedules`. Evidence: academic `internal/domain/enrollment.go` (`Enrollment.Schedule`, `EnrollmentResponse.Schedule`, `EnrollmentScheduleSummary`), `internal/repository/enrollment_repository.go`, `internal/usecase/enrollment_usecase.go` (`enrollmentScheduleSummary`); tests `internal/repository/enrollment_schedule_summary_test.go`, `internal/repository/enrollment_schedule_postgres_test.go` (`KEL70_TEST_DSN`: parent A vs parent B isolation and a soft-deleted schedule on real PostgreSQL), `internal/usecase/enrollment_schedule_summary_test.go`; academic PR [#29](https://github.com/kelolakelas/kelolakelas-academic-service/pull/29), squash `2c469ce47717a729b92a13fd464481d498ebd03e`.

## Schedule validity in catalog and enrollment (KEL-52)

**Implemented (KEL-52):** both `GET /api/v1/catalog/classes` and `GET /api/v1/catalog/classes/:id` omit schedules whose `valid_until` is before the application process's current local calendar date. A schedule ending today or with no end date remains visible; future `valid_from` does not hide it. A group class with no remaining schedules stays in the catalog with an empty schedule array. The response shape and seat availability calculation do not change.

Catalog enrollment with an ended `schedule_id` returns HTTP 422 without creating an enrollment; schedule assignment rejects an ended schedule with the same status. Existing pending enrollments are not changed. Date validity uses the application's `time.Now().Location()` calendar date, consistent with `normalizeDate`, rather than the database server's timezone or clock; `valid_until` is inclusive through today. Evidence: academic `internal/repository/{catalog_repository,enrollment_repository}.go`, `internal/delivery/http/handler/enrollment_handler.go`, `internal/repository/schedule_validity_postgres_test.go`, and PR #22 (`e27fd61737c29ed25a6aa2260c80cdeff9ec2b8b`).

## Catalog mutation authorization

**Implemented:** authenticated category, class, schedule, and schedule-related session mutations call identity's persisted permission check before entering the handler. `category:create|delete`, `class:create|update|delete`, and `schedule:create|update|delete` are mapped at route registration. The same check guards the tenant-side student and enrollment operations: `student:read` for student list/detail, `student:create|update|delete` for the student mutations, `enrollment:create` for `POST /api/v1/tenants/:tenant_id/enrollments`, and `enrollment:read` for enrollment list/detail. The request carries `tenant_id` next to `role_id` and `permission`, taken from the verified JWT claim and never from a header, and identity answers it against the role that belongs to that tenant or is a system role; a caller without a usable tenant claim is refused with 403 before identity is consulted, so a role lifted from another tenant cannot authorize the mutation. A tenant member without the required assignment — including the seeded `Teacher` role, which holds no student or enrollment permission — receives 403 with no data change, and a tenant member whose token carries no `role_id` is refused with 403 before identity is consulted. Since KEL-80 the request also carries the token's `member_id`, so identity denies a member who was removed, deactivated or moved to another role (403) with a still-valid token, and a tenant token without a UUID `member_id` is refused with 403 before identity is consulted; parents are unaffected. An identity dependency failure receives 503. The student and enrollment routes are also reachable by parents, whose token carries ownership instead of a role; for those callers the check is skipped and the handler's existing owned-resource rules remain the only authority, so a parent keeps managing its own students and creating catalog enrollments without a `role_id`, even while identity is unavailable. Public catalog list/detail reads remain unauthenticated. Tenant/resource ownership checks remain in the academic use cases. See [ADR 0002](../adr/0002-academic-permission-enforcement.md). Evidence: `cmd/server/main.go`, `internal/delivery/http/middleware/permission_middleware.go`, `pkg/grpcclient/permission_client.go`, `internal/delivery/http/handler/student_enrollment_permission_handler_test.go`, and identity `internal/delivery/grpc/permission_service.go`.

## Session read permission, own-session filter, and substitute-tutor validation (KEL-135)

**Implemented:** the three session read routes shared by tenant members and parents — `GET /api/v1/sessions`, `GET /api/v1/sessions/:id`, and `GET /api/v1/sessions/:id/attendees` — now require the `schedule:read` permission for tenant-member tokens via `RequirePermissionForTenantResource`, the same pattern the attendance/report table uses (ADR 0002). A member whose role lacks `schedule:read` (for example a custom role) receives 403 before the handler; Creator and Teacher hold it from the seeded permission catalog. A denied check is 403 and an identity failure or timeout is 503. Parent tokens skip the check and keep their existing handler behaviour, so no parent path changed.

`GET /api/v1/sessions?mine=true` returns only the caller's own sessions: the filter derives `tutor_id` from the verified JWT `member_id` claim and ignores any client-supplied `tutor_id` in that case (a tenant caller without a usable member claim gets 401 `Invalid user context`); a request without `mine=true` keeps accepting an explicit `tutor_id` filter unchanged.

`PATCH /api/v1/sessions/substitute-tutor` (and the `:id` alias) validates the substitute before any write. Academic resolves the session tenant-scoped first (an unknown or foreign session stays 404 with no membership probe), then calls identity `tenant.MembershipService/CheckActiveMembership` with the session's tenant and the requested tutor id; the call is bounded by `IDENTITY_PERMISSION_TIMEOUT_MS` like the permission check. A tutor that is not an active member of the same tenant (another tenant's member, an inactive/removed member, or a random id) is rejected 400 `Substitute tutor must be an active member of this tenant` with zero session writes; an unreachable, slow, or malformed identity answer — or an unwired membership client — is rejected 503 `Substitute tutor membership could not be verified`, never a silent pass. Only after an explicit `active: true` does the existing tutor change run. See [ADR 0051](../adr/0051-substitute-tutor-active-membership-gate.md). Evidence: `cmd/server/routes.go`, `internal/delivery/http/handler/session_handler.go`, `internal/delivery/http/handler/schedule_handler.go`, `internal/usecase/schedule_usecase.go` (`ErrSubstituteTutorNotEligible`, `ErrSubstituteTutorUnavailable`), `pkg/grpcclient/membership_client.go` (`ParseActiveMember` strict verdict, per-call deadline); tests `internal/delivery/http/handler/session_mine_filter_test.go`, `internal/usecase/substitute_tutor_membership_test.go`, `pkg/grpcclient/membership_client_test.go`, `cmd/server/attendance_report_routes_test.go` (`TestAttendanceReportRoutesPermissionMatrix`), `cmd/server/swagger_contract_test.go` (swagger `@x-permission` ↔ middleware); academic [PR #42](https://github.com/kelolakelas/kelolakelas-academic-service/pull/42), squash `f77f3f9e8d620b723f041c9838230a1c3d3af5bc`, with the identity side in identity PR [#35](https://github.com/kelolakelas/kelolakelas-identity-service/pull/35).

## Tenant context resolution

**Implemented:** every tenant-scoped academic handler derives the tenant from the verified JWT claim. `tenantIDFromContext` reads only the `tenant_id` value `AuthMiddleware` stored from the token and never reads `X-Tenant-ID`; category, class, list, and schedule handlers call it directly, and `list_handler.go` keeps a `tenantID` wrapper onto the same helper. A request whose token carries no tenant claim receives 403, and a claim that is not a parseable non-nil UUID receives 401; unknown tenant errors fail closed to 403. The gateway removes `X-Tenant-ID` from every inbound request and republishes it from the verified claim on protected routes, and a non-parent token without a usable tenant claim is refused with 401 at the gateway, so a caller cannot select a tenant the token does not carry. See [ADR 0010](../adr/0010-tenant-context-from-verified-jwt-claim-only.md) and [ADR 0017](../adr/0017-gateway-context-header-trust-boundary.md). Evidence: `internal/delivery/http/handler/tenant_context.go`, `tenant_context_regression_test.go`, `internal/delivery/http/middleware/auth_middleware.go`.

For `POST /api/v1/tenants/:tenant_id/enrollments`, a non-parent caller must present a claim equal to the `:tenant_id` path segment; a mismatch is 403 and no enrollment is created. A parent caller keeps the existing public catalog enrollment flow, which is scoped by student ownership rather than by tenant, and the path segment is still validated as a UUID (400 when malformed). Evidence: `internal/delivery/http/handler/enrollment_handler.go`.

The academic Swagger document no longer declares `X-Tenant-ID` as a request parameter on any operation; the regenerated `docs/swagger.{json,yaml}` and `docs/docs.go` contain no occurrence of it.

## Class attribute update

**Implemented:** `PATCH /api/v1/classes/:id` applies a partial update to a class owned by the caller’s tenant. The handler requires the `class:update` permission, derives the tenant from the verified JWT claim, and passes only the supplied fields; `category_id`, `name`, `description`, `price`, and `type` are the accepted fields, and an omitted field keeps its stored value. The use case loads the class tenant-scoped, reports a class owned by another tenant as 404 rather than 403 so the endpoint does not confirm the existence of foreign rows, and the repository write repeats `WHERE id = ? AND tenant_id = ?` so a zero row count becomes not found. A changed `category_id` is re-validated for existence and ownership; both a missing category and a foreign-tenant category are 422, so the endpoint is not an existence oracle for other tenants’ categories either. Changing `type` is rejected with 422 because schedules, sessions, and enrollments were created against the stored type. A blank `name` and a negative `price` are 422. Price changes are forward-only: each enrollment persists the price snapshot it was created with, so an existing enrollment keeps its stored gross amount and is never re-priced. See [ADR 0013](../adr/0013-tenant-scoped-class-update.md). Evidence: `internal/delivery/http/handler/class_handler.go`, `internal/usecase/class_usecase.go`, `internal/repository/class_repository.go`, `internal/domain/class.go`, `internal/delivery/http/handler/class_update_test.go`, `internal/usecase/class_update_test.go`.

## Internal chat context (KEL-118)

**Implemented (KEL-118):** Academic serves `GET /internal/chat-context/schedule-requests/:id` and `GET /internal/chat-context/reports/:id` only inside the `/internal` group guarded by `X-Internal-Service-Credential`. An absent or incorrect credential returns 401 before any database read; malformed or nil UUID returns 400; an unknown resource or one with soft-deleted related rows returns 404.
