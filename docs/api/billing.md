**Implemented (KEL-58):** `GET /api/v1/billing/transactions/summary` returns the caller tenant's paid sales, one bucket per currency so different currencies are never added: `transaction_count`, `SUM(gross_amount)` and `SUM(net_amount)` of rows with `status = 'paid'` and `paid_at` in the half-open interval `[from 00:00 UTC, to+1 day 00:00 UTC)`. `from` and `to` are optional `YYYY-MM-DD` UTC calendar days; the default is today (UTC) and the 29 days before it. A malformed date, `from > to`, or a span over 366 inclusive days is 400 `Invalid sales summary range`. The tenant comes only from the verified JWT `tenant_id` claim (no query or header is read); soft-deleted rows are excluded by the GORM filter. `totals` is `[]` for a tenant without sales. Net follows the stored `net_amount`; platform fee policy is unchanged. Authorization is `middleware.RequirePermission(billing:read)`: unlike the list/get reads, a parent token is refused with 403 before identity is consulted, even when it carries a tenant claim ([ADR 0039](../adr/0039-tenant-sales-summary-per-currency-utc.md)). Evidence: billing `internal/delivery/http/handler/transaction_handler.go` (`SalesSummary`), `internal/repository/transaction_repository.go` (`SummarizePaid`), `internal/delivery/http/middleware/permission_middleware.go` (`RequirePermission`), `cmd/server/routes.go`; tests `internal/repository/transaction_sales_summary_{test,integration_test}.go`, `internal/delivery/http/handler/transaction_sales_summary_handler_test.go`, `cmd/server/routes_test.go`; [PR #21](https://github.com/kelolakelas/kelolakelas-billing-service/pull/21), squash `2f0982de17fe993ef9c2ed74a148af9bd1aa1da0`.

Invoice creation is available only at `POST /internal/billing/transactions`, after academic has verified the enrollment and supplied the internal bearer credential. `DuitkuCallbackPayload` requires merchant code, amount, merchant order ID, result code, reference, and signature according to `internal/domain/payment_gateway.go`. The handler rejects a failed signature before business processing. **Implemented (KEL-56):** on a signed `resultCode=00` callback for an unpaid transaction, billing calls Duitku `POST /transactionStatus` with the configured timeout, then accepts `paid` only when the returned status is `00` and the merchant order, amount and reference agree with the stored transaction/callback. Provider errors or mismatches yield a non-2xx response and no wallet/ledger mutation, while an already-paid replay stays idempotent without another status call. The `01`/`02` callback paths are unchanged. The public callback request/response schema is unchanged. See [ADR 0033](../adr/0033-confirm-duitku-payment-status-before-settlement.md) and [payment callback flow](../flows/payment-callback.md). Evidence: billing `internal/usecase/transaction_usecase.go`, `pkg/duitku/client.go`, `internal/usecase/transaction_status_confirmation_test.go`; PR #15 (`66597cdd5a5a0ee570534d34824c8e64b4bf5737`).

**Implemented (KEL-75):** that invoice request now carries an optional `sender_email`. Invoice creation itself remains internal-only (`POST /internal/billing/transactions`; there is no JWT write route for transactions). Validation sits on the request binding (`GenerateSubscriptionPaymentRequest.SenderEmail`, `binding:"omitempty,email"` in `internal/domain/transaction.go`): an empty value is accepted — rollout tokens without the parent email claim keep working, same behaviour as before this change — while a non-empty value that is not a real address answers the binding-validation 400 before the use case runs, so no transaction or subscription row is written. A valid value is stored as `Subscription.BillingEmail` and `Transaction.BillingEmail` and is sent to Duitku as the invoice email. The value is stored as received: the sender email is normalised once upstream in academic's auth middleware (TrimSpace, case preserved), and pre-existing rows are not backfilled, so a subscription created without the claim keeps no billing email and the renewal worker skips its reminder (existing skip behaviour).

**Implemented (KEL-125):** `POST /internal/billing/transactions` accepts optional `payment_method` in exactly `VC`, `VA`, `BC`, `SP`, `NQ`; absent means `VC`. `VC` stays on Duitku's hosted card URL; `VA` and `BC` are VA and `SP` and `NQ` are QRIS. Binding rejects other values with 400, and the use case repeats validation before writes for internal callers bypassing HTTP. New transactions store the chosen value in the existing `payment_method` column and pass it to Duitku inquiry. A valid existing invoice returns its original link even if a replay asks for another channel; expired reissue retains its saved channel (legacy empty becomes VC). The paid callback does not replace a nonempty selected method. No card number/CVV is accepted, no new checkout endpoint or schema migration is introduced. Private approval/recommendation still omit the field (VC); KEL-133 covers private selection. Evidence: billing `internal/domain/transaction.go`, `internal/usecase/transaction_usecase.go`, `internal/delivery/http/handler/transaction_handler.go`; tests `internal/usecase/payment_method_test.go`, `internal/repository/payment_method_postgres_test.go` (isolated database), `internal/delivery/http/handler/platform_fee_handler_test.go`; [billing PR #25](https://github.com/kelolakelas/kelolakelas-billing-service/pull/25), squash `f1e1a14cfe19b3f238b16c4676f9eced9f1a8093`. Operator sandbox inquiry accepted all five codes (HTTP 200/statusCode 00); production channel availability and expiry limits are not established by that test.

**Implemented (KEL-126):** the existing scoped transaction list/detail responses add optional `payment_method`, `va_number`, `qr_string`, and `app_url` without removing `checkout_session_url`, `status`, or `invoice_expires_at`. Duitku inquiry fields `vaNumber`, `qrString`, and `appUrl` are persisted together with `reference` and `paymentUrl`; an older row or a provider response containing only `paymentUrl` still offers hosted checkout. Payment intent, hosted URL and instruction fields are omitted unless the transaction is `pending` and its deadline has not passed (an absent deadline preserves legacy pending checkout). A reinvoice clears the previous fields before writing the replacement. An expired or failed row and even a paid late callback retain status/expiry evidence but cannot appear payable. Billing checks the parent/tenant scope before constructing the response; gateway's existing proxy forwards it unchanged. Provider error bodies and SQL parameter values are not logged. No live sandbox call was run for this change; provider-shape fixtures were tested locally. **Implemented (KEL-128):** the internal invoice request accepts optional boolean `private_schedule_request` (`GenerateSubscriptionPaymentRequest.PrivateScheduleRequest`, default false), set only by academic's private schedule approval and recommendation acceptance next to the saved `sender_email`. A true flag stores on the transaction and opts the invoice into exactly one payment-link email to the persisted `billing_email` (amount, exact stored expiry, HTTPS checkout link), dispatched from the persisted row through a conditional claim; a missing Resend configuration fails that delivery (observable `failure_reason`, retried by the per-minute worker) instead of being skipped silently. The route's response contract is unchanged — the checkout URL is still returned and an email failure never fails the request. See [billing component](../components/billing-service.md) for claim/retry semantics. **Implemented (KEL-99):** the request's `platform_fee` is still accepted (academic sends it) but ignored. Billing computes the fee from identity's applied platform fee policy ([ADR 0044](../adr/0044-platform-fee-policy-applied-snapshot.md)). Two new error answers of `POST /internal/billing/transactions` carry a stable `code` next to the envelope's `message`, and neither writes a subscription or transaction:
- `422` with code `platform_fee_exceeds_gross` and message `Biaya platform melebihi jumlah pembayaran` when `platform_fee + payment_gateway_fee > gross_amount`;
- `503` with code `platform_fee_policy_unavailable` when identity cannot answer, returns a malformed policy, or has no applied version.

Transaction responses expose the snapshot as `platform_fee_policy_version`, `platform_fee_percent_bps` and `platform_fee_fixed`. They are omitted for transactions created before KEL-99, which carry no policy version. Evidence: billing `internal/delivery/http/handler/transaction_handler.go`, `internal/domain/transaction.go`, `internal/delivery/http/handler/platform_fee_handler_test.go`; PR [#24](https://github.com/kelolakelas/kelolakelas-billing-service/pull/24), squash `95cce66636e5efa4f01b55fae0d0d9423969fa19`.

`POST /internal/billing/transactions/cancel` is the withdrawal path a parent cancellation uses (KEL-27, [ADR 0016](../adr/0016-cancel-pending-enrollment.md)). It takes an `enrollment_id` and marks the enrollment's unpaid transaction `cancelled`, releasing the reserved seat through the existing release reconciliation. A `paid` or `refunded` transaction is never rewritten: it answers 409 so the caller knows the money is in, and an enrollment with no transaction at all answers 404 so a failed invoice creation does not strand a seat. Repeating the call for an already-`cancelled` transaction returns the current transaction, so a retried request is safe.

The two transaction reads are authorized per caller type (KEL-57, [ADR 0024](../adr/0024-billing-read-permission-on-tenant-transaction-reads.md)). A parent token reads only its own transactions and never reaches identity. A tenant token must carry `role_id`, `tenant_id` and (since KEL-80) a UUID `member_id`; billing asks identity's `CheckPermission` for `billing:read` inside that tenant, pinned to that membership, before the handler runs, so a member who was removed or moved to another role is denied with a still-valid token. A missing claim or a denied check answers `403 {"status":"error","message":"Permission denied","data":null}`; an identity failure or timeout answers `503` with message `Authorization service unavailable` and no transaction data. The built-in Creator role holds `billing:read`; the built-in Teacher role does not, and a custom role has it only when an owner grants it.

For paid transactions, the list/detail response also exposes `reconciliation_status`, `reconciliation_attempts`, `reconciliation_next_attempt_at`, and `reconciliation_last_error`. `active` means Academic activation succeeded, `reconciling` means durable retry is pending/in progress, and `terminal_failed` means the configured retry limit was reached.

`reconciliation_kind` names the Academic action an outstanding job owes: `activation` confirms a paid seat, `release` gives the seat back after the payment failed or the invoice expired (KEL-26, [ADR 0012](../adr/0012-release-enrollment-seat-on-failed-payment.md)). It is omitted when no reconciliation row exists, so an operator can tell a payment that is still settling from a failed payment that freed the seat again.

Every transaction response also exposes `invoice_expires_at` (the deadline sent to Duitku and enforced locally) and `expired_at` (set when the local expiry worker moved an unpaid transaction to `expired`). Both are omitted when unset. A transaction can legitimately be `paid` with a non-null `expired_at` when a valid payment callback arrived after the local deadline; see [ADR 0009](../adr/0009-local-invoice-expiry-without-losing-late-payments.md). Callback result codes outside `00`/`01`/`02` change nothing and are recorded as structured `WARN` logs.

The `status` filter accepts exactly the statuses the code writes, including `creating`. The handler validates through `domain.IsTransactionStatusFilterValue` (`internal/domain/transaction.go:61`) instead of hand-listing values per call site, and an unknown status answers `400 Invalid transaction status`. `domain.TransactionStatusFilterValues` (`:45`) is the single accepted set; `internal/domain/transaction_status_test.go` parses `transaction.go` with `go/parser` and fails if the constants the code writes and that accepted set ever diverge, so a new status cannot be written without also being filterable.

`GET /internal/billing/reconciliations` and `POST /internal/billing/reconciliations/requeue` are the operator path for reconciliation jobs that no longer retry themselves (KEL-29). They sit behind the same internal credential middleware as the other `/internal/billing` routes and are deliberately not exposed through the gateway, because there is no platform-admin persona to authenticate them for a browser. The list endpoint returns the raw rows — attempt count, stored failure, and timestamps included — newest first, so a stuck `release` can be told apart from a stuck `activation` without a database session. Its `status` parameter is validated against `domain.ReconciliationStatusValues` (`internal/domain/payment_reconciliation.go`), the same set the state machine writes; `internal/domain/reconciliation_status_test.go` parses the source with `go/parser` and fails if a new status is added without becoming filterable. The re-drive endpoint keeps its guard inside the update statement: only `terminal_failed` rows match, so replaying it never resets a job that is pending, in flight, or completed, and `requeued` reports the number of rows the database actually changed. The attempt count is not reset, so `PAYMENT_RECONCILIATION_MAX_ATTEMPTS` continues to bound how many further attempts a re-driven job gets. Both endpoints answer `503` when billing was started without a reconciliation store, and `500` without leaking the store error. Every transition they act on is also recorded in the service log; see [operations](../07-operations.md).

A transaction response also exposes `invoice_claimed_at` (when the in-flight attempt to create the invoice took exclusive ownership of the row) and `invoice_failure_reason` (why the last attempt failed). Both are omitted when unset. They are the durable evidence behind the recovery behaviour described in [billing and subscriptions](../flows/billing-and-subscriptions.md), and they are what makes a `creating` row diagnosable through the API instead of only visible in the database.

**Implemented (KEL-142):** tenant wallet and ledger reads plus payout-account management. `GET /api/v1/billing/wallet` returns the caller tenant's wallet balance behind `billing:read`; parents are refused 403 before identity is consulted, like the sales summary. A tenant without a wallet gets a zero balance, not an error: sandbox callbacks never credit the wallet or the ledger, and the response documents this. On payment-only data the balance equals the sum of the tenant's ledger entries. `GET /api/v1/billing/ledger` returns the tenant's append-only ledger mutations behind `billing:read`, newest first, with `page`/`page_size` (at most 100, invalid is 400); a tenant without a wallet gets an empty page. `GET`/`POST /api/v1/billing/bank-accounts`, `PATCH`/`DELETE /api/v1/billing/bank-accounts/:id`, and `POST /api/v1/billing/bank-accounts/:id/set-primary` manage payout accounts behind `billing:withdraw` with the same parent refusal. Exactly one primary per tenant is enforced by the partial unique index `uq_bank_accounts_tenant_primary` plus a transactional clear-then-promote with row lock, so two concurrent set-primary calls still leave one primary; set-primary and delete preserve history (soft delete), and deleting the primary while an active withdrawal references it answers 409. Account numbers are always masked to the last four digits in tenant reads. Billing is the owner of all tenant finance data; see [ADR 0055](../adr/0055-tenant-finance-data-ownership.md).
