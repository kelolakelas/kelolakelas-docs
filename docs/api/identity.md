# Identity API

Implemented routes are registered in `kelolakelas-identity-service/cmd/server/main.go:103-131`; request binding structs and response branches are in `internal/delivery/http/handler/`.

| Tenant register | `RegisterTenantRequest`: email (case-insensitive, KEL-89), password 6–72 bytes, first/last/tenant name max 255 characters, phone/tenant_phone max 50 characters | 201 token/user/tenant; 400 invalid/oversized input, 409 name/email conflict (email compared case-insensitively) |
| Invitation create/verify/register | `CreateInvitationPayload`; token query; invited-user payload | creation requires `member:invite` and returns 403 when absent, 400 for a foreign non-system role, 403 for the system Creator role, and 409 for an email already belonging to an account (without sending mail). Resending to an unregistered email replaces its unredeemed invitations in the tenant transactionally before creating the new token. A stored invitation answers **201 whether or not the email was delivered**: `data` contains `id`, `email`, `role_id`, `expires_at`, `status`, and `email_sent`, never `token`; its message states the delivery outcome (KEL-36). Validation handles absent/expired/used tokens, including revoked and superseded tokens. Delivery failures are logged with invitation and tenant IDs, never the token |

| Members (`GET /api/v1/members`) | Bearer tenant token; pagination and filters; `sort` supports `joined_at`, `created_at` (alias of joined_at), `updated_at`, `email`, `name`; `order` asc/desc | Without `sort`, 200 ordered by `joined_at ASC`, then `tm.id ASC` for stable pagination; `order=desc` reverses both. Unknown sort → 400 `Invalid sort`; surrounding spaces are trimmed, but sort names are case-sensitive. Repository failures → sanitized 500. Tenant context comes only from the verified JWT claim: 403 without tenant claim, 401 for unusable claim (KEL-165) |
| Other members / tutors | pagination/query filters; UUID path | tenant context from the verified JWT claim only; 403 when the token carries no tenant claim, 401 when the claim is unusable, 400 malformed query/ID |
| Own membership (`GET /api/v1/members/me/membership`) | Bearer tenant token; no body | 200 `{member_id, role_id, role_name, permissions}` read from the caller's active membership in the claim tenant, never from the token claims. 403 for a tenantless/parent token or an inactive membership, 500 on lookup failure |
| Member role change (`PUT /api/v1/members/{id}/role`) | Bearer tenant token; `role_id` | 200 updated member (visible in `GET /api/v1/members/{id}`). `member:update` required through an active membership with the token's role (403 otherwise, checked before any lookup). Inside one transaction, before any write: 404 member not in the token's tenant; **409 "You cannot change your own member role"** when the target is the caller's own membership (matched on the `member_id` claim, or `user_id` for tokens without it); 409 "Role does not belong to tenant" for a role of another tenant or an unknown role; 403 "Creator role requires platform approval" for the system Creator target (KEL-94); 403 "Creator role cannot be changed" when the member's current role is the system Creator. A member on the system Teacher role, or on a tenant custom role, can be moved (KEL-79) |
| Member removal (`DELETE /api/v1/members/{id}`) | Bearer tenant token; UUID path id | 200 success envelope; the membership is soft-deleted (`deleted_at`) and disappears from `GET /api/v1/members`. `member:delete` required through an active membership with the token's role (403 otherwise, checked before any lookup). Inside one transaction, before the write: 404 when the member is not in the token's tenant, or was already removed (including by a concurrent request); **409 "You cannot remove your own membership"** when the target is the caller's own membership (matched on the `member_id` claim, or `user_id` for tokens without it) and nothing is deleted. The removed member's still-valid token is then denied (403) on permission-gated routes by the KEL-76 active-membership rule. A member holding the system Creator role is not protected from removal by another caller with `member:delete` (see known gaps) (KEL-81) |
| Roles / permissions | role DTOs | custom-role create/update/delete require `role:create`, `role:update`, and `role:delete`; tenant ownership and system-role restrictions are enforced in the role use case. Every permission decision is evaluated inside the caller's tenant: the assignment counts only when the role belongs to that tenant or is a system role (`roles.tenant_id IS NULL`), so a role lifted from another tenant is denied and a role deleted after the token was issued resolves no rows and is denied |
| Tenant settings/location | settings: name max 255 characters, phone? max 50; location: google_place_id? max 255 | settings and location mutation require `tenant:update` (403 when absent); 400 invalid/oversized input; 409 if settings rename matches another tenant's name case-insensitively, without mutation; own-name case-only rename is allowed. Optional geocode on address-only location update |

**Implemented (KEL-165):** member-list sort is normalized and validated at the HTTP boundary; only fixed mapped SQL columns reach `ORDER BY`, with `tm.id` as a deterministic secondary key. The earlier generic member-list entry did not document a default, while the old repository fallback used the nonexistent `tm.created_at` and returned 500 without `sort`; the current contract above corrects that behavior. Local real-identity/PostgreSQL E2E 22/22 passed, recorded outside the repository in `.kel-autopilot/kel165/manual-e2e.md`; PR and post-merge CI `gate` passed. No web or tutor-route changes.

Invited-user registration also rejects passwords over 72 bytes and first/last names over 255 characters with the identity error envelope (400). **Implemented (KEL-88):** byte-length password guards precede registration use cases; settings name conflicts are checked before mutation (unique-constraint races remain outside this change). Evidence: identity PR #15, squash `cc9459680436ce5ac5d2bd246b718a53efb30fb4`; `internal/delivery/http/handler/{auth_handler,invitation_handler,tenant_handler,registration_limits_test}.go`, `internal/domain/tenant.go`, `internal/usecase/{tenant_usecase,tenant_settings_conflict_test}.go`, `internal/repository/{tenant_repository,tenant_name_test}.go`.

Every tenant-scoped route resolves its tenant from the `tenant_id` claim of the
validated access token (`internal/delivery/http/handler/tenant_context.go`,
KEL-16). A caller whose token carries no tenant claim — all parents, and any
user without an active membership — is rejected with **403 before the use case
is invoked**, so no repository query runs and no other tenant's data is read or
written. A `X-Tenant-ID` header is ignored entirely and is no longer part of any
published operation in `docs/swagger.json`; sending the caller's own tenant in
the header changes nothing, because the claim always wins.

Status codes on these routes are deliberately distinct:

- **403** — the token is valid but grants no tenant scope for this operation.
- **401** — the token was accepted by the middleware but carries an unusable
  (unparseable) tenant claim; a missing or nil claim is 403, not 401.
- **400** — malformed request input such as an unparseable UUID in the path or
  query, unchanged from before.

All payload fields should be confirmed against current Go domain structs or `docs/swagger.json` before client generation. The in-web copied Swagger documents are stale `Tutorin` artifacts and should not be used as the primary contract.
