# Operations

**Implemented health endpoints:** gateway `GET /health`, identity `GET /health`, academic `GET /health`, and billing `GET /health` return `{"status":"healthy","service":...}` without dependency probes. Evidence: gateway router `:29-35`; `cmd/server/health.go` in services.

Identity, billing, and gateway install JSON `slog` as default; academic uses slog in startup but no access-log middleware is registered in it. Gin recovery is registered in every Go HTTP server. No Prometheus/metrics endpoint, distributed tracing, readiness probe, liveness dependency check, backup/restore procedure, or alert configuration was found.

The gateway is the only service with an access log: `middleware/access_log_middleware.go` writes exactly one JSON line per request with `request_id`, `method`, `path`, `status`, `latency_ms`, `client_ip`, and `target`. Query strings, the `Authorization` header, and request bodies are never logged, so the invitation `?token=…` carried by the public verification route and the browser page at `/invitations/verify` does not reach the log. Requests refused by CORS or the rate limiter are logged too, because correlation middleware runs first. The identifier is `X-Request-ID` on both the request and the response; an operator with a request ID from a user report can find the matching line, but the identifier is not written by the downstream services, so following a request past the gateway still needs timestamp and path. See [ADR 0015](adr/0015-gateway-request-correlation-and-access-log.md).

Billing handles SIGINT/SIGTERM and performs a 10-second HTTP shutdown. Its subscription worker is optional and runs in-process when enabled; its payment reconciliation worker and its transaction expiry worker are enabled by default and run in-process (`kelolakelas-billing-service/cmd/server/main.go:69-116`). The reconciliation worker retries durable Academic state; the expiry worker marks overdue unpaid transactions `expired` in bounded batches with a conditional update that is safe across replicas. Identity and academic use `r.Run`, with no analogous graceful shutdown shown. The gateway constructs its own `http.Server` (`cmd/server/main.go`, `newHTTPServer`) so it can apply bounded `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout` and `IdleTimeout` values; a connection that stalls at any phase is closed at the configured bound instead of holding a goroutine and a file descriptor indefinitely. It too has no graceful shutdown: `ListenAndServe` is not paired with a signal handler. Terminal reconciliation failures require operator follow-up through the billing transaction response fields.

A reconciliation row names the Academic action it owes through `kind`. `activation` confirms a paid seat and a `release` returns the seat of a payment that failed or expired. Reading the kind is what tells an operator whether an outstanding or failed job means a parent's payment has not been applied yet or a seat is still held for a payment that never completed; a `release` row stuck at `terminal_failed` leaves the seat occupied and needs intervention. A `paid` transaction whose reconciliation row is `release` with a rejection in `last_error` means the parent paid after the seat was already released. See [ADR 0012](adr/0012-release-enrollment-seat-on-failed-payment.md).

Terminal reconciliation failures no longer depend on a provider callback to be recovered. Billing exposes two internal-credential endpoints, `GET /internal/billing/reconciliations` and `POST /internal/billing/reconciliations/requeue`, both behind `middleware.InternalServiceAuth` like the other internal routes (`cmd/server/main.go`, `internal/delivery/http/handler/reconciliation_handler.go`, `internal/usecase/reconciliation_admin_usecase.go`). The list endpoint accepts an optional `status` query parameter restricted to the four statuses the state machine writes — `pending`, `processing`, `active`, `terminal_failed` — and an unknown value answers `400` rather than an empty page, so a mistyped filter cannot read as "nothing failed". Omitting the parameter returns up to 200 rows newest first. The re-drive endpoint moves at most 200 `terminal_failed` rows back to `pending` with a due-immediately timestamp: the status guard lives in the statement, so an already pending, in-flight, or completed job is never reset and the call is safe to replay. The attempt count is preserved, so `PAYMENT_RECONCILIATION_MAX_ATTEMPTS` still bounds the next round. Both endpoints answer `503` when the service was started without a reconciliation store.

Every reconciliation transition is now logged as a structured `slog` line carrying `transaction_id`, `enrollment_id`, `kind`, `status`, and `attempt_count`; `internal/repository/payment_reconciliation_repository.go` is the only layer that logs, because it is the layer that knows whether a statement actually changed a row. A conflicting insert or a skipped conflict update is therefore never reported as a transition. Retries are `WARN` with `next_attempt_at`, reaching the attempt limit is `ERROR`, and the completion of an activation or release is `INFO`. Expiry and cancellation enqueue release jobs inside one batch statement, so those transitions are logged from the row the statement reports as inserted. No credential, provider payload, or request header value is included. See [ADR 0001](adr/0001-durable-payment-reconciliation.md).

Operators monitoring unpaid invoices should treat `status = 'expired'` as expected steady state rather than an incident, and should read `paid` with a non-null `expired_at` as a payment that arrived after the local deadline — not as a data conflict. Expiry timing is tunable through `TRANSACTION_EXPIRY_WORKER_INTERVAL_MINUTES` and the invoice window through `SUBSCRIPTION_PAYMENT_EXPIRY_PERIOD_DAYS`.
