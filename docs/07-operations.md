# Operations

**Implemented health endpoints:** gateway `GET /health`, identity `GET /health`, academic `GET /health`, and billing `GET /health` return `{"status":"healthy","service":...}` without dependency probes. `GET /ready` returns JSON `status`, `service`, and `components`: required failures return 503 (`database` in each stateful service, `identity_grpc` in academic, `identity`/`academic`/`billing` in gateway); Redis failures in identity/gateway report `degraded` with HTTP 200 if required dependencies are healthy. Since KEL-122 chat is an optional gateway probe: it is skipped when `CHAT_SERVICE_URL` is empty and checked at `/health` when set. Probes share a one-second request deadline and do not write. Route registration and handlers: gateway `internal/delivery/http/{router,readiness}.go`; services `cmd/server/{main,readiness,health}.go` (KEL-40).

Deploy identity before academic, then the other services before gateway. A gateway pointed at an older service without `/ready` reports 503 until it is upgraded. Configure orchestration liveness against `/health` and readiness against `/ready`; do not use the readiness endpoint as liveness. No database migration is required. The readiness payload reports component status only, not connection details. Identity, billing, and gateway install JSON `slog` as default; academic uses slog for startup and request/event logging. Gin recovery is registered in every Go HTTP server. No Prometheus/metrics endpoint, distributed tracing, backup/restore procedure, or alert configuration was found.

**Implemented (KEL-39):** The gateway access log (`middleware/access_log_middleware.go`) writes `request_id`, `method`, `path`, `status`, `latency_ms`, `client_ip`, and `target`. `client_ip` is also the rate-limiter key: the socket address unless trusted proxies are configured (KEL-62, [ADR 0025](adr/0025-gateway-client-ip-from-explicit-trusted-proxies.md)). Requests refused by CORS or the rate limiter are logged too. Its `X-Request-ID` is forwarded to identity, academic, or billing, where each HTTP middleware validates the ID (ASCII letters/digits/`-_.`, 1–64 bytes), generates a safe ID for direct/invalid-header requests, sets the response header, and logs `request_id`, method, route template, final status, and `duration_ms`. Query strings, path parameters, request bodies, `Authorization`, and internal credentials are not serialized by these access loggers. An unmatched path logs `unmatched`. Academic omits only successful GET/HEAD on public catalog list/detail; errors, enrollment POST, and internal calls remain visible. Follow `request_id` from the gateway line to the downstream HTTP line, then through academic/billing permission gRPC metadata to identity's gRPC `request_id`/method/code line; billing also forwards it on activate/release HTTP calls to academic. Billing warns on invalid Duitku callback signature and academic/billing warn on permission 403/503 with the same ID. Billing's internal-call failure warnings omit provider error contents. Background workers have no invented HTTP ID (their warning field can be empty); pre-existing unrelated error logs are not globally redacted. Operators should filter by ID and correlate status before inspecting failures; do not treat absence of a successful public catalog access line as dropped traffic. See [ADR 0015](adr/0015-gateway-request-correlation-and-access-log.md) for the gateway boundary; service evidence is indexed in [KEL-39](reference/evidence-index.md).

Billing handles SIGINT/SIGTERM and performs a 10-second HTTP shutdown. Since KEL-71 its server also applies bounded `ReadHeaderTimeout`/`ReadTimeout`/`WriteTimeout`/`IdleTimeout` (`SERVER_*_TIMEOUT_SECONDS`, defaults 5/30/60/120), and it refuses to start when `SERVER_WRITE_TIMEOUT_SECONDS` does not exceed the Duitku webhook's outbound chain (Duitku + Resend + 10 s Academic) ([ADR 0043](adr/0043-gateway-graceful-shutdown-and-billing-server-timeouts.md)). Its subscription worker is optional and runs in-process when enabled; its payment reconciliation worker and its transaction expiry worker are enabled by default and run in-process (`kelolakelas-billing-service/cmd/server/main.go:69-116`). The reconciliation worker retries durable Academic state; the expiry worker marks overdue unpaid transactions `expired` in bounded batches with a conditional update that is safe across replicas. Identity and academic handle SIGINT/SIGTERM too (KEL-69, [ADR 0040](adr/0040-bounded-graceful-lifecycle-identity-academic.md)): they stop accepting connections and drain in-flight HTTP requests (and, in identity, gRPC calls through `GracefulStop`) for up to `SERVER_SHUTDOWN_TIMEOUT_SECONDS` (default 15), then force-close what remains and exit 1; a clean drain exits 0. Set the platform's termination grace period above that value, or SIGKILL still cuts the drain. Both also apply bounded HTTP server timeouts, and identity refuses to start when `:50051` or its HTTP port cannot be bound. The gateway constructs its own `http.Server` (`cmd/server/main.go`, `newHTTPServer`) so it can apply bounded `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout` and `IdleTimeout` values; a connection that stalls at any phase is closed at the configured bound instead of holding a goroutine and a file descriptor indefinitely. Since KEL-71 it also handles SIGINT/SIGTERM like identity and academic: it stops accepting connections, lets in-flight proxied requests finish for up to `SERVER_SHUTDOWN_TIMEOUT_SECONDS` (default 15), then force-closes what remains and exits 1; a clean drain exits 0 ([ADR 0043](adr/0043-gateway-graceful-shutdown-and-billing-server-timeouts.md)). Keep the platform termination grace period above that value. Terminal reconciliation failures require operator follow-up through the billing transaction response fields.

**Academic session generation worker (KEL-90).** Academic runs `SessionGenerationWorker` in-process on every replica by default (`SESSION_GENERATION_WORKER_ENABLED`). It runs at startup and every `SESSION_GENERATION_INTERVAL_MINUTES` (default 60), and keeps sessions generated through the end of next month (`SESSION_GENERATION_HORIZON_MONTHS`). Replicas share the work through `FOR UPDATE SKIP LOCKED`, and inserts are idempotent. A pass that did work logs `session generation pass finished` with `horizon_end`, `schedules`, `sessions_created` and `failed`. A failing schedule logs `session generation: failed to generate sessions` with its `schedule_id` and is retried on the next tick. Before deploying migration `00001790492411_session_generation_horizon`, confirm that `SELECT schedule_id, session_date, count(*) FROM class_sessions WHERE schedule_id IS NOT NULL GROUP BY 1,2 HAVING count(*) > 1` returns no rows. Otherwise the migration stops with an explicit error and does not delete anything. See [ADR 0042](adr/0042-rolling-session-generation-horizon.md).

A reconciliation row names the Academic action it owes through `kind`. `activation` confirms a paid seat and a `release` returns the seat of a payment that failed or expired. Reading the kind is what tells an operator whether an outstanding or failed job means a parent's payment has not been applied yet or a seat is still held for a payment that never completed; a `release` row stuck at `terminal_failed` leaves the seat occupied and needs intervention. A `paid` transaction whose reconciliation row is `release` with a rejection in `last_error` means the parent paid after the seat was already released. See [ADR 0012](adr/0012-release-enrollment-seat-on-failed-payment.md).

Terminal reconciliation failures no longer depend on a provider callback to be recovered. Billing exposes two internal-credential endpoints, `GET /internal/billing/reconciliations` and `POST /internal/billing/reconciliations/requeue`, both behind `middleware.InternalServiceAuth` like the other internal routes (`cmd/server/main.go`, `internal/delivery/http/handler/reconciliation_handler.go`, `internal/usecase/reconciliation_admin_usecase.go`). The list endpoint accepts an optional `status` query parameter restricted to the four statuses the state machine writes — `pending`, `processing`, `active`, `terminal_failed` — and an unknown value answers `400` rather than an empty page, so a mistyped filter cannot read as "nothing failed". Omitting the parameter returns up to 200 rows newest first. The re-drive endpoint moves at most 200 `terminal_failed` rows back to `pending` with a due-immediately timestamp: the status guard lives in the statement, so an already pending, in-flight, or completed job is never reset and the call is safe to replay. The attempt count is preserved, so `PAYMENT_RECONCILIATION_MAX_ATTEMPTS` still bounds the next round. Both endpoints answer `503` when the service was started without a reconciliation store.

Every reconciliation transition is now logged as a structured `slog` line carrying `transaction_id`, `enrollment_id`, `kind`, `status`, and `attempt_count`; `internal/repository/payment_reconciliation_repository.go` is the only layer that logs, because it is the layer that knows whether a statement actually changed a row. A conflicting insert or a skipped conflict update is therefore never reported as a transition. Retries are `WARN` with `next_attempt_at`, reaching the attempt limit is `ERROR`, and the completion of an activation or release is `INFO`. Expiry and cancellation enqueue release jobs inside one batch statement, so those transitions are logged from the row the statement reports as inserted. No credential, provider payload, or request header value is included. See [ADR 0001](adr/0001-durable-payment-reconciliation.md).

Operators monitoring unpaid invoices should treat `status = 'expired'` as expected steady state rather than an incident, and should read `paid` with a non-null `expired_at` as a payment that arrived after the local deadline — not as a data conflict. Expiry timing is tunable through `TRANSACTION_EXPIRY_WORKER_INTERVAL_MINUTES` and the invoice window through `SUBSCRIPTION_PAYMENT_EXPIRY_PERIOD_DAYS`.

## Session reminder operations (KEL-156)

Apply academic migration `1790900003` before deploying the new binary. It creates only a coverage ledger/function; it does not send messages or backfill history. The dispatch query needs this ledger even when `SESSION_REMINDER_WORKER_ENABLED=false`. No shared development/production migration is performed as part of the implementation.

Default behavior captures tomorrow's sessions according to Asia/Jakarta at boot and every 15 minutes. Configure day offset/window width and polling with the `SESSION_REMINDER_*` settings. Multiple replicas share session locks and durable markers; the notification worker sends chat/email from the existing outbox. Logs `session reminder pass finished` contain session/coverage/queued counts only; a failed pass logs `reminder_outbox_unavailable` and is retried on the next tick. Inspect ledger counts and existing delivery statuses through restricted operator database access; markers mean captured, not delivered. Do not delete markers or alter deterministic event IDs to force a resend.

For acceptance with synthetic data, fix the clock in tests or select tomorrow's WIB date: include an active group sibling pair, a private enrollment and a legacy missing-email enrollment. Run capture twice and concurrently; expect one parent/channel snapshot per session, with chat only for missing email. Cancel a queued session or deactivate all matching enrollments before dispatch; the reminder should end in `failed` with `reminder_no_longer_eligible`, without HTTP delivery. A reschedule into tomorrow after an earlier empty pass is captured on the next poll. A previously reminded session follows KEL-155 change notifications rather than sending a second reminder after replacement.

Turning off capture leaves already-queued deliveries intact; turn off `PARENT_NOTIFICATION_WORKER_ENABLED` as well to pause both. Missed past windows are not backfilled. Already accepted provider messages cannot be recalled; eligibility is checked at capture and again at claim, with unavoidable concurrency after claim. Guarded rollback preserves coverage and outbox history.
